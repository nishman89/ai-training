## 4.1 Evals

<ExamRef section="4.1" />







### In plain English

This domain is about proving your Claude feature works, and noticing when it breaks. Collect example inputs with the correct answers, run your feature on all of them, and score it. Re-run the score after every change.

**Real-life example:** you have 200 sample emails with known categories, and your classifier scores 94%. After a prompt tweak it drops to 81%, so you undo the tweak before customers notice. If you've written a regression suite, you already know this; the twist is that outputs vary, so you grade meaning, not exact strings.

<RoleLens dev={"An eval is a test suite for prompts: fixed inputs, expected outcomes, a score. Run it in CI whenever the prompt or model changes."} test={"This is your world: a regression pack with a pass-rate threshold instead of all-green, because outputs vary. Golden datasets equal test data."} data={"The eval dataset is a curated table. Version it, sample real production rows into it, and track the score over time in a dashboard."} ba={"You write the cases: realistic inputs and what \"good\" looks like. Without BA-quality acceptance criteria an eval measures nothing useful."} />

### Define "done" first

Write a one-page design document **before** building: success criteria specific enough to test (these become eval cases), the failures to survive (retriable or terminal), the cost and latency budget, and the trust boundary. Writing it first stops you rationalising whatever the model happens to produce.

## 4.3 Calibrating an LLM judge

<ExamRef section="4.3" />







### A judge is a second model call with a rubric

Ask it for strengths, weaknesses and short reasoning **before** the score, so the score is grounded.

1. Start with cases already labelled by a human.
2. Run the judge on the same cases and measure how often they agree.
3. If agreement is low, tighten what each score means, add an example of a good and a bad answer, and re-measure.

<CodeSwitch title="A minimal eval as a regression test">

```java
record Case(String input, String expectedLabel) {}

double runEval(List<Case> cases) {
    int pass = 0;
    for (Case c : cases) {
        String out = classifier.classify(c.input());      // the feature under test
        if (out.equals(c.expectedLabel())) pass++;        // code-graded check
    }
    return (double) pass / cases.size();
}

@Test void classifierDoesNotRegress() {
    double score = runEval(loadCases("eval/tickets.jsonl"));
    assertTrue(score >= BASELINE_SCORE, "Score " + score + " fell below baseline");
}
```

```python
from dataclasses import dataclass

@dataclass
class Case:
    input: str
    expected_label: str

def run_eval(cases: list[Case]) -> float:
    passed = sum(classifier.classify(c.input) == c.expected_label   # code-graded check
                 for c in cases)
    return passed / len(cases)

def test_classifier_does_not_regress():                 # pytest
    score = run_eval(load_cases("eval/tickets.jsonl"))
    assert score >= BASELINE_SCORE, f"Score {score} fell below baseline"
```

```typescript
interface Case { input: string; expectedLabel: string }

async function runEval(cases: Case[]): Promise<number> {
  let passed = 0;
  for (const c of cases) {
    if ((await classifier.classify(c.input)) === c.expectedLabel) passed++;   // code-graded check
  }
  return passed / cases.length;
}

test('classifier does not regress', async () => {          // Vitest / Jest
  const score = await runEval(await loadCases('eval/tickets.jsonl'));
  expect(score).toBeGreaterThanOrEqual(BASELINE_SCORE);
});
```

</CodeSwitch>

The same eval gates deployments: run a new model version against a **pinned baseline** before it goes live (Domain 2).

## 4.4 Tests, traces and debugging

<ExamRef section="4.4" />







### Test levels

| Level | For a Claude feature | Catches |
|---|---|---|
| Unit | Your parsing, prompt building, tool code | Ordinary code bugs |
| Functional | A Claude call gives acceptable output for an input | Prompt or model regressions |
| Integration | The handoff between components, e.g. retrieval → model | **Most silent production failures** live here |
| End-to-end | The whole flow from the user's view | Broken journeys |

### Tracing

Record each step of a run: the prompt, tool calls, intermediate outputs and timing. When an eval case fails, the trace shows which step produced the bad result, and later confirms the fix.

### Debugging checklist

1. **stop_reason** - truncated (max_tokens)? refusal? a tool_use you didn't handle?
2. **usage** - did the cache hit? Is the context much bigger than you thought?
3. **The previous turn** - was it assembled from an interrupted stream?
4. **The request-id** - log it for support.
