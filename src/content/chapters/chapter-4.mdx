## 4.1 Evals

<ExamRef section="4.1" />

### In plain English

This domain is about proving your Claude feature works, and noticing when it breaks. The tool for that is an **eval** (short for evaluation): a set of example inputs with the correct answers, run through your feature and scored. It's a test suite for AI output. Re-run the score after every change.

The part that does the scoring is called a **grader**: it decides whether each answer passed. It can be an exact match, a piece of code, a person, or another Claude call acting as a judge (4.2 compares them).

**Real-life example:** you have 200 sample emails with known categories, and your classifier scores 94%. After a prompt tweak it drops to 81%, so you undo the tweak before customers notice. If you've written a **regression suite** (tests you re-run after every change to catch things that used to work), you already know this; the twist is that outputs vary, so you grade meaning, not exact strings.

**Where the test cases come from:** usually real examples. Take a few hundred past tickets, emails or documents, and have people who know the domain write down the correct answer for each (that's called **labelling**). Add the awkward ones on purpose: empty messages, mixed topics, injection attempts. Store them in your repo next to the code, and add a new case whenever a bug reaches production.

### Define "done" first

Before building, write a one-page design document. It answers four questions:

| Question | Example answer (ticket summariser) |
|---|---|
| What counts as success? Specific enough to test: these become your eval cases | "Every summary names the product and the customer's request, in under 60 words" |
| Which failures must it survive? Split into **retriable** (try again) and **terminal** (give up and report) | Retriable: 429, 529, timeouts. Terminal: 400, empty ticket |
| What's the budget? | Under 2 seconds and under $0.002 per ticket |
| Where's the **trust boundary**, the point where untrusted data enters (Domain 7)? | The ticket text: customers write it, so it's treated as data, never as instructions |

Writing this first matters. If you decide what "good" means *after* seeing the output, it's tempting to call whatever the model produced good.

**Why one change at a time:** if you change the prompt, the model and two tool descriptions together and the score drops from 94% to 81%, you can't tell which change caused it, so you can't fix it. Change one thing, re-run, record the score, then change the next. A drop is useful information only when you know what caused it.

Cover the unhappy paths too: ask Claude to brainstorm edge cases that could break the current implementation. Coverage matters more than a perfect **rubric** (the written scoring guide, 4.3); the point is to catch regressions.

## 4.2 Choosing a grader

<ExamRef section="4.2" />
<Imagine text={"Acme's ticket classifier, reply drafter and outage summariser all need testing. A category is simply right or wrong; a reply can be more or less polite. They need different kinds of marking."} />

### Match the grader to the output

A **grader** is whatever scores each eval case. It can be an exact comparison, a piece of code, a human, or an **LLM-as-judge**: another Claude call that reads the output and scores it. Pick the cheapest one that can tell good from bad for your kind of output.

{/* more:4-graders-table */}
| Grader | How it marks | Cost and speed | Good for | Weakness |
|---|---|---|---|---|
| **Exact match** | Output must equal the expected answer | Free, instant | One correct label (BILLING) | Fails on equivalent wording |
| **Code check** | Your code tests a property | Free, instant | Valid JSON, a field present, a number in range | Says nothing about meaning |
| **LLM judge** | Another Claude call scores against a rubric | A model call per case | Tone, helpfulness, "is this summary faithful?" | Must be checked against humans first |
| **Human** | A person marks it | Slow, expensive | Calibrating the judge, high-stakes samples | Doesn't scale |
{/* /more */}

<Compare caption="Three ways to grade, from cheapest to most flexible" columns={[
  { title: 'Exact match', sub: 'one correct form', points: ['Cheapest', 'Most brittle', 'Fails on equivalent wording or order'] },
  { title: 'Code check', sub: 'valid format', points: ['Valid JSON, field present, number in range', 'Fast: run on every commit', 'Says nothing about correctness'] },
  { title: 'LLM-as-judge', sub: 'open-ended quality', points: ['"Is this summary faithful?"', 'Costly and noisy', 'Meaningless until calibrated'] },
]} />

A common split: code checks on every commit, the slower judge on a scheduled quality run. For a single fixed-format output, a code check alone is enough.

```java
boolean passes(String output) {
    try {
        JsonNode json = new ObjectMapper().readTree(output);
        return json.hasNonNull("total")                    // field present

    } catch (JsonProcessingException e) {
        return false;                                      // not even valid JSON
    }
}
```

## 4.3 Calibrating an LLM judge

<ExamRef section="4.3" />
<Imagine text={"You use Claude to mark the reply drafter's answers out of 5, and it gives everything a 4 or 5. Is the drafter that good, or is the marker too generous?"} />

### A judge is a second model call with a rubric

An **LLM judge** reads an output and scores it against a **rubric**, a written guide to what each score means ("5 = correct, complete and polite"). **Calibrating** the judge means checking that its scores agree with a human's before you trust them. Ask it for strengths, weaknesses and short reasoning **before** the score, so the score is grounded.

1. Start with cases already labelled by a human.
2. Run the judge on the same cases and measure how often they agree.
3. If agreement is low, tighten what each score means, add an example of a good and a bad answer, and re-measure.

<CodeSwitch title="A minimal eval as a regression test">

```java
// ── Setup: where the names below come from ──
// Imports: java.util.*
final double BASELINE_SCORE = 0.90;   // the score the last release achieved
// classifier: the code under test (it calls Claude and returns a label)
// loadCases: reads test cases (input + expected label) from a JSONL file
// ── The example ──
record Case(String input, String expectedLabel) {}

double runEval(List<Case> cases) {
    int pass = 0;
    for (Case c : cases) {
        String out = classifier.classify(c.input());      // the feature under test
        if (out.equals(c.expectedLabel())) pass++;        // code-graded check
    }
    return (double) pass / cases.size();
}

@Test void classifierDoesNotRegress() {
    double score = runEval(loadCases("eval/tickets.jsonl"));
    assertTrue(score >= BASELINE_SCORE, "Score " + score + " fell below baseline");
}
```

```python
# ── Setup: where the names below come from ──
BASELINE_SCORE = 0.90   # the score the last release achieved
# classifier: the code under test (it calls Claude and returns a label)
# load_cases: reads test cases (input + expected label) from a JSONL file
# ── The example ──
from dataclasses import dataclass

@dataclass
class Case:
    input: str
    expected_label: str

def run_eval(cases: list[Case]) -> float:
    passed = sum(classifier.classify(c.input) == c.expected_label   # code-graded check
                 for c in cases)
    return passed / len(cases)

def test_classifier_does_not_regress():                 # pytest
    score = run_eval(load_cases("eval/tickets.jsonl"))
    assert score >= BASELINE_SCORE, f"Score {score} fell below baseline"
```

```typescript
// ── Setup: where the names below come from ──
const BASELINE_SCORE = 0.90;   // the score the last release achieved
// classifier: the code under test (it calls Claude and returns a label)
// loadCases: reads test cases (input + expected label) from a JSONL file
// ── The example ──
interface Case { input: string; expectedLabel: string }

async function runEval(cases: Case[]): Promise<number> {
  let passed = 0;
  for (const c of cases) {
    if ((await classifier.classify(c.input)) === c.expectedLabel) passed++;   // code-graded check
  }
  return passed / cases.length;
}

test('classifier does not regress', async () => {          // Vitest / Jest
  const score = await runEval(await loadCases('eval/tickets.jsonl'));
  expect(score).toBeGreaterThanOrEqual(BASELINE_SCORE);
});
```

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
String question = "How many days do I have to return a router?";   // the user's question
String reply = "You can return it within 30 days of delivery.";   // the support reply being graded
// reply: the Message Claude just returned (its stop_reason is "tool_use")
// ── The example ──
String JUDGE = """
    You grade customer-support replies. Rubric:
    1 = wrong or unsafe; 3 = correct but misses the customer's actual question; 5 = correct, complete, polite.
    Explain your reasoning in two sentences, then end with a line: SCORE: <1-5>
    """;

Message verdict = client.messages().create(MessageCreateParams.builder()
    .model(Model.CLAUDE_SONNET_5_5).maxTokens(400L)
    .system(JUDGE)
    .addUserMessage("<question>" + question + "</question>\n<reply>" + reply + "</reply>")
    .build());
String text = verdict.content().stream().flatMap(b -> b.text().stream()).map(TextBlock::text).collect(joining());
int score = Integer.parseInt(text.replaceAll("(?s).*SCORE:\\s*(\\d).*", "$1"));
// Before trusting it: compare these scores with human scores on the same sample
```

## 4.4 Tests, traces and debugging

<ExamRef section="4.4" />
<Imagine text={"A customer complains the bot quoted the wrong refund amount. Every test passes. Where do you even start looking?"} />

### Test levels

<Imagine text={"The search step passes its tests and the answering step passes its tests, yet together they give wrong answers."} />

The usual layers of testing still apply to a Claude feature. What changes is where the failures hide.

| Level | For a Claude feature | Catches |
|---|---|---|
| Unit | Your parsing, prompt building, tool code | Ordinary code bugs |
| Functional | A Claude call gives acceptable output for an input | Prompt or model regressions |
| Integration | The handoff between components, e.g. **retrieval** (fetching relevant documents for the prompt, 6.5) → model | **Most silent production failures** live here |
| End-to-end | The whole flow from the user's view | Broken journeys |

### Tracing

<Imagine text={"A wrong answer went out at 14:03 yesterday. Without a record of exactly what Claude was sent, you can't reproduce it."} />

A **trace** is a step-by-step record of one run. Record each step: the prompt, tool calls, intermediate outputs and timing. When an eval case fails, the trace shows which step produced the bad result, and later confirms the fix.

**What a trace looks like:** here's one run of the order tool from 8.1, where the customer typed "my order is 1234":

```text
run 7f3a · prompt v12 · claude-sonnet-5-5 · 14:03:11
1  user     "Where's my order? It's 1234."
2  claude   stop_reason: tool_use → get_order_status {"order_id": "1234"}    ← wrong: should be "A-1234"
3  tool     is_error: true  "No such order: 1234"
4  claude   stop_reason: end_turn → "Sorry, I can't find that order."        ← wrong answer to the customer
   total: 2 calls · 1,840 tokens in / 96 out · 2.1 s
```

### Is it your code or the model?

<Imagine text={"The app crashes parsing Claude's JSON. One developer wants to rewrite the prompt; another says the parser is the problem. Who's right?"} />

When a Claude feature misbehaves, first decide **which layer** the fault is in, because the fixes are completely different:

| Layer | Symptoms | Typical causes | Fix it in… |
|---|---|---|---|
| **Integration** (your code) | Crashes, parse errors, missing context, duplicate or lost requests | Reading `content[0]`, ignoring `stop_reason`, brittle string slicing, not resending history, no retry or timeout handling | Your code: defensive parsing, structured outputs, proper error handling |
| **Model output** (what Claude wrote) | The request is fine, but the answer is wrong, off-scope, badly formatted or inconsistent | Vague prompt, missing context or examples, wrong model or effort | The prompt, context, model choice, or schema |
| **Tools and data** | Claude's reasoning is fine, but it was given wrong or empty data | A tool hid an error, returned stale data, or retrieval missed | The tool or retrieval layer |

**How to tell:** open the **trace** (above) and compare what was sent with what came back.

| What you see | The layer at fault |
|---|---|
| The reply would satisfy a careful person, but your code still failed | **Integration** |
| The request was right, but the reply is wrong | **Model output** |
| The reply faithfully used bad data | **Tool or data** |

A JSON parser crashing on markdown fences is an **integration** fault first: parse defensively and use structured outputs, rather than only rewording the prompt.

### Debugging checklist

1. **stop_reason** - truncated (max_tokens)? refusal? a tool_use you didn't handle?
2. **usage** - did the cache hit (did prompt caching reuse the saved prefix, 5.3)? Is the context much bigger than you thought?
3. **The previous turn** - was it assembled from an interrupted stream?
4. **The request-id** - the unique ID Anthropic gives every request. Log it so support can find the call.

### After launch: watch for drift

<Imagine text={"The ticket classifier passed every eval and shipped. Two months later complaints rise, yet nobody has changed the code, the prompt or the model ID."} />

Passing evals before release doesn't keep a feature good forever. What users send **changes over time**: new products, new kinds of complaint, a new customer group. That gradual change is called **drift**, and it lowers quality even when nothing in your system has changed. Cost and errors can creep up the same way.

Running a feature after launch (the *operate* phase, 2.5) means watching it continuously:

| Watch | How | Alert when |
|---|---|---|
| **Quality** | Every day, take a random sample of real requests and replies, and score them with your graders (code checks, calibrated LLM judge, occasional human review) | The score falls below the release baseline |
| **Cost** | Sum `usage` tokens per feature and per day (2.1) | Spend per request rises, or the cache hit rate falls |
| **Latency** | Time to first token and total time | The slowest 5% (p95) gets worse |
| **Errors** | Count 4xx/5xx, refusals and `max_tokens` cut-offs | A spike above normal |

Add the bad cases you find to the eval set, so the next release is tested against them.

```java
final double BASELINE_SCORE = 0.90;   // the score the last release achieved
// callLog, metrics, alerts: your own services: the request/response log (4.4), a metrics store, and alerting (PagerDuty, Slack…)
// judge: a calibrated LLM judge (4.3): judge(input, output) returns a score
// ── The example ──
List<LoggedCall> sample = callLog.randomSample(Duration.ofDays(1), 200);    // yesterday's real traffic

    .average().orElse(0);

    alerts.raise("Classifier quality " + score + " is below baseline " + BASELINE_SCORE);
}
```
