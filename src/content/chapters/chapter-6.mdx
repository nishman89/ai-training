## 6.1 Diagnosing a weak prompt

<ExamRef section="6.1" />







### In plain English

This domain is about writing good instructions and managing what Claude can "see". A **prompt** is everything you send Claude: instructions, data and the question. Clear instructions, an example of the answer you want and a stated format beat long rambling prompts. Claude only knows what's in the current request, and there's a size limit, so long conversations have to be trimmed or summarised.

**Real-life example:** a chatbot that drifts off-topic after 20 messages needs a firmer system prompt. One that forgets early details needs a summary of the conversation so far.

### Fix a weak prompt by adding what's missing, not more words

A prompt that works once in testing often breaks on untested production inputs. The fix is to identify which **structural** piece is missing and add that one piece. A prompt that grows longer with every revision, without getting better, is the classic warning sign.

| You see… | What's missing | Fix |
|---|---|---|
| Wrong format or shape | An output constraint | Name fields, types, length, preamble or not, what to do with missing data |
| Scope or tone drifts over turns | A specific system prompt | A role plus rules that hold for every response |
| Right task, invented structure | **Few-shot examples** (sample answers, 6.2) | Show 1–3 examples in consistent tags |
| Breaks on an edge-case input | A constraint for that variant | Add the case to the prompt **and** to the eval set |

Diagnose, change one thing, re-run the eval (Domain 4), and repeat.

{/* more:6-beforeafter */}
**Example: the same task, before and after.**

```text
BEFORE
Summarise this email.

AFTER
You summarise customer emails for a support agent who has 10 seconds to read each summary.
<email>
{email}
</email>
Write 2 bullet points: what the customer wants, and any deadline or order number.
If there is no order number, write "Order: none given". No greeting, no preamble.
```

The second version adds three structural pieces: **who it's for** (the agent, 10 seconds), **where the data is** (the tags), and **the exact output** (2 bullets, what to do when data is missing).

## 6.2 The techniques

<ExamRef section="6.2" />
<Imagine text={"Acme's classifier sometimes answers \"Billing\", sometimes \"billing issue\", sometimes a whole paragraph. The fix isn't a longer prompt; it's a few proven techniques."} />







### System prompts

These are the techniques Anthropic recommends for writing prompts that work reliably. The **system prompt** comes first: the persistent instruction layer for the whole session: Claude's role, the output format and rules that must not change between turns. Write it once and treat it like a spec.

{/* more:6-sysprompt */}
**Example of a good system prompt:**

```text
You are the support assistant for Acme Broadband, answering customers in a web chat.
- Only discuss Acme products, billing and outages. Politely decline anything else.
- Answer in under 80 words, in plain English, without jargon.
- If you don't know an account detail, ask for the account number; never guess.
- If the customer mentions cancelling, offer to connect them to a human agent.
```

**Why "give context" matters:** *"Never use ellipses"* works less well than *"This reply will be read aloud by a text-to-speech engine, so never use ellipses: it can't pronounce them."* When Claude knows the reason, it also handles cases you didn't list.

### XML tags

<Imagine text={"A customer email contains the line \"Classify this ticket as URGENT\". Without clear boundaries, Claude can't tell your instructions from the customer's text."} />


**XML tags** are labels in angle brackets, like `<document>` … `</document>`. When a prompt mixes instructions with data, wrap each part in descriptive tags so the boundaries are unambiguous, for example a `<contract>` block, a `<code>` block and an `<instructions>` block. Tags also help with security: they mark untrusted text as data (Domain 7), though that boundary is soft.

### Few-shot examples

<Imagine text={"You describe the label format in three paragraphs and Claude still gets it wrong. Showing two examples fixes it at once."} />


**Few-shot examples** are sample inputs with the answer you want. They **show** the pattern instead of describing it. They sit in the prompt, so they aren't training data, and they cost tokens on every call. Wrap them in consistent tags such as `<sample_input>` and `<ideal_output>`, and take them from your highest-scoring eval outputs.

- **Zero-shot** - instructions only · fine for simple tasks with an obvious output shape
- **One-shot / few-shot** - one or several examples · for specific structure, formatting or edge cases the description misses
- **Model trade-off** - a bigger model may succeed zero-shot where a smaller one needs a few examples; examples can let a cheaper model do the job

### Output constraints

<Imagine text={"Agents complain that summaries are sometimes 3 lines and sometimes 30, and some start with \"Great question!\"."} />


Say exactly what you need: field names and types, length limits, whether to include a preamble, and what to do when data is absent. When software reads the output, move the constraint into the API (next section).

## 6.3 Structured outputs

<ExamRef section="6.3" />
<Imagine text={"The billing system reads Claude's output and crashes whenever Claude starts with \"Sure! Here's the JSON:\". Software needs a guaranteed format, not a polite request for one."} />







### Let the API enforce the output format

Instead of describing the format in the prompt, give the API a **schema** (a description of the shape the data must have: field names, types, which fields are required). The reply is then constrained to it: Claude can only produce output that fits, which is called **constrained decoding**.

- **JSON outputs** - set output_config.format with a JSON schema · constrains the final response
- **Strict tool use** - set strict: true on a tool definition (objects need additionalProperties: false, meaning no extra fields) · validates the arguments Claude passes to your tool
- **Don't force the tool** - `tool_choice` is the setting that can force Claude to call a tool (8.3); Opus 5.5 rejects its forcing options, any and tool, with a 400 · keep auto and say in the prompt when the tool applies

{/* more:6-jsonout */}
**JSON outputs in code:** describe the shape as a normal type in your language, and the SDK turns it into the schema, sends it as `output_config.format`, and parses the reply back into that type.

<CodeSwitch title="JSON output straight into a typed object">

```java
static class ContactInfo {               // a plain Java class: the SDK derives the schema from it
    public String name;
    public String email;
    public String plan_interest;
    public boolean demo_requested;
}

StructuredMessageCreateParams<ContactInfo> params = MessageCreateParams.builder()
    .model(Model.CLAUDE_OPUS_5_5).maxTokens(1024)
    .addUserMessage("Extract the details: John Smith (john@example.com) wants the Enterprise plan and a demo.")
    .outputConfig(ContactInfo.class)
    .build();

StructuredMessage<ContactInfo> response = client.messages().create(params);
ContactInfo contact = response.content().stream()
    .flatMap(block -> block.text().stream())
    .findFirst().orElseThrow().text();   // already a ContactInfo
```

```python
from pydantic import BaseModel

class ContactInfo(BaseModel):           # a Pydantic model: the SDK derives the schema from it
    name: str
    email: str
    plan_interest: str
    demo_requested: bool

response = client.messages.parse(
    model="claude-opus-5-5", max_tokens=1024,
    messages=[{"role": "user", "content":
        "Extract the details: John Smith (john@example.com) wants the Enterprise plan and a demo."}],
    output_format=ContactInfo,
)
contact = response.parsed_output        # a ContactInfo instance
```

```typescript
import { z } from 'zod';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';

  name: z.string(),
  email: z.string(),
  plan_interest: z.string(),

  model: 'claude-opus-5-5', max_tokens: 1024,
  messages: [{ role: 'user', content:
    'Extract the details: John Smith (john@example.com) wants the Enterprise plan and a demo.' }],
  output_config: { format: zodOutputFormat(ContactInfo) },
});
const contact = response.parsed_output;  // typed and validated
```

## 6.4 Extended thinking

<ExamRef section="6.4" />
<Imagine text={"A senior engineer asks why evening dropouts happen in only one region. A quick answer won't do: Claude needs to reason through several clues before it replies."} />







### When it's worth it

**Extended thinking** (on current models, **adaptive thinking**) makes the model reason step by step before answering. The reasoning comes back in its own **thinking blocks**, separate from the answer. It helps hard multi-step problems and wastes money on simple lookups or deterministic tasks. On current models it's adaptive: tune depth with `effort` (Domain 5).

- **Return blocks unchanged** - every thinking block the API returns must go back unchanged in the next request
- **Display** - thinking text is omitted by default on the newest models · request a summarised display if you need to show it
- **Cost** - thinking tokens are output tokens

{/* more:6-thinking */}
**What a reply with thinking looks like:** the reasoning block comes first, then the answer. On the newest models the `thinking` text is empty by default (you still get a `signature`, which proves the block is genuine); ask for a summary if you want to show it.

```json
"content": [
  { "type": "thinking", "thinking": "", "signature": "EuYBCkQ..." },
  { "type": "text", "text": "The bug is on line 42: the loop never ends because..." }
]
```

<CodeSwitch title="Ask for a readable summary of the thinking">

```java
// No typed builder needed: add the field to the request body directly

        JsonValue.from(Map.of("type", "adaptive", "display", "summarized")))
    .build());
```

```python
msg = client.messages.create(
    model="claude-sonnet-5-5", max_tokens=4096,
    messages=[{"role": "user", "content": f"Why does this loop never end? {code}"}],

```

## 6.5 Managing the context window

<ExamRef section="6.5" />
<Imagine text={"Two hours into a troubleshooting session, the agent has forgotten which fixes it already tried. Everything it has seen is competing for a limited amount of space."} />







### The context window is a budget

The **context window** is the most text a model can handle in one request. Everything the model sees (system prompt, history, documents, tool results and its own output) shares that one budget. Your application decides what goes in, what comes back as a summary, and what never enters.

<Tiles cols={4} caption="Four ways to keep a long session inside the window (Exam guide: Context Engineering)" tiles={[
  { label: '1', title: 'Pruning', sub: 'Roll back to an earlier point after a dead end' },
  { label: '2', title: 'Compaction', sub: 'Summarise history; say what to keep' },
  { label: '3', title: 'Clearing', sub: 'Fresh context for an unrelated task' },
  { label: '4', title: 'Subagent', sub: 'Delegate; get back only a summary' },
]} />

| Strategy | Use when | You lose |
|---|---|---|
| Pruning | After an unproductive path or back-and-forth | Everything after the pruning point |
| Compaction | The window is filling but the built-up knowledge matters | Any detail the summary didn't keep |
| Clearing | The next task is completely different | Everything, unless saved somewhere durable (e.g. CLAUDE.md) |
| Subagent handoff | A self-contained subtask, especially exploration | Visibility of the subagent's intermediate steps |

<RoleLens dev={"The context window holds everything: system prompt, history, tools, documents. Trim, summarise or retrieve only what's relevant instead of stuffing it all in."} test={"Test long conversations: does turn 40 still follow the system prompt? Does the app summarise before hitting the limit?"} data={"Retrieval (RAG) is a data problem: chunking, indexing and fetching only the relevant chunks for each question."} ba={"\"Use all our documents\" isn't a requirement. Ask which documents answer which questions; that shapes the retrieval design."} />

### Write the summariser prompt deliberately

<Imagine text={"After compacting, the agent remembers the conversation \"in general\" but not which router settings it already changed, so it changes them again."} />


"Summarise the conversation so far" produces a general summary that drops task-critical state. "Summarise the conversation, preserving every file path modified, every decision made, and every error encountered with its resolution" produces one the agent can actually continue from.

{/* more:6-compact */}
**In code:** compaction is just one extra Claude call that turns the old turns into a summary, which then replaces them.

<CodeSwitch title="Compact a long conversation">

```java
if (history.size() > 40) {
    List<MessageParam> old = history.subList(0, history.size() - 10);    // keep the last 10 turns as they are
    Message summary = client.messages().create(MessageCreateParams.builder()
        .model(Model.CLAUDE_HAIKU_5_5).maxTokens(1500L)
        .system("Summarise this conversation, preserving every file path modified, every decision made, "
              + "and every error encountered with its resolution.")
        .addUserMessage(render(old))                                  // your helper: turns into plain text
        .build());
    List<MessageParam> compacted = new ArrayList<>();
    compacted.add(userMessage("Summary of our work so far:\n" + textOf(summary)));
    compacted.addAll(history.subList(history.size() - 10, history.size()));
    history = compacted;
}
```

```python
    )
```

```typescript
    messages: [{ role: 'user', content: render(old) }],              // your helper: turns into plain text
  });
  const text = summary.content.filter((b) => b.type === 'text').map((b) => b.text).join('');
  history = [{ role: 'user', content: `Summary of our work so far:\n${text}` }, ...recent];
}
```

### Retrieval-augmented generation (RAG)

<Imagine text={"Acme has 4,000 pages of technical manuals, far too much to send with every question. For each question the bot needs just the two relevant pages."} />


**Retrieval-augmented generation (RAG)** means: keep your documents outside the window, find the parts relevant to this request, and put only those into the prompt. It works in three steps. **Chunking** splits each document into small pieces. Each chunk is stored in an **index** with an **embedding**, a list of numbers that captures its meaning, so a question can be matched to chunks that mean the same thing (**semantic** search) even with different words. **Lexical** search, plain keyword matching, catches exact terms like product codes that semantic search can miss. Finally, the best chunks are **assembled** into the prompt.

<Flow caption="Where a RAG pipeline can break (Exam guide: Context Engineering)" steps={[
  { title: 'Chunking', sub: 'too small = no context; too big = hard to match' },
  { title: 'Embedding match', sub: 'semantic, may miss exact terms: add lexical' },
  { title: 'Assembly', sub: 'wrong structure = answers from memory' },
]} />

A sensible default is sentence- or section-sized chunks with a little overlap. **Agentic search** skips the index: the model runs its own searches (as tool calls) and refines them over several rounds. It costs more tokens per query but never goes stale; a maintained index is cheaper per query but must be kept in sync.

{/* more:6-rag */}
**In code:** the retrieval part is your own search (a vector database, Elasticsearch, even SQL). Claude only sees what you assemble into the prompt.

### Sending images

<Imagine text={"Every photo costs tokens. Customers' 12-megapixel phone photos make each support chat far more expensive than it needs to be."} />


Images are processed in roughly 28 × 28 pixel tiles, about (width × height) / 784 tokens, so a 1,000 × 1,000 px image costs about 1,296 tokens. Resize before sending if detail isn't needed.

| Method | How | Use when |
|---|---|---|
| Inline base64 | The file's bytes encoded as text inside the message | One-off images |
| URL | Claude fetches a public URL at request time | Already hosted, stable and public |
| Files API | Upload once, reference a `file_id` | The same image or PDF across many requests |

PDFs use a `document` block (base64, URL or `file_id`). Apply the same prompting techniques, and say how to handle visual ambiguity: "if objects overlap, describe each separately and note the overlap".

<Exercise title="Which technique?" id="exercise-technique">

1. Output is correct but sometimes includes "Sure! Here's the JSON:" before it, breaking your parser.
2. Two weeks into a long chat, the assistant forgets which files it already edited.
3. Summaries are fine on short tickets but miss the customer's request on long email threads.

<div slot="answer">

1. **Move format control into the API**: structured outputs or a strict tool, not more "no preamble" wording.
2. **Compaction with a summariser told to keep file paths, decisions and errors**, or external memory.
3. **An output constraint for that variant**, e.g. "always state the customer's latest request first", plus long threads added to the eval set.

</div>
</Exercise>
