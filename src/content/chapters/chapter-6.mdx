## 6.1 Diagnosing a weak prompt

<ExamRef section="6.1" />







### In plain English

This domain is about writing good instructions and managing what Claude can "see". Clear instructions, an example of the answer you want and a stated format beat long rambling prompts. Claude only knows what's in the current request, and there's a size limit, so long conversations have to be trimmed or summarised.

**Real-life example:** a chatbot that drifts off-topic after 20 messages needs a firmer system prompt. One that forgets early details needs a summary of the conversation so far.

### Fix a weak prompt by adding what's missing, not more words

A prompt that works once in testing often breaks on untested production inputs. The fix is to identify which **structural** piece is missing and add that one piece. A prompt that grows longer with every revision, without getting better, is the classic warning sign.

| You see… | What's missing | Fix |
|---|---|---|
| Wrong format or shape | An output constraint | Name fields, types, length, preamble or not, what to do with missing data |
| Scope or tone drifts over turns | A specific system prompt | A role plus rules that hold for every response |
| Right task, invented structure | Few-shot examples | Show 1–3 examples in consistent tags |
| Breaks on an edge-case input | A constraint for that variant | Add the case to the prompt **and** to the eval set |

Diagnose, change one thing, re-run the eval (Domain 4), and repeat.

## 6.2 The techniques

<ExamRef section="6.2" />







### System prompts

The persistent instruction layer for the whole session: Claude's role, the output format and rules that must not change between turns. Write it once and treat it like a spec.

<RoleLens dev={"Clear role and task, XML tags to separate inputs, a few examples, and asking for reasoning before the answer: these are the techniques that work."} test={"Few-shot examples are like test fixtures for the model: include the edge cases you most care about."} data={"Wrap each record in tags (`<row>…</row>`) and give 2–3 examples of input → output. Consistency across millions of rows depends on it."} ba={"Examples in a prompt work like worked examples in a spec: they remove ambiguity faster than more prose."} />

### XML tags

When a prompt mixes instructions with data, wrap each part in descriptive tags so the boundaries are unambiguous, for example a `<contract>` block, a `<code>` block and an `<instructions>` block. Tags also help with security: they mark untrusted text as data (Domain 7), though that boundary is soft.

### Few-shot examples

Examples **show** the pattern instead of describing it. They sit in the prompt, so they aren't training data, and they cost tokens on every call. Wrap them in consistent tags such as `<sample_input>` and `<ideal_output>`, and take them from your highest-scoring eval outputs.

- **Zero-shot** - instructions only · fine for simple tasks with an obvious output shape
- **One-shot / few-shot** - one or several examples · for specific structure, formatting or edge cases the description misses
- **Model trade-off** - a bigger model may succeed zero-shot where a smaller one needs a few examples; examples can let a cheaper model do the job

### Output constraints

Say exactly what you need: field names and types, length limits, whether to include a preamble, and what to do when data is absent. When software reads the output, move the constraint into the API (next section).

## 6.3 Structured outputs

<ExamRef section="6.3" />







### Let the API enforce the output format

Instead of describing the format in the prompt, give the API a schema and the response is constrained to it (constrained decoding).

- **JSON outputs** - set output_config.format with a JSON schema · constrains the final response
- **Strict tool use** - set strict: true on a tool definition (objects need additionalProperties: false) · validates the arguments Claude passes to your tool
- **Don't force the tool** - Opus 5.5 rejects tool_choice any and tool with a 400 · keep auto and say in the prompt when the tool applies

<MythReality rows={[
  { myth: 'A guaranteed schema means a guaranteed answer', reality: 'You can still get stop_reason refusal, or max_tokens truncation. Check stop_reason before parsing' },
  { myth: 'Schemas are free', reality: 'The first request on a new schema is slower (it compiles to a grammar, cached ~24 h), and the added instructions count as input tokens' },
  { myth: 'Combine JSON outputs with prefilling the reply', reality: 'Structured outputs and assistant-message prefilling are not compatible' },
]} />

<CodeSwitch title="Structured output via a strict tool">

```java
Tool recordInvoice = Tool.builder()
    .name("record_invoice")
    .description("Record the fields extracted from an invoice. Call exactly once.")
    .inputSchema(Tool.InputSchema.builder()
        .properties(JsonValue.from(Map.of(
            "vendor",   Map.of("type", "string"),
            "total",    Map.of("type", "number"),
            "due_date", Map.of("type", "string", "description", "ISO-8601 date"))))
        .required(List.of("vendor", "total"))
        .putAdditionalProperty("additionalProperties", JsonValue.from(false))   // required for strict
        .build())
    .strict(true)                                       // validate args against the schema
    .build();

Message msg = client.messages().create(MessageCreateParams.builder()
    .model(Model.CLAUDE_HAIKU_5_5).maxTokens(512L)
    .addTool(recordInvoice)
    // tool_choice stays auto: forcing a tool ("any"/"tool") is rejected on Opus 5.5
    .addUserMessage("Extract the invoice fields with record_invoice.\n<invoice>\n" + invoiceText + "\n</invoice>")
    .build());
```

```python
record_invoice = {
    "name": "record_invoice",
    "description": "Record the fields extracted from an invoice. Call exactly once.",
    "strict": True,                                     # validate args against the schema
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor": {"type": "string"},
            "total": {"type": "number"},
            "due_date": {"type": "string", "description": "ISO-8601 date"},
        },
        "required": ["vendor", "total"],
        "additionalProperties": False,                  # required for strict
    },
}

msg = client.messages.create(
    model="claude-haiku-5-5", max_tokens=512,
    tools=[record_invoice],
    # tool_choice stays auto: forcing a tool ("any"/"tool") is rejected on Opus 5.5
    messages=[{"role": "user", "content": f"Extract the invoice fields with record_invoice.\n<invoice>\n{invoice_text}\n</invoice>"}],
)
fields = next(b.input for b in msg.content if b.type == "tool_use")
```

    type: 'object',
    properties: {

const msg = await client.messages.create({

const fields = msg.content.find((b) => b.type === 'tool_use')?.input;

## 6.4 Extended thinking

<ExamRef section="6.4" />







### When it's worth it

Thinking makes the model reason step by step before answering. It helps hard multi-step problems and wastes money on simple lookups or deterministic tasks. On current models it's adaptive: tune depth with `effort` (Domain 5).

- **Return blocks unchanged** - every thinking block the API returns must go back unchanged in the next request
- **Display** - thinking text is omitted by default on the newest models · request a summarised display if you need to show it
- **Cost** - thinking tokens are output tokens

## 6.5 Managing the context window

<ExamRef section="6.5" />







### The context window is a budget

Everything the model sees in one request (system prompt, history, documents, tool results and its own output) shares one budget. Your application decides what goes in, what comes back as a summary, and what never enters.

<Tiles cols={4} caption="Four ways to keep a long session inside the window (Exam guide: Context Engineering)" tiles={[
  { label: '1', title: 'Pruning', sub: 'Roll back to an earlier point after a dead end' },
  { label: '2', title: 'Compaction', sub: 'Summarise history; say what to keep' },
  { label: '3', title: 'Clearing', sub: 'Fresh context for an unrelated task' },
  { label: '4', title: 'Subagent', sub: 'Delegate; get back only a summary' },
]} />

| Strategy | Use when | You lose |
|---|---|---|
| Pruning | After an unproductive path or back-and-forth | Everything after the pruning point |
| Compaction | The window is filling but the built-up knowledge matters | Any detail the summary didn't keep |
| Clearing | The next task is completely different | Everything, unless saved somewhere durable (e.g. CLAUDE.md) |
| Subagent handoff | A self-contained subtask, especially exploration | Visibility of the subagent's intermediate steps |

<RoleLens dev={"The context window holds everything: system prompt, history, tools, documents. Trim, summarise or retrieve only what's relevant instead of stuffing it all in."} test={"Test long conversations: does turn 40 still follow the system prompt? Does the app summarise before hitting the limit?"} data={"Retrieval (RAG) is a data problem: chunking, indexing and fetching only the relevant chunks for each question."} ba={"\"Use all our documents\" isn't a requirement. Ask which documents answer which questions; that shapes the retrieval design."} />

### Write the summariser prompt deliberately

"Summarise the conversation so far" produces a general summary that drops task-critical state. "Summarise the conversation, preserving every file path modified, every decision made, and every error encountered with its resolution" produces one the agent can actually continue from.

Also: cache stable prefixes (Domain 5), and **count tokens before sending** so oversized requests are trimmed instead of failing. A session that ran fine in development often hits the ceiling in production because real inputs are longer.

### Retrieval-augmented generation (RAG)

RAG keeps documents outside the window, finds the parts relevant to this request, and supplies only those.

<Flow caption="Where a RAG pipeline can break (Exam guide: Context Engineering)" steps={[
  { title: 'Chunking', sub: 'too small = no context; too big = hard to match' },
  { title: 'Embedding match', sub: 'semantic, may miss exact terms: add lexical' },
  { title: 'Assembly', sub: 'wrong structure = answers from memory' },
]} />

A sensible default is sentence- or section-sized chunks with a little overlap. **Agentic search** skips the index: the model issues its own queries and refines across rounds. It costs more tokens per query but never goes stale; a maintained index is cheaper per query but must be kept in sync.

  title={"The summary that forgot what it had done"}
  scenario={"A long coding session is compacted with the prompt \"summarise the conversation so far\"."}
  gotcha={"The summary is readable but drops which files were edited and which approach was already rejected, so the agent redoes failed work."}
  fix={"Tell the summariser exactly what to keep: file paths changed, decisions made, errors hit and how they were fixed."}
/>

## 6.6 Images and PDFs

<ExamRef section="6.6" />







### Sending images

Images are processed in roughly 28 × 28 pixel tiles, about (width × height) / 784 tokens, so a 1,000 × 1,000 px image costs about 1,296 tokens. Resize before sending if detail isn't needed.

| Method | How | Use when |
|---|---|---|
| Inline base64 | Bytes encoded in the message | One-off images |
| URL | Claude fetches a public URL at request time | Already hosted, stable and public |
| Files API | Upload once, reference a `file_id` | The same image or PDF across many requests |

PDFs use a `document` block (base64, URL or `file_id`). Apply the same prompting techniques, and say how to handle visual ambiguity: "if objects overlap, describe each separately and note the overlap".

<Exercise title="Which technique?" id="exercise-technique">

1. Output is correct but sometimes includes "Sure! Here's the JSON:" before it, breaking your parser.
2. Two weeks into a long chat, the assistant forgets which files it already edited.
3. Summaries are fine on short tickets but miss the customer's request on long email threads.

<div slot="answer">

1. **Move format control into the API**: structured outputs or a strict tool, not more "no preamble" wording.
2. **Compaction with a summariser told to keep file paths, decisions and errors**, or external memory.
3. **An output constraint for that variant**, e.g. "always state the customer's latest request first", plus long threads added to the eval set.

</div>
</Exercise>
