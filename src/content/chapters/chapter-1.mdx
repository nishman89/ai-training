## 1.1 Workflow or agent?

<ExamRef section="1.1" />

### In plain English

This domain is about getting Claude to finish jobs that take several steps. A **workflow** is a fixed recipe you write: step 1 summarise, step 2 translate. An **agent** chooses its own steps: it asks for a **tool** (a function your code runs on Claude's behalf, such as "look up an order"), looks at the result, decides what to do next, and repeats until the job is done.

**Real-life example:** "Find out why order 1234 is late and email the customer." The agent looks up the order, checks the courier, drafts an email, and asks a person to approve sending it.

**The rule:** use the simplest option that works.
- **Agents** are powerful, but slower, pricier and less predictable than a fixed workflow.
- **Multi-agent** systems (several agents splitting one job) are the most powerful and the most expensive of all.

{/* more:1-three-table */}
| | Single call | Workflow | Agent |
|---|---|---|---|
| **Who decides the steps** | There are no steps | Your code | Claude, as it goes |
| **Uses tools?** | No | Your code calls them | Claude asks for them |
| **Predictable?** | Very | Yes: same path every run | Less: the path can change |
| **Cost and speed** | Cheapest, fastest | Low | Highest, slowest |
| **Acme example** | "Summarise this complaint" | Fetch order → check courier → write apology | "Find out why order 1234 is late and sort it out" |
| **Choose it when** | One answer from text you already have | You can write the steps down in advance | You know the goal but not the path |
{/* /more */}

{/* more:1-three */}
**The same job three ways, in code.** The task: deal with the complaint about late order 1234.

## 1.2 The five workflow patterns

<ExamRef section="1.2" />
<Imagine text={"Acme wants every new support ticket handled automatically. Some steps never change (summarise it, then translate it for the overseas team); others depend on the ticket (billing or technical?). Before building an agent, check whether one of five standard shapes already fits."} />

### The five patterns at a glance

Anthropic describes five standard ways to arrange Claude calls into a **workflow**. They're called **patterns** because, like design patterns in Java, they're reusable shapes you'll recognise again and again. In all five, *your code* decides the order of the steps.

{/* more:1-patterns-table */}
These are **five separate patterns**, not variations of one. Each answers a different question:

| Pattern | The question it answers | Acme example |
|---|---|---|
| **Prompt chaining** | "The job has fixed steps, in order" | Write a description → check its length → translate it |
| **Routing** | "Different requests need different handling" | Billing or technical? Send each ticket to the right handler |
| **Parallelisation** | "Several independent pieces can run at once" | Security, performance and style reviews at the same time |
| **Orchestrator-workers** | "A big job must be split, but I can't know the pieces in advance" | Research competitor prices in 12 countries |
| **Evaluator-optimizer** | "Quality matters, and a second pass improves it" | Translate the T&Cs, check them, fix them, check again |

Patterns can be combined: a router might send legal documents down an evaluator-optimizer path, and simple FAQs to a single call.
{/* /more */}

### Prompt chaining

**Prompt chaining** is the simplest: a fixed sequence of calls, each using the previous output, with optional code checks ("gates") between steps. Example: write marketing copy, check it meets length and tone rules, then translate it. Use it when a task splits cleanly into steps and accuracy matters more than **latency** (how long the user waits).

{/* more:1-chain */}
<CodeSwitch title="Prompt chaining with a gate" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.stream.Collectors
String product = "a noise-cancelling headset for call-centre staff";
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
String ask(String prompt) {                // one Claude call that returns the reply text
    Message msg = client.messages().create(MessageCreateParams.builder()
        .model(Model.CLAUDE_SONNET_5_5).maxTokens(1024L).addUserMessage(prompt).build());
    return msg.content().stream().flatMap(b -> b.text().stream())
        .map(TextBlock::text).collect(Collectors.joining());
}
// ── The example ──
String draft = ask("Write a 50-word product description for: " + product);   // step 1
if (draft.split("\\s+").length > 60) {                                        // gate: plain code check
    draft = ask("Shorten this to under 50 words:\n" + draft);                   // fix before moving on
}
String french = ask("Translate into French, keeping the tone:\n" + draft);     // step 2 uses step 1's output
// ask(...) = one messages().create call that returns the text
```

### Routing

<Imagine text={"Billing questions need the account tools; technical ones need the line-test tools. Giving every ticket every tool makes Claude slower and more likely to pick the wrong one."} />

**Routing** means sorting each request into a category first, then sending it to the handler built for that category. Think of a phone menu: "press 1 for billing, 2 for technical support".

- **How:** one quick Claude call classifies the input; your code sends it to the matching prompt, tools or model.
- **Example:** refunds, technical questions and general queries each go to their own handler.
- **Also for cost:** easy questions go to Haiku, hard ones to a bigger model.

{/* code:1.2 */}
**In code:** routing is just a cheap classification call, then a normal `switch` in your own code.

<CodeSwitch title="Routing: classify with Haiku, then hand off" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
String ticket = "I was charged twice for my March bill.";   // an example input
// billingHandler, techHandler: your handlers, each with its own prompt, tools and model
// humanQueue: passes the ticket to a person
// ── The example ──
// Step 1: a cheap, fast call decides the category
Message route = client.messages().create(MessageCreateParams.builder()
    .model(Model.CLAUDE_HAIKU_5_5).maxTokens(10L)
    .system("Classify the ticket. Reply with exactly one word: BILLING, TECHNICAL or OTHER.")
    .addUserMessage(ticket)
    .build());
String category = route.content().stream()
    .flatMap(b -> b.text().stream()).map(TextBlock::text)
    .findFirst().orElse("OTHER").trim();

// Step 2: YOUR code routes it: a fixed, testable decision
String answer = switch (category) {
    case "BILLING"   -> billingHandler.reply(ticket);     // e.g. its own prompt + refund tools
    case "TECHNICAL" -> techHandler.reply(ticket);        // e.g. Sonnet with the docs search tool
    default          -> humanQueue.add(ticket);
};
```

### Parallelisation

<Imagine text={"A code change needs a security review, a performance review and a style review. Doing them one after another takes three times as long as necessary."} />

**Parallelisation** means running several Claude calls at the same time and combining the results. There are two kinds:

- **Sectioning** - split the job into independent parts that run at once · e.g. one call answers the customer while another checks the message for policy problems
- **Voting** - run the same task several times and combine the answers · e.g. ask three times whether some code has a security hole, and flag it if at least two say yes

{/* more:1-parallel */}
<CodeSwitch title="Parallelisation: three calls at once" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.nio.file.*, java.util.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
String code = Files.readString(Path.of("payment_service.py"));   // the code to review
// textOf: a small helper that joins the text blocks of a reply into one string
// ── The example ──
AnthropicClientAsync async = client.async();                  // non-blocking client
List<CompletableFuture<Message>> calls = List.of(
    async.messages().create(review("security", code)),
    async.messages().create(review("performance", code)),
    async.messages().create(review("readability", code)));
CompletableFuture.allOf(calls.toArray(new CompletableFuture[0])).join();   // wait for all three
List<String> reviews = calls.stream().map(f -> textOf(f.join())).toList();
```

```python
# ── Setup: where the names below come from ──
import anthropic
from pathlib import Path
code = Path("payment_service.py").read_text()   # the code to review
# ── The example ──
import asyncio
aclient = anthropic.AsyncAnthropic()                          # non-blocking client

async def review(aspect: str) -> str:
    msg = await aclient.messages.create(model="claude-sonnet-5-5", max_tokens=800,
        messages=[{"role": "user", "content": f"Review this code for {aspect} only:\n{code}"}])
    return "".join(b.text for b in msg.content if b.type == "text")

async def main():
    return await asyncio.gather(review("security"), review("performance"), review("readability"))

reviews = asyncio.run(main())                                 # all three run at the same time
```

### Orchestrator-workers

<Imagine text={"\"Research every competitor's broadband prices in 12 countries.\" Nobody knows in advance how to split that job up."} />

One lead call, the **orchestrator**, decides the subtasks **at run time**, hands each one to a separate call (a **worker**), and merges the results. It looks like parallelisation, except the subtasks aren't fixed in advance.

- **Cost:** Anthropic reports multi-agent research runs using roughly **15× the tokens** of a single chat.
- **Use it for:** broad work that splits into independent parts, such as researching several topics.
- **Avoid it for:** work where every part depends on the others, such as changing one module of code. A single agent that sees everything does better.

### Evaluator-optimizer

<Imagine text={"Acme's terms and conditions must be translated with legal precision. First drafts are close, but not quite right."} />

One call generates an answer (the **optimizer**), another checks it against clear criteria (the **evaluator**), and the loop repeats until the check passes. Use it when you can state what "good" looks like and iteration measurably improves the result, such as literary translation or a search that needs several rounds.

{/* more:1-evalopt */}
<CodeSwitch title="Evaluator-optimizer: write, check, repeat" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.stream.Collectors
String text = "Thank you for your order. It will arrive on Monday.";   // the text to translate
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
String ask(String prompt) {                // one Claude call that returns the reply text
    Message msg = client.messages().create(MessageCreateParams.builder()
        .model(Model.CLAUDE_SONNET_5_5).maxTokens(1024L).addUserMessage(prompt).build());
    return msg.content().stream().flatMap(b -> b.text().stream())
        .map(TextBlock::text).collect(Collectors.joining());
}
// ── The example ──
String draft = ask("Translate into formal German:\n" + text);
for (int round = 0; round < 3; round++) {                         // always cap the rounds
    String verdict = ask("Check this translation against the original. Reply PASS, or list the problems.\n"
                       + "<original>" + text + "</original><translation>" + draft + "</translation>");
    if (verdict.startsWith("PASS")) break;
    draft = ask("Improve the translation to fix these problems:\n" + verdict + "\n\n" + draft);
}
```

## 1.3 The agent loop

<ExamRef section="1.3" />
<Imagine text={"A customer writes \"my broadband keeps dropping\". Nobody can say in advance which checks are needed: the line status? recent outages? the router logs? You give Claude those three lookups and let it decide, one step at a time, until it can explain the problem."} />

### The loop

The **agent loop** is the code that makes an agent work. Four words first:

| Word | Meaning |
|---|---|
| **Tool** | A function in **your** code that Claude can ask you to run, such as "look up an order" |
| `stop_reason` | A field on every reply from Claude saying **why it stopped**: `end_turn` means it has finished; `tool_use` means it wants a tool run |
| `tool_use` | The part of the reply where Claude asks for a tool: which one, and with what input |
| `tool_result` | What your code sends back after running the tool |

The loop is then simple:

1. Call Claude with the conversation so far and the list of tools.
2. If `stop_reason` is `tool_use`, run the tool, add the `tool_result` to the conversation, and go back to step 1.
3. If it's `end_turn`, the job is done: show the answer.

**This code is called the harness.** The **harness** is the loop, plus everything around it that keeps the agent working and safe:

**Agent = Claude (the brain) + the harness (the loop and the rules) + tools (the hands).**

The harness's main jobs, and where each is taught:

- **Run the loop:** call Claude, check `stop_reason`, repeat (this section).
- **Run the tools:** call your function for each `tool_use` and send back the `tool_result` (8.1).
- **Manage the context:** keep the history, and trim or summarise it as it grows (6.5).
- **Enforce the rules:** turn limits, budgets, approvals, permission checks (exit conditions, below, and 7.2), plus retries and logging.

Each call to the Messages API is just one step inside the harness: the "call Claude" step, repeated every turn. **The Batch API can't run an agent:** the loop needs each reply straight away to decide the next step, and batch results can take hours.

**What's here and what's in 8.1:** a single tool round trip (what the `tool_use` and `tool_result` blocks look like, matching IDs, reporting tool errors) is explained in **8.1**. This section is about the **loop around it**: repeating the round trip, and deciding when to stop.

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
final int MAX_TURNS = 10;   // hard cap on loop iterations
// runToolSafely: your code that runs the named tool and catches errors; returns the result text and whether it failed
// ToolOutcome: your own small data classes
// orderTool: step 1's tool description (8.1)
// ── The example ──
List<MessageParam> history = new ArrayList<>();
history.add(MessageParam.builder().role(MessageParam.Role.USER)
    .content("Where's order A-1234, and can you change the delivery address?").build());

for (int turn = 0; turn < MAX_TURNS; turn++) {   // ← new: repeat, at most MAX_TURNS times
    Message reply = client.messages().create(MessageCreateParams.builder()
        .model(Model.CLAUDE_SONNET_5_5).maxTokens(2048L)
        .system("You are an order-status agent. Use only the tools given.")
        .addTool(orderTool)
        .messages(history).build());

    history.add(reply.toParam());                          // keep the tool_use blocks intact
    if (!reply.stopReason().map(StopReason.TOOL_USE::equals).orElse(false)) break;   // ← new: finished

    List<ContentBlockParam> results = new ArrayList<>();
    for (ContentBlock block : reply.content()) {   // ← new: Claude may ask for several tools at once
        block.toolUse().ifPresent(use -> {
            ToolOutcome r = runToolSafely(use);            // YOUR code runs the tool
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id())                       // must match the tool_use id
                .content(r.text())
                .isError(r.failed())                       // never hide errors as empty data
                .build()));
        });
    }
    history.add(MessageParam.builder().role(MessageParam.Role.USER)
        .contentOfBlockParams(results).build());
}
```

### Exit conditions and human gates

<Imagine text={"The agent decides a customer deserves a £300 refund. Should it just go ahead? And what stops it if it never decides it's finished?"} />

An **exit condition** is a rule that stops the loop. Every agent needs them, usually three: the goal is reached, a maximum number of turns, and a token or cost budget. A **human gate** is a point where a person must approve before the agent continues. Place one where the worst case is expensive.

{/* more:1-exit */}
<CodeSwitch title="Exit conditions in the loop" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
List<MessageParam> history = new ArrayList<>();   // the conversation so far (user/assistant turns)
// paramsFor: builds the request (model, system prompt, tools, messages) from the history
// runToolsAndAppend: runs the tools Claude asked for and appends the results to history
// escalate: alerts a person and records why the agent stopped
// wantsRefundOver: checks whether Claude is asking to refund more than the limit
// awaitHumanApproval: pauses until a person approves or rejects the action
// ── The example ──
long tokensUsed = 0;
for (int turn = 0; turn < 15; turn++) {                              // 1. maximum turns
    Message reply = client.messages().create(paramsFor(history));
    tokensUsed += reply.usage().inputTokens() + reply.usage().outputTokens();
    if (tokensUsed > 200_000) { escalate("Budget exceeded"); break; }   // 2. token budget
    if (!reply.stopReason().equals(Optional.of(StopReason.TOOL_USE))) break; // 3. goal reached: no more tools
    if (wantsRefundOver(reply, 50)) { awaitHumanApproval(reply); }      // human gate before a costly action
    runToolsAndAppend(reply, history);
}
```

### How many tools to give an agent

<Imagine text={"The agent has 35 tools, several doing nearly the same thing, and it keeps picking the wrong one."} />

How well an agent picks the right tool depends on how the tools are described and how many you give it. Give it too many similar tools and it picks the wrong one; give it too few and it improvises, or stops with a half-finished result. Start with the minimum set and add a tool only for a specific gap.

## 1.4 Three ways to wire an agent

### Who provides the harness: you, a library, Claude Code or Anthropic?

There are four ways to get the harness from 1.3 (the loop and everything around it): write it yourself, use a library, use a finished one, or let Anthropic run it.

| | Raw Messages API | Agent SDK | Claude Code | Claude Managed Agents |
|---|---|---|---|---|
| **Who provides the harness** | You write it | A library, running inside your program | A finished harness for coding work | Anthropic, on its servers, in a **sandbox** (an isolated environment where the agent's actions can't touch anything else) |
| **What you own** | Everything | Tool execution and the app around it | Your project, CLAUDE.md, settings and hooks (Domain 3) | The app layer and the agent definition |
| **Choose when** | You need full control, or have constraints a library can't meet | You want a ready loop, context handling and tools in your own environment (Python or TypeScript; no Java version) | A developer working in a codebase, interactively or in CI | You want long-running execution and a managed sandbox |
| **Watch out** | You maintain all of it | Set `settingSources` explicitly: whether CLAUDE.md and skills load by default has changed between SDK versions | It's built for coding; for your own product, use the Agent SDK (the same engine) | Public beta; sessions stored server-side, so **not** eligible for Zero Data Retention (Anthropic keeping none of your data) or HIPAA (the US health-data law) |

Whichever you choose, you still do the same four things: decide which tools the agent gets, write its system prompt, run the loop (or let something run it for you), and set exit conditions.

Other agent **frameworks** can also run Claude. They're libraries that provide the loop, state and tool plumbing, and they work with several model providers:

| Framework | In one line | Consider it when |
|---|---|---|
| **LangGraph** | Agents as a graph of steps with saved state | You want explicit, inspectable control flow and checkpoints |
| **Strands Agents** | AWS's open-source, model-driven agent SDK | You're building on AWS (for example with Bedrock) |
| **PydanticAI** | Type-safe Python agents built around Pydantic models | You want validated, typed inputs and outputs in Python |
| **Claude Agent SDK** | Anthropic's own: the engine behind Claude Code | You want Claude Code's tools, permissions, hooks and context handling |

**Graph frameworks** such as LangGraph describe the flow as a diagram you can read in code. Three words come up a lot:

| Term | Plain English | In a ticket pipeline |
|---|---|---|
| **Node** | One step in the flow | "Classify the ticket" |
| **Conditional edge** | A rule in code that picks the next step | "If it's a refund, go to the refund handler" |
| **Interrupt** | A planned pause until something outside the flow happens | Stop and wait for a person to approve the refund |

Because the route and the pauses live in code, the flow is the same every time and easy to audit. A plain loop can do the same job if you write the branching and the approval gate in code yourself. What matters is that the control flow is in code, not left to the model's judgment.

Whichever you pick, the point is the same: a framework doesn't remove the fundamentals. You still choose the tools, write the system prompt, set exit conditions, and enforce the hard rules in code.

## 1.5 Memory and long-horizon work

<ExamRef section="1.5" />
<Imagine text={"Acme's migration agent is moving 40 database tables to a new system. It takes all afternoon, and halfway through, the session ends. Tomorrow, how does it know which tables are already done?"} />

### Memory scopes

**Long-horizon** work means tasks that run for hours or across many separate conversations (**sessions**). Because the API remembers nothing between calls, an agent only "remembers" what you choose to give it. Its **memory scope** is that choice: decide at design time what the agent should know when a new session starts.

| Scope | What persists | Cost | Use when | You lose |
|---|---|---|---|---|
| In-context | The conversation, within one session | Grows with every turn | Short sessions that fit the window | Everything at session end |
| External storage | State in a database, read at start or on demand | Retrieval latency + code | State must survive sessions or be shared | Nothing (beyond latency) |
| Summarised | A short summary, added to the start of the next session | Cheaper than replaying history | Long-running conversational agents | Any detail the summary dropped |
| Stateless | Nothing | None | Independent task runs and pipelines | All prior context |

{/* more:1-memory */}

### Subagents for long tasks

<Imagine text={"To find a bug, the agent must read 50 log files. If they all land in the main conversation, there's no room left to work on the fix."} />

A **subagent** is a second agent that the main agent starts for one sub-task. It gets that task, the minimum context it needs, the tools for that task and clear exit conditions. It works in its own context window and returns only a summary, which keeps the parent's context small. The trade-off: you see only its summary, not how it got there.
