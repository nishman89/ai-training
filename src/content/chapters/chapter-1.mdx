## 1.1 The Messages API

### In plain English

This domain is how your program talks to Claude. You send one HTTP request, a package of settings plus the conversation so far, and get back a message, a note on why it stopped and an itemised bill. Everything else in the exam is a field on that request, a way to handle the reply, or a pattern for sending many requests in a row.

**Real-life example:** a bank's help chat. Behind it, the bank's Java service sends each customer question to Claude and shows the answer. When 10,000 customers ask at once, some calls get a "slow down" error (429), and the service should wait and retry instead of crashing. That's Domain 1.

### Anatomy of a request

A request to `POST /v1/messages` needs three fields and two headers. Everything else is optional.

| Part | What it is | Required? |
|---|---|---|
| `x-api-key` header | Your secret key; proves who you are and who pays | Yes |
| `anthropic-version` header | API version, `2023-06-01`; beta features add `anthropic-beta` | Yes |
| `model` | Which Claude does the work, e.g. `claude-sonnet-5-5` | Yes |
| `max_tokens` | Ceiling on the reply length, in tokens | Yes |
| `messages` | The conversation: alternating `user` and `assistant` turns | Yes |
| `system` | Standing instructions for the whole conversation (a top-level field, **not** a role) | No |
| `tools`, `tool_choice` | Functions Claude may ask you to run (Domain 5) | No |
| `stream` | Receive the reply as server-sent events | No |

The API is **stateless**: it keeps no conversation. Your app stores the history and resends it every turn, which is why long chats get slower and pricier.

<CodeSwitch>

```java
AnthropicClient client = AnthropicOkHttpClient.builder()
    .fromEnv()          // reads ANTHROPIC_API_KEY - never hard-code it
    .maxRetries(4)      // default is 2
    .build();           // create ONE client per app: it owns the connection pool

Message msg = client.messages().create(MessageCreateParams.builder()
    .model(Model.CLAUDE_SONNET_5_5)
    .maxTokens(1024L)
    .system("You are a concise support assistant.")
    .addUserMessage("Summarise this ticket: ...")
    .build());
```

```python
import anthropic

client = anthropic.Anthropic(max_retries=4)   # reads ANTHROPIC_API_KEY; default retries is 2
                                               # create ONE client per app and reuse it
msg = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system="You are a concise support assistant.",
    messages=[{"role": "user", "content": "Summarise this ticket: ..."}],
)
```

</CodeSwitch>

### The response: content, stop_reason, usage

| Field | Meaning | Real-life comparison |
|---|---|---|
| `content` | A list of blocks: `text`, `tool_use`, `thinking` | The work delivered |
| `stop_reason` | Why it stopped (below) | The contractor's note: "done", "ran out of hours", "need you to fetch something" |
| `usage` | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` | The itemised invoice |

| `stop_reason` | Means | Your code should… |
|---|---|---|
| `end_turn` | Claude finished naturally | Use the answer |
| `max_tokens` | Hit your `max_tokens` cap; the reply is cut off | Raise the cap, ask for less, or continue |
| `stop_sequence` | Wrote one of your stop strings | Use the text before it |
| `tool_use` | Wants you to run a tool | Run it, send back a `tool_result` (Domain 5) |
| `pause_turn` | A server-tool loop paused | Resend the conversation as it is |
| `refusal` | Declined for safety reasons | Surface it, log it; don't retry blindly |

A 200 OK does **not** mean a complete answer. Branch on `stop_reason` every time, like checking an exit code.

<CodeSwitch>

```java
msg.content().forEach(b -> b.text().ifPresent(t -> System.out.println(t.text())));

if (msg.stopReason().map(StopReason.MAX_TOKENS::equals).orElse(false)) {
    // truncated: never parse this as complete JSON
}
System.out.printf("in=%d out=%d%n", msg.usage().inputTokens(), msg.usage().outputTokens());
```

```python
for block in msg.content:
    if block.type == "text":
        print(block.text)

if msg.stop_reason == "max_tokens":
    ...  # truncated: never parse this as complete JSON
print(f"in={msg.usage.input_tokens} out={msg.usage.output_tokens}")
```

</CodeSwitch>

## 1.2 Request parameters, explained

### Think of a call as a job for a contractor

You pick the contractor (`model`), hand over the standing brief (`system`) and the case file so far (`messages`), and cap the billable hours (`max_tokens`). You get back the work (`content`), a note on why they stopped (`stop_reason`) and an invoice (`usage`).

### Tokens

A token is the unit Claude reads, writes and bills in: a chunk of text of roughly ¾ of an English word. Think of a taxi meter that ticks per chunk of road. Your prompt, the whole history, tool definitions, tool results and images all tick the **input** meter. Everything Claude writes ticks the **output** meter, which costs 5× more per token on every current model.

### model

Which Claude does the work. Think of choosing junior, mid or senior staff: seniors are better, slower and pricier.

- **Haiku** - tagging 1M support tickets overnight
- **Sonnet** - a customer-facing chatbot
- **Opus** - a multi-hour coding agent
- **Fable** - the hardest reasoning, when Opus still falls short on your evals

<CodeSwitch>

```java
.model(Model.CLAUDE_SONNET_5_5)      // or .model("claude-sonnet-5-5"); pin the full ID in production
```

```python
model="claude-sonnet-5-5"      # pin the full ID in production
```

</CodeSwitch>

### max_tokens

A hard ceiling on how many tokens Claude may **write** in this reply. It isn't a target, it doesn't limit the input, and you only pay for what's actually written. Think of a word limit on an essay.

If Claude reaches the limit mid-sentence, the reply is simply cut off and `stop_reason` is `max_tokens`. There's **no error**: just truncated text or broken JSON. Size it to the longest good answer: about 300 tokens for a label plus a reason, 1,024–4,096 for chat, and much more (with streaming) for long documents or code.

### messages and system

Think of it as the employee handbook versus today's case file. Because the API remembers nothing, it's like phoning a call-centre agent who has no notes: you read out the whole file each time.

### stop_sequences, temperature and effort

- **stop_sequences** - strings that end the reply as soon as Claude writes them; stop_reason becomes stop_sequence · e.g. stop at a closing answer tag so no commentary follows
- **temperature / top_p** - randomness knobs, low = predictable · on the newest models you can't set them: steer with the prompt and test properties, not exact wording
- **effort** - how hard the model thinks before answering · current models think adaptively: low for routing an email, high for a tricky bug · more thinking = more output tokens, cost and latency

### Worked cost example

Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens. A support-bot call with a 3,000-token system prompt, 1,500 tokens of history and a 400-token answer:

| Item | Tokens | Rate | Cost |
|---|---|---|---|
| Input | 4,500 | $2 / 1M | $0.0090 |
| Output | 400 | $10 / 1M | $0.0040 |
| **Per call** | | | **$0.0130** |
| **100,000 calls a day** | | | **≈ $1,300 a day** |

Caching the 3,000-token system prompt (cache reads cost 0.05× base on Sonnet 5.5) cuts that slice from $0.006 to $0.0003 per call, saving about $570 a day. Domain 2 covers how.

<Exercise title="What went wrong?" id="exercise-max-tokens">

A nightly job asks Claude to return 200 product descriptions as one JSON array, with `max_tokens` set to 1,024. Your JSON parser throws on about half the runs, but there are no API errors. What's happening, and what are two fixes?

<div slot="answer">

The reply is longer than 1,024 tokens, so it's **cut off** (`stop_reason: max_tokens`) and the JSON is incomplete. The API returned 200 OK because truncation isn't an error.

Fixes: check `stop_reason` before parsing; raise `max_tokens` or, better, **split the work** (fewer items per call, or the Batch API with one item per request).

</div>
</Exercise>

## 1.3 Streaming

### When to stream

Streaming sends the reply as it's written, like watching a live broadcast instead of waiting for the recording. Use it for chat UIs and long outputs. Skip it for short backend jobs where nobody is watching: it adds code (you assemble the message yourself) without benefit.

### The event sequence

<Flow caption="Server-sent events for one streamed message" steps={[
  { title: 'message_start', sub: 'empty shell' },
  { title: 'content_block_start', sub: 'block type + index' },
  { title: 'content_block_delta', sub: 'append fragment' },
  { title: 'content_block_stop', sub: 'block complete' },
  { title: 'message_delta', sub: 'stop_reason, usage' },
  { title: 'message_stop', sub: 'message is whole' },
]} />

A `tool_use` block's input arrives as JSON fragments, so it isn't valid JSON until its `content_block_stop`. **Never act on a partial block.**

### Interrupted streams

A stream *ending* isn't the same as a message *completing*. Only `message_stop` means the message is whole. If your handler saves a turn whenever its read loop exits, a dropped connection writes a half-built block into history, and the failure shows up on the **next** request.

<WhenThen whenLabel="When the stream…" thenLabel="…do this" rows={[
  { when: 'reaches message_stop', then: 'Append the assembled message to history, then check stop_reason' },
  { when: 'drops (network, timeout, client disconnect)', then: 'Discard the partial turn and retry from the last complete turn' },
  { when: 'a retry then fails with a tool-use error', then: 'Check whether the previous turn was built from an interrupted stream before touching the schema' },
]} />

<CodeSwitch>

```java
MessageAccumulator acc = MessageAccumulator.create();
try (StreamResponse<RawMessageStreamEvent> stream = client.messages().createStreaming(params)) {
    stream.stream()
        .peek(acc::accumulate)                              // rebuilds the full Message
        .flatMap(e -> e.contentBlockDelta().stream())
        .flatMap(d -> d.delta().text().stream())
        .forEach(t -> System.out.print(t.text()));         // show text as it arrives
}
Message complete = acc.message();   // only reached if the stream ended cleanly
history.add(complete.toParam());    // commit to history AFTER completion
```

```python
with client.messages.stream(model="claude-sonnet-5-5", max_tokens=1024, messages=history) as stream:
    for text in stream.text_stream:          # show text as it arrives
        print(text, end="", flush=True)
    complete = stream.get_final_message()     # only reached if the stream ended cleanly

history.append({"role": "assistant", "content": complete.content})   # commit AFTER completion
```

</CodeSwitch>

In Java, `MessageAccumulator` rebuilds the full message and mid-stream failures throw `SseException`; in Python, `stream.get_final_message()` does the same job.

## 1.4 Errors, retries and rate limits

### Retriable or terminal?

Ask one question of every failure: could waiting and sending the **same** request succeed?

| Status | `error.type` | Meaning | Retry? |
|---|---|---|---|
| 400 | `invalid_request_error` | Bad request shape (or a spend limit you set) | **No**: fix the request |
| 401 / 403 | authentication / permission | Bad key or no access | **No** |
| 404 / 413 | not_found / request_too_large | Wrong model or path; payload too big | **No** |
| 429 | `rate_limit_error` | Your org hit a rate or spend limit | **Yes**, after `retry-after`. A spend-cap 429 has no `retry-after` and won't clear by waiting |
| 500 / 504 | `api_error` / `timeout_error` | Server-side fault | **Yes**, bounded backoff |
| 529 | `overloaded_error` | Anthropic-wide capacity, not your quota | **Yes**, backoff with jitter |
| 200 + `refusal` | (not an error) | A content decision by the model | **No**: surface and log it |

<VsPair
  left={{ title: '429 rate_limit_error', meaning: 'YOU are sending too much: your organisation hit RPM, ITPM or OTPM.', example: 'Fix: honour retry-after, reduce concurrency, ask for a higher tier.' }}
  right={{ title: '529 overloaded_error', meaning: 'ANTHROPIC is busy across the board, whatever your rate.', example: 'Fix: backoff with jitter, fail over or degrade gracefully if it persists.' }}
/>

### Rate limits

Limits are set **per organisation, per model**, as requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM). They use a token-bucket model and rise with your usage tier. Cached input reads typically don't count against ITPM on current models, so caching raises throughput as well as cutting cost.

### What the SDK already does

The official SDKs retry connection errors, 408, 409, 429 and 5xx automatically, **twice by default**, with exponential backoff, honouring `retry-after`. Don't wrap your own retry loop around that: it multiplies attempts. Tune `maxRetries`, then handle what's left.

<CodeSwitch>

```java
try {
    Message msg = client.messages().create(params);
} catch (RateLimitException e) {          // 429, after the SDK's retries ran out
    // queue the work, or fall back to a cached or simpler answer
} catch (BadRequestException e) {         // 400: terminal, fix the request
    throw e;
} catch (InternalServerException e) {     // 5xx after retries
    // degrade gracefully, alert
} catch (AnthropicServiceException e) {   // any other HTTP status: e.statusCode()
    log.error("Claude call failed", e);
} catch (AnthropicIoException e) {        // network problem
    // retry later
}
```

```python
try:
    msg = client.messages.create(**params)
except anthropic.RateLimitError:          # 429, after the SDK's retries ran out
    ...  # queue the work, or fall back to a cached or simpler answer
except anthropic.BadRequestError:         # 400: terminal, fix the request
    raise
except anthropic.InternalServerError:     # 5xx after retries
    ...  # degrade gracefully, alert
except anthropic.APIStatusError as e:     # any other HTTP status: e.status_code
    log.exception("Claude call failed")
except anthropic.APIConnectionError:      # network problem
    ...  # retry later
```

</CodeSwitch>

Python raises `anthropic.BadRequestError`, `RateLimitError`, `InternalServerError` and so on. Java exception map: 400 `BadRequestException` · 401 `UnauthorizedException` · 403 `PermissionDeniedException` · 404 `NotFoundException` · 422 `UnprocessableEntityException` · 429 `RateLimitException` · 5xx `InternalServerException`. Log the `request-id` response header for support (Java: `withRawResponse()...requestId()`; Python: `msg._request_id`).

## 1.5 The lifecycle and deployment

### Seven lifecycle phases

A Claude application moves through the same lifecycle as any engineered system. Your Accelerators notes frame each phase with a gate.

- **Functional requirements** - what the system must do, with enough detail to check · these become your eval cases
- **Infrastructure requirements** - latency, scale, data residency, identity, audit · some of these decide the platform, so capture them first
- **Gates** - don't build until the platform meets residency · don't release until the new version clears the eval

### Choosing a platform

The customer's existing cloud, identity and compliance agreements usually decide the platform.

| Platform | Identity and data | Choose when |
|---|---|---|
| Claude API (first-party) | Anthropic identity and terms; new features first | No binding cloud or residency constraint |
| Claude Platform on AWS | Through the customer's AWS account, Anthropic model IDs and lifecycle | On AWS but wants first-party parity |
| Amazon Bedrock | AWS identity; data stays in the configured AWS boundary | On AWS with a compliance posture there |
| Google Vertex AI | Google Cloud IAM; regional or global endpoints | On Google Cloud |
| Microsoft Foundry | Wrapping product's identity and billing | Customer already runs Foundry |

Compare platforms on **latency** (measured from the customer's region), **compliance** (usually pass or fail) and **total cost** (tokens plus egress, fees and integration effort), not token price alone.

### Pin what ships

Every full model ID is a fixed snapshot; an alias moves over time and may resolve differently per platform. Pin the full ID in configuration, keep the previous version available for rollback, and promote a new model only after it clears your eval baseline (Domain 7). A moving alias is fine for a throwaway prototype, never for production.
