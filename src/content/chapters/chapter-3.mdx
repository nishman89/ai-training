## 3.1 Workflow or agent?

### In plain English

This domain is about getting Claude to finish jobs that take several steps. A **workflow** is a fixed recipe you write: step 1 summarise, step 2 translate. An **agent** chooses its own steps: it asks for a tool, looks at the result, decides what to do next, and repeats until the job is done.

**Real-life example:** "Find out why order 1234 is late and email the customer." The agent looks up the order, checks the courier, drafts an email and asks a human to approve sending it. The rule is to use the simplest option that works: agents are powerful, but slower, pricier and less predictable.

## 3.2 The five workflow patterns

### Prompt chaining

A fixed sequence of calls, each using the previous output, with optional code checks ("gates") between steps. Example: write marketing copy, check it meets length and tone rules, then translate it. Use it when a task splits cleanly into steps and accuracy matters more than latency.

### Routing

Classify the input, then send it to a specialised prompt, tool set or model. Example: route refund requests, technical questions and general queries to different handlers, or send easy questions to Haiku and hard ones to a bigger model.

### Parallelisation

Run calls at the same time and combine the results.

- **Sectioning** - independent subtasks at once · e.g. one call answers the user while another screens for policy issues
- **Voting** - the same task several times, then aggregate · e.g. three reviewers flag vulnerabilities, flag if any two agree

### Orchestrator-workers

A lead model decides the subtasks **at run time**, hands them to workers, and merges the results. It looks like parallelisation, but the subtasks aren't predefined. Anthropic reports multi-agent research runs using roughly **15× the tokens** of a single chat, so use it only for broad work that genuinely splits into independent parts. For tightly coupled work like coding, a single agent with good context wins.

### Evaluator-optimizer

One call generates, another critiques against clear criteria, and the loop repeats until the critique passes. Use it when you can state what "good" looks like and iteration measurably improves the result, such as literary translation or a search that needs several rounds.

## 3.3 The agent loop

### The loop

An agent is a multi-step tool-use loop with managed context and a defined goal.

### In code

This is the raw loop. In **Python** (or TypeScript) the Claude Agent SDK can run this loop for you; it isn't available for **Java**, where you write the loop yourself or use the Java SDK's beta tool runner.

<CodeSwitch>

```java
List<MessageParam> history = new ArrayList<>();
history.add(MessageParam.builder().role(MessageParam.Role.USER)
    .content("Find order 1234 and tell me its status").build());

for (int turn = 0; turn < MAX_TURNS; turn++) {             // exit condition: iteration cap
    Message reply = client.messages().create(MessageCreateParams.builder()
        .model(Model.CLAUDE_SONNET_5_5).maxTokens(2048L)
        .system("You are an order-status agent. Use only the tools given.")
        .addTool(LOOKUP_ORDER_TOOL)
        .messages(history).build());

    history.add(reply.toParam());                          // keep the tool_use blocks intact
    if (!reply.stopReason().map(StopReason.TOOL_USE::equals).orElse(false)) break;

    List<ContentBlockParam> results = new ArrayList<>();
    for (ContentBlock block : reply.content()) {
        block.toolUse().ifPresent(use -> {
            ToolOutcome r = runToolSafely(use);            // YOUR code runs the tool
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id())                       // must match the tool_use id
                .content(r.text())
                .isError(r.failed())                       // never hide errors as empty data
                .build()));
        });
    }
    history.add(MessageParam.builder().role(MessageParam.Role.USER)
        .contentOfBlockParams(results).build());
}
```

```python
history = [{"role": "user", "content": "Find order 1234 and tell me its status"}]

for turn in range(MAX_TURNS):                       # exit condition: iteration cap
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2048,
        system="You are an order-status agent. Use only the tools given.",
        tools=[LOOKUP_ORDER_TOOL],
        messages=history,
    )
    history.append({"role": "assistant", "content": reply.content})   # keep tool_use blocks intact
    if reply.stop_reason != "tool_use":
        break

    results = []
    for block in reply.content:
        if block.type == "tool_use":
            outcome = run_tool_safely(block.name, block.input)   # YOUR code runs the tool
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,                      # must match the tool_use id
                "content": outcome.text,
                "is_error": outcome.failed,                   # never hide errors as empty data
            })
    history.append({"role": "user", "content": results})
```

</CodeSwitch>

Builder method names can differ slightly between SDK versions. What the exam tests is the shape: loop on `tool_use`, append the assistant turn unchanged, return each `tool_result` with the matching ID.

### Exit conditions and human gates

Every agent needs a clear stopping rule: a goal check, a maximum number of turns and a token or cost budget. Place human approval where the worst case is expensive.

<WhenThen whenLabel="Insert a human check…" thenLabel="…because" rows={[
  { when: 'Before a destructive tool call (write, delete, send, pay)', then: 'High risk: the action can\'t be undone' },
  { when: 'After a planning step, before execution', then: 'Medium risk: a wrong plan gives a wrong outcome even if executed perfectly' },
  { when: 'On unexpected output (error flag, empty result, out-of-range value)', then: 'Catches failures that retry logic alone won\'t fix' },
]} />

### Tool orchestration

Routing depends on how tools are described and how many are registered. Too many overlapping tools make choices erratic; too few and the agent invents a path or returns an incomplete result. Start with the minimum set and add a tool only for a specific gap.

## 3.4 Three ways to wire an agent

### Who runs the loop?

| | Raw Messages API loop | Agent SDK | Claude Managed Agents |
|---|---|---|---|
| **Who runs the loop** | You | The SDK, inside your process | Anthropic, in its sandbox |
| **What you own** | Everything | Tool execution and the app around it | The app layer and the agent definition |
| **Choose when** | You need full control, or have constraints a library can't meet | You want a ready loop, context handling and tools in your own environment (Python or TypeScript; no Java version) | You want long-running execution and a managed sandbox |
| **Watch out** | You maintain all of it | Set `settingSources` explicitly, or CLAUDE.md and skills won't load | Public beta; sessions stored server-side, so **not** eligible for Zero Data Retention or HIPAA |

Whichever path you take, the four steps are the same: register tools, scope the system prompt, run the tool loop, define exit conditions.

## 3.5 Memory and long-horizon work

### Memory scopes

Choose at design time what the agent should know when a new session starts.

| Scope | What persists | Cost | Use when | You lose |
|---|---|---|---|---|
| In-context | The conversation, within one session | Grows with every turn | Short sessions that fit the window | Everything at session end |
| External storage | State in a database, read at start or on demand | Retrieval latency + code | State must survive sessions or be shared | Nothing (beyond latency) |
| Summarised | A condensed summary injected next session | Cheaper than replaying history | Long-running conversational agents | Any detail the summary dropped |
| Stateless | Nothing | None | Independent task runs and pipelines | All prior context |

### Subagents for long tasks

A subagent gets a scoped task, the minimum context it needs, the tools for that task and clear exit conditions. It works in its own context window and returns only a summary, which keeps the parent's context small. You lose visibility of how it reached its answer.
