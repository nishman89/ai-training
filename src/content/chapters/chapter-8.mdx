## 8.1 How tool use works

<ExamRef section="8.1" />







### In plain English

This domain is about letting Claude **do** things, not just talk, through **tool use** (also called function calling). You describe a function ("get_order_status takes an order ID"). Claude replies "please run get_order_status with A-1234", **your** code runs it and sends back the answer, and Claude continues. **MCP** (the **Model Context Protocol**) is an open standard for packaging tools so they plug into any Claude app, like USB for tools. A program that offers tools this way is an **MCP server**; an app that connects to it is an **MCP client**.

**Real-life example:** connect the GitHub MCP server once, and Claude can search code and open issues in any app that supports MCP.

Each one is effectively an integration requirement: what it can read or change, and under what rules."} />

### The round trip

<Flow caption="Claude never runs your tools: it asks, your code runs them (Exam guide: Tool Implementation)" steps={[
  { title: 'Send tools + question', sub: 'name, description, input_schema' },
  { title: 'stop_reason: tool_use', sub: 'tool_use block: name, id, input' },
  { title: 'Your code runs it', sub: 'Claude is not connected meanwhile' },
  { title: 'Send tool_result', sub: 'same tool_use_id' },
  { title: 'Claude continues', sub: 'answer or another tool' },
]} />

Each tool is defined by a name, a description, and an `input_schema` (a JSON schema listing its parameters and their types). A tool conversation is built from typed blocks: `text`, `tool_use`, `tool_result` and (with thinking) `thinking`. The API enforces the pairing: each `tool_use` must be answered by a `tool_result` with the matching ID in the next user turn. Most bugs sit on that boundary between what Claude owns and what your code owns.

<CodeSwitch title="One tool call, answered">

```java
// Claude asked for a tool: echo its turn, then answer every tool_use with a tool_result
history.add(reply.toParam());
List<ContentBlockParam> results = new ArrayList<>();
for (ContentBlock block : reply.content()) {
    block.toolUse().ifPresent(use -> {
        try {
            String out = orders.status(use.input().toString());
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id()).content(out).build()));
        } catch (Exception e) {
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id())
                .content("Order service unavailable: " + e.getMessage())
                .isError(true)                          // tell Claude it failed
                .build()));
        }
    });
}
history.add(MessageParam.builder().role(MessageParam.Role.USER).contentOfBlockParams(results).build());
```

```python
    try:

        results.append({
            "type": "tool_result", "tool_use_id": block.id,
            "content": f"Order service unavailable: {e}",

        })

```

**The scenario:** the customer asks "Where's order A-1234?". Your app has registered one tool, `get_order_status`. These are the real messages, in order.

#### Request 1: your app sends the question and the tool definition

```json
{
  "model": "claude-sonnet-5-5", "max_tokens": 1024,
  "tools": [{
    "name": "get_order_status",
    "description": "Look up the delivery status of an order by ID. Do not use for refunds.",
    "input_schema": { "type": "object",
                      "properties": { "order_id": { "type": "string" } },
                      "required": ["order_id"] }
  }],
  "messages": [{ "role": "user", "content": "Where's order A-1234?" }]
}
```

#### Response 1: Claude asks you to run the tool

```json
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me check that for you." },
    { "type": "tool_use", "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_order_status", "input": { "order_id": "A-1234" } }
  ]
}
```

Claude has **not** looked anything up. It has asked your code to.

#### Your code runs it

Your code calls your own order database or API (`orderService.status("A-1234")`), gets `{"status":"out for delivery","eta":"today 14:00–16:00"}`, and sends request 2.

#### Request 2: the whole conversation again, plus the result

```json
"messages": [
  { "role": "user", "content": "Where's order A-1234?" },
  { "role": "assistant", "content": [ …the text + tool_use blocks from response 1, unchanged… ] },
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
        "content": "{\"status\":\"out for delivery\",\"eta\":\"today 14:00-16:00\"}" } ] }
]
```

#### Response 2: the final answer

```json
{ "stop_reason": "end_turn",
  "content": [{ "type": "text", "text": "Good news: A-1234 is out for delivery and should arrive today between 2 and 4pm." }] }
```

Two HTTP calls, one tool run by **your** code, and the IDs tie them together.

## 8.2 Designing tools Claude picks correctly

<ExamRef section="8.2" />
<Imagine text={"Claude keeps calling the refund tool when customers ask where their order is. Both tools have one-line descriptions, so Claude is guessing."} />







### Claude picks tools by their description

Claude picks a tool by reasoning over every registered description in the context of the conversation. When two descriptions look alike, it has no reliable signal and picks on surface details.

- **Say when NOT to use it** - one sentence of exclusion gives a decision boundary · "Look up an order's status. Do not use for refunds."
- **Merge what you can't separate** - two overlapping tools → one tool with a type parameter
- **Use the schema** - an enum (a fixed list of allowed values) for fixed values, required only for truly required fields, clear parameter descriptions
- **Don't over-tool** - every definition costs tokens on every call, and overlap makes selection erratic · start minimal

{/* more:8-describe */}
**Example:** two definitions of the same tool. Claude reads only the name, description and schema, so the second one gets picked correctly far more often.

<CodeSwitch title="A tool description that says when, and when not">

```java
// Weak: Tool.builder().name("orders").description("Order tool.")...
Tool getOrderStatus = Tool.builder()
    .name("get_order_status")
    .description("Look up the delivery status of ONE existing order by its ID (format A-1234). "
               + "Use when the customer asks where an order is. Do NOT use for refunds or cancellations.")
    .inputSchema(Tool.InputSchema.builder()
        .properties(JsonValue.from(Map.of(
            "order_id", Map.of("type", "string", "description", "Order ID, e.g. A-1234"),
            "detail",   Map.of("type", "string", "enum", List.of("summary", "full")))))
        .required(List.of("order_id"))
        .build())
    .build();
```

```python
# Weak: {"name": "orders", "description": "Order tool.", ...}

    "name": "get_order_status",
    "description": ("Look up the delivery status of ONE existing order by its ID (format A-1234). "
                    "Use when the customer asks where an order is. Do NOT use for refunds or cancellations."),
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "Order ID, e.g. A-1234"},
            "detail": {"type": "string", "enum": ["summary", "full"]},   # a fixed list of allowed values
        },
        "required": ["order_id"],
    },
}
```

### Errors go back to Claude

<Imagine text={"The stock system times out, your tool quietly returns an empty list, and Claude tells a customer the router is out of stock. It isn't."} />


Return failures as a `tool_result` with `is_error: true` and a useful message, so the model can retry, try another approach, ask the user or stop. An empty result is read as valid data ("no orders found"), and the model carries on confidently.

<Gotcha
  title={"\"Sorry, that item is out of stock\""}
  scenario={"The inventory API times out, and the tool catches the exception and returns an empty list."}
  gotcha={"Claude reads the empty result as real data and confidently tells a customer the item is unavailable. A lost sale and a false statement."}
  fix={"Return `is_error: true` with a message (\"inventory service timed out\") so Claude can retry, apologise, or hand off."}
/>

<SectionSummary points={[
  "The description is the interface: say what the tool does AND when not to use it.",
  "Merge tools you can't separate; use enums and only truly required fields.",
  "Return failures with `is_error: true`: an empty result reads as valid data.",
  "Start with the fewest tools: each costs tokens every call and overlap makes selection erratic.",
]} />

## 8.3 Client tools, server tools and tool_choice

<ExamRef section="8.3" />
<Imagine text={"Some questions need live information Acme doesn't hold, like \"is there a national outage on other networks?\". You don't want to build and maintain a web-search tool yourself."} />







### Client tools vs server tools: where the tool runs

Tools differ in *who runs them*. Most are yours, but Anthropic also runs some tools for you on its own servers.

<VsPair
  left={{ title: 'Client tools', meaning: 'Defined by you (or tools whose definition Anthropic provides, like bash and text_editor) and run in YOUR application.', example: 'Response stops with stop_reason tool_use; you run it and send tool_result.' }}
  right={{ title: 'Server tools', meaning: 'Run on Anthropic\'s side, e.g. web search, web fetch, code execution. Declared in the request; nothing to implement.', example: 'May cost extra per use. A long server loop returns pause_turn.' }}
/>

`tool_choice` is a request setting that controls whether Claude may, must or must not call a tool.

| `tool_choice` | Meaning |
|---|---|
| `auto` (default) | Claude decides whether to call a tool |
| `any` | Must call some tool |
| `tool` + name | Must call that specific tool (forced) |
| `none` | Must not call tools |

**Model check:** Claude Opus 5.5 rejects the forcing options (`any` and `tool`) with a 400 error, so code that forced a tool breaks when you upgrade. On that model, keep `auto`, make the tool `strict`, and say in the prompt when it applies. For a guaranteed JSON shape, use structured outputs (`output_config.format`).

Claude can ask for several tools in one reply (**parallel tool use**). Add `disable_parallel_tool_use: true` to allow at most one tool call per turn. When a server-tool loop hits its iteration cap the response has `stop_reason: pause_turn`. Resend the conversation as it is; don't add a "please continue" message.

{/* more:8-parallel */}
**Example of parallel tool use:** the customer asks *"Where are orders A-1 and A-2?"*. Claude can ask for both lookups in one reply, and you answer both in **one** user message, each `tool_result` with its own matching ID:

```json
// Claude's reply
{ "role": "assistant", "content": [
  { "type": "tool_use", "id": "toolu_01", "name": "get_order_status", "input": { "order_id": "A-1" } },
  { "type": "tool_use", "id": "toolu_02", "name": "get_order_status", "input": { "order_id": "A-2" } }
]}
// Your next message: both results together
{ "role": "user", "content": [
  { "type": "tool_result", "tool_use_id": "toolu_01", "content": "Delivered yesterday" },
  { "type": "tool_result", "tool_use_id": "toolu_02", "content": "Out for delivery" }
]}
```
{/* /more */}








{/* code:8.3 */}
**In code:** a server tool is declared, not implemented. Claude runs the search on Anthropic's side and the reply comes back with `server_tool_use` and `web_search_tool_result` blocks, plus a cited answer.

## 8.4 The Model Context Protocol

<ExamRef section="8.4" />
<Imagine text={"Three Acme apps (the chatbot, the staff dashboard and Claude Code) all need to check stock levels. Writing the same integration three times, and keeping three copies in sync, is wasted effort."} />







### Why MCP

Wiring a tool straight into each app means three apps need three integrations. MCP moves the tool into a **server** that any **MCP client**, meaning any app that speaks MCP (Claude Code, Claude apps, your own app), can attach to, so you build the integration once. Think JDBC: one driver standard, many databases and clients.

{/* more:8-mcpcaps */}
**Example, for an inventory MCP server:** a **tool** `get_stock(sku)` that Claude decides to call; a **resource** `inventory://warehouses`, a read-only list of warehouses the app can attach to the conversation; and a **prompt** `restock-report`, a ready-made template a user picks from a menu (in Claude Code, prompts appear as slash commands).
{/* /more */}

<RoleLens dev={"MCP is a standard way to expose tools and data to Claude: build one MCP server, and every MCP-capable client can use it."} test={"MCP servers for Jira or your test management tool let an agent read requirements and log defects directly."} data={"An MCP server in front of the warehouse gives Claude governed, read-only access to agreed views."} ba={"With MCP, Claude can read Confluence or Jira directly, so it can draft stories from real context. ### Transports: how Claude connects to an MCP server

<Imagine text={"One MCP server is a script on a developer's laptop; another is a shared service the whole company uses. They can't connect the same way."} />


A **transport** is the channel the client and server use to exchange messages. There are two.

<VsPair
  left={{ title: 'stdio', meaning: 'The client launches the server as a local subprocess and talks over stdin/stdout. Runs on ONE machine.', example: 'A personal script, a local database tool, a dev server.' }}
  right={{ title: 'Streamable HTTP', meaning: 'The server runs remotely; clients connect to its URL over the network.', example: 'A shared team server or a hosted integration.' }}
/>

SSE (Server-Sent Events) is the older remote transport and isn't recommended for new servers. Each connected server's tool definitions cost context, so connect only the servers a task needs. Claude Code defers loading tool definitions until they're needed.

{/* code:8.4 */}
**In code:** an MCP server is a small program that registers tools. These follow the official MCP quickstart: Python's `MCPServer`, TypeScript's `@modelcontextprotocol/server`, and Spring AI for Java.

<CodeSwitch title="A minimal MCP server with one tool">

```java
// Spring AI MCP server (spring-ai-starter-mcp-server): annotate a service, register it as tools
@Service
public class InventoryService {
    @Tool(description = "Get the stock level for a product SKU")
    public String getStock(@ToolParam(description = "Product SKU, e.g. AB-123") String sku) {
        return inventoryApi.stockFor(sku);           // call your real REST service here
    }
}

@SpringBootApplication
public class InventoryMcpServer {
    public static void main(String[] args) { SpringApplication.run(InventoryMcpServer.class, args); }

    @Bean
    public ToolCallbackProvider inventoryTools(InventoryService service) {
        return MethodToolCallbackProvider.builder().toolObjects(service).build();
    }
}
```

```python
from mcp.server import MCPServer

mcp = MCPServer("inventory")

@mcp.tool()
async def get_stock(sku: str) -> str:
    """Get the stock level for a product SKU.

    Args:
        sku: Product SKU, e.g. AB-123
    """
    return await inventory_api.stock_for(sku)        # call your real REST service here

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

```typescript
import { McpServer } from '@modelcontextprotocol/server';
import { serveStdio } from '@modelcontextprotocol/server/stdio';
import { z } from 'zod';

function createServer() {
  const server = new McpServer({ name: 'inventory', version: '1.0.0' });
  server.registerTool(
    'get_stock',
    {
      description: 'Get the stock level for a product SKU',
      inputSchema: z.object({ sku: z.string().describe('Product SKU, e.g. AB-123') }),
    },
    async ({ sku }) => ({
      content: [{ type: 'text', text: await inventoryApi.stockFor(sku) }],  // call your real REST service
    }),
  );
  return server;
}

serveStdio(createServer);
```

## 8.5 MCP scope, permissions and auth

<ExamRef section="8.5" />
<Imagine text={"The team shares a Jira MCP server. Everyone should be able to read and create issues, nobody should be able to delete them, and the password must never end up in Git."} />







### MCP server scopes in Claude Code

In Claude Code, an MCP server's **scope** is where its configuration is saved, and that decides who gets the server.

| Scope | Stored in | Who gets it | Right for |
|---|---|---|---|
| Local | `~/.claude.json` under the project | Only you, in this project | A tool tied to one project |
| User | Your personal Claude settings | Only you, every project | Your own local utilities |
| Project | `.mcp.json` at the repo root (committed) | Everyone who clones the repo | Team-wide servers |
| Enterprise | Managed settings, set by an admin | Everyone in the organisation | Internal services, security tooling |

Transport and scope are separate decisions with linked consequences: a **stdio server in `.mcp.json` looks shared but isn't**, because it only runs where it's installed. A shared team server needs HTTP plus project or enterprise scope.

### Per-tool permissions

<Imagine text={"The GitHub MCP server offers 40 tools. You want Claude to open issues freely but never merge a pull request."} />


Connecting a server exposes its whole tool list. Permission rules can target one tool by name: `mcp__server__tool`. For example, allow `mcp__github__create_issue` without a prompt while other GitHub tools still prompt, or deny a write tool while read tools stay available. **A deny on one tool beats an allow on the server.** Through the API's **MCP connector** (remote servers called straight from the Messages API), an `mcp_toolset` can enable or disable each tool: a permission rule decides "can it run", enabling decides "can the model see it".

{/* more:8-pertool */}
```json
// .claude/settings.json: tool names follow mcp__<server>__<tool>; check your server's actual tool names
{
  "permissions": {
    "allow": ["mcp__github__create_issue"],
    "deny":  ["mcp__github__merge_pull_request"]
  }
}
```
{/* /more */}








### Authentication

<Imagine text={"The Jira MCP server needs credentials. A password typed into the shared config file would leak to everyone who clones the repo."} />


<MythReality rows={[

- **User identity (SaaS, cloud)** - for hosted products such as Jira or GitHub: OAuth, where each user signs in through their browser · audit with a PostToolUse hook
- **Service identity (internal API)** - API key in an environment variable or secrets manager · never in committed config
- **Local (filesystem, local DB)** - stdio, no network auth · deny rules enforce path access

<Exercise title="Configure it" id="exercise-mcp-config">

Your team wants everyone's Claude Code to use the company's hosted Jira MCP server, but nobody should be able to delete issues. What transport, scope and permission rule do you use, and where does the credential go?

<div slot="answer">

**HTTP** transport (it's hosted), **project scope** in a committed `.mcp.json` (or enterprise managed settings for the whole org), a **deny rule** on the delete tool (`mcp__jira__delete_issue`), and the credential via **OAuth** per user or an environment variable, never in the file.

</div>
</Exercise>

**In practice:** a project-scoped MCP server is a committed `.mcp.json` file at the repo root, so everyone on the team gets it.

**A team MCP server in .mcp.json**
