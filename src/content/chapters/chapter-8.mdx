## 8.1 How Claude Code works

### In plain English

Claude Code is Claude working as a coding assistant inside your project folder. It can read files, write code and run commands, but asks permission first (how often depends on the permission mode). You give it standing project rules in a file called CLAUDE.md, and you can add automatic checks ("hooks") that always run, like "run the tests after every edit" or "never touch the secrets file".

## 8.2 Permission modes and settings

### Pick the mode by risk, not speed

| Mode | Auto-approves | Still gated | Use for |
|---|---|---|---|
| `default` | Reads | Edits and shell commands | New or unfamiliar codebases |
| `acceptEdits` | Reads, edits and common file commands in the working dir | Other shell commands, writes outside the dir, protected paths | Trusted local work where shell still needs an eye |
| `plan` | Reads only | Everything until you approve a plan | Sensitive or unfamiliar code |
| `auto` | Most actions, after a classifier reviews each one | Deploys, mass deletes, credential access, force-push | Fewer prompts (research preview; not a safety guarantee) |
| `dontAsk` | Only pre-approved tools | Everything else, auto-denied | Locked-down CI and scripts |
| `bypassPermissions` | Everything | Almost nothing | Disposable containers or VMs only, never a live workstation |

### Settings layers

| Level | File | Applies to |
|---|---|---|
| User | `~/.claude/settings.json` | All your projects |
| Project | `.claude/settings.json` (committed) | Everyone who clones the repo |
| Local | `.claude/settings.local.json` (git-ignored) | Your overrides for one project |
| Enterprise | Managed settings, set by admins | Everyone; can't be overridden |

**Deny beats allow**, and an enterprise deny can't be overridden, even in bypass mode. Put the human gate where the worst case is hard to undo: the agent's work is an input to a human decision on sensitive code, not a replacement for one.

## 8.3 Durable context

### Each rule in its right place

<Tiles cols={5} caption="Five mechanisms, five jobs" tiles={[
  { title: 'CLAUDE.md', sub: 'every session, always' },
  { title: 'Rules', sub: 'when a path matches' },
  { title: 'Skills', sub: 'loaded on demand' },
  { title: 'Hooks', sub: 'guaranteed, outside the model' },
  { title: 'Subagents', sub: 'isolated context' },
]} />

| Mechanism | Loads | Context cost | Belongs here |
|---|---|---|---|
| CLAUDE.md | At every session start (`/init` drafts one) | Constant; dilutes as it grows | Universal rules, build and test commands |
| `.claude/rules` | When a file matches its `paths` glob | Only when triggered | Path-specific guidance |
| Skills (`SKILL.md`) | Description at start, body on demand | Only when used | Reusable procedures; also replaces custom slash commands |
| Hooks | At lifecycle events, as your script | Minimal | Guardrails, side effects, audit logs |
| Subagents | Own context; returns a summary | Keeps the main context small | Exploration and parallel work |

CLAUDE.md is a working set of rules, not an append log: every line weakens the others. Past a few hundred lines, audit it. Instructions are **probabilistic**; hooks are **guarantees**. If a rule must always hold, make it a hook. Custom subagents don't inherit your skills unless they're listed in the subagent's definition.

### Hook events

<WhenThen whenLabel="Event" thenLabel="Typical use" rows={[
  { when: 'PreToolUse', then: 'Block an action before it runs (exit code 2), e.g. writes to .env or credentials in .mcp.json' },
  { when: 'PostToolUse', then: 'Format after an edit, run tests, write an audit log entry' },
  { when: 'UserPromptSubmit', then: 'Validate a prompt or inject context before the model sees it' },
  { when: 'Stop', then: 'Follow-up when Claude finishes: notify, clean up, commit the audit log' },

**For Java teams:** put `mvn -q test` or `./gradlew test` in CLAUDE.md and add a PostToolUse hook that runs your formatter (e.g. Spotless) after every edit. **For Python:** `pytest -q` and a `ruff format` hook.

## 8.4 Sharing a setup

### Skills, commands and plugins

- **Skill** - a SKILL.md in .claude/skills · loads when its description matches, or by name · the same skill can run in Claude Code, the API (code execution container) and the Agent SDK (set settingSources)
- **Custom command** - a named, explicit entry point · now written as a skill (set disable-model-invocation to stop automatic use) · the old .claude/commands folder is legacy
- **Plugin** - a versioned bundle of skills, hooks, subagents and MCP servers · installed from a marketplace in one step · admins can deploy org-wide

### Make it portable

A plugin that hard-codes `/Users/you/...` works for its author and fails for everyone else. Use `$CLAUDE_PROJECT_DIR` for project scripts and `${CLAUDE_PLUGIN_ROOT}` for scripts inside the plugin, bundle every file the plugin depends on, document and validate the environment variables it needs, and test the install on a clean machine. A deny rule or hook you relied on locally only travels with the plugin if it's bundled.
