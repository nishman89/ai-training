## 8.1 How tool use works

<ExamRef section="8.1" />

### In plain English

This domain is about letting Claude **do** things, not just talk:

- **Tool use** (also called function calling): you describe a function ("get_order_status takes an order ID"). Claude replies "please run get_order_status with A-1234". **Your** code runs it and sends back the answer, and Claude continues.
- **MCP** (the **Model Context Protocol**): an open standard for packaging tools so they plug into any Claude app, like USB for tools. A program that offers tools this way is an **MCP server**; an app that connects to it is an **MCP client**.

**Real-life example:** connect the GitHub MCP server once, and Claude can search code and open issues in any app that supports MCP.

Each one is effectively an integration requirement: what it can read or change, and under what rules."} />

### The round trip

First, the words you'll see in this chapter. They're all parts of Claude's reply (2.1 shows a full one):

| Word | What it means | Example |
|---|---|---|
| **Content block** | Claude's reply is a list of pieces called blocks, each with a `type` | A `text` block, then a `tool_use` block |
| `text` block | Words for the user | "Let me check that order." |
| `tool_use` block | Claude asking you to run a tool: the tool's `name`, the `input` it chose, and an `id` | `get_order_status`, `{"order_id": "A-1234"}`, `toolu_01A...` |
| `tool_result` block | What **you** send back after running it, quoting the same `id` | "Out for delivery, arriving today" |
| `stop_reason` | A field on every reply saying **why Claude stopped**. Your code checks it to know what to do next | `end_turn`: finished, show the answer. `tool_use`: it wants a tool, so run it and reply |
| **Tool definition** | What you send in the `tools` field of **every** request: a `name`, a `description`, and an `input_schema`. If a tool isn't listed, Claude doesn't know it exists | Step 1 below |
| **JSON schema** | A standard way to describe the shape of some data: which fields, what type, which are required | `order_id` must be a string |

**Claude never runs your code.** It only sees a description of each tool, and asks *you* to run it. Then you repeat until Claude stops asking: that's the **agent loop** (1.3).

**Where it usually goes wrong:** a `tool_use` with no `tool_result`, the wrong ID, or a failure your code hid instead of reporting it to Claude.

<CodeSwitch title="Order tool, step 2: the round trip">

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
// orderTool: step 1's tool description (8.1)
// getOrderStatus: your own function, e.g. a database lookup: takes an order ID, returns its status as text
// ── The example ──
// 1. Ask the question, sending the description from step 1
MessageCreateParams.Builder request = MessageCreateParams.builder()
    .model("claude-sonnet-5-5").maxTokens(1024)
    .addTool(orderTool)
    .addUserMessage("Where's order A-1234?");
Message reply = client.messages().create(request.build());   // stop_reason: tool_use

// 2. Claude asked for the tool: call YOUR method with the input Claude chose
ToolUseBlock use = reply.content().get(0).toolUse().orElseThrow();   // simplified: assumes it's the first block
String orderId = use._input().asObject().orElseThrow().get("order_id").asString().orElseThrow();
String status = getOrderStatus(orderId);                             // your method from step 1

// 3. Send the answer back as a tool_result with the same ID
request.addMessage(reply)
       .addUserMessageOfBlockParams(List.of(ContentBlockParam.ofToolResult(
           ToolResultBlockParam.builder().toolUseId(use.id()).content(status).build())));

// 4. Claude now writes the reply for the customer
Message answer = client.messages().create(request.build());          // stop_reason: end_turn
System.out.println(answer.content().get(0).text().get().text());     // "Your order A-1234 is out for delivery..."
```

```python
import anthropic
client = anthropic.Anthropic()            # one client per app; reads ANTHROPIC_API_KEY
# order_tool: step 1's tool description (8.1)
# get_order_status: your own function, e.g. a database lookup: takes an order ID, returns its status as text
# ── The example ──
# 1. Ask the question, sending the description from step 1

messages.append({"role": "assistant", "content": reply.content})
messages.append({"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": use.id, "content": status}]})

answer = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024,
                                tools=[order_tool], messages=messages)  # stop_reason: end_turn
print(answer.content[0].text)   # "Your order A-1234 is out for delivery..."
```

```typescript
// ── Setup: where the names below come from ──
import Anthropic from '@anthropic-ai/sdk';
const client = new Anthropic();             // one per app; reads ANTHROPIC_API_KEY
// orderTool: step 1's tool description (8.1)
// getOrderStatus: your own function, e.g. a database lookup: takes an order ID, returns its status as text
// ── The example ──
// 1. Ask the question, sending the description from step 1
const messages: Anthropic.MessageParam[] = [{ role: 'user', content: "Where's order A-1234?" }];
const reply = await client.messages.create({ model: 'claude-sonnet-5-5', max_tokens: 1024,
                                             tools: [orderTool], messages });   // stop_reason: tool_use

// 2. Claude asked for the tool: call YOUR method with the input Claude chose
const use = reply.content.find((b) => b.type === 'tool_use') as Anthropic.ToolUseBlock;
const status = await getOrderStatus((use.input as { order_id: string }).order_id);   // step 1's method

// 3. Send the answer back as a tool_result with the same ID
messages.push({ role: 'assistant', content: reply.content });
messages.push({ role: 'user', content: [{ type: 'tool_result', tool_use_id: use.id, content: status }] });

// 4. Claude now writes the reply for the customer
const answer = await client.messages.create({ model: 'claude-sonnet-5-5', max_tokens: 1024,
                                              tools: [orderTool], messages });   // stop_reason: end_turn
console.log((answer.content[0] as Anthropic.TextBlock).text);   // "Your order A-1234 is out for delivery..."
```

## 8.2 Designing tools Claude picks correctly

<ExamRef section="8.2" />
<Imagine text={"Claude keeps calling the refund tool when customers ask where their order is. Both tools have one-line descriptions, so Claude is guessing."} />

### Claude picks tools by their description

Claude decides which tool to use by reading the name and description of every tool you've given it, and comparing them with what the user asked. If two descriptions sound alike, it has nothing reliable to go on, so it guesses.

- **Say when NOT to use it** - one sentence saying when not to use a tool shows Claude exactly where the line is · "Look up an order's status. Do not use for refunds."
- **Merge what you can't separate** - if two tools overlap and you can't describe the difference clearly, make them one tool with a parameter for the type
- **Use the schema** - an enum (a fixed list of allowed values) wherever only certain values are valid · mark a field required only if it truly is · describe every parameter
- **Don't give it too many tools** - every definition costs tokens on every call, and overlapping tools make Claude's choices unreliable · start with the fewest that do the job

{/* more:8-describe */}
**Example:** two definitions of the same tool. Claude reads only the name, description and schema, so the second one gets picked correctly far more often.

### Errors go back to Claude

<Imagine text={"The stock system times out, your tool quietly returns an empty list, and Claude tells a customer the router is out of stock. It isn't."} />

Return failures as a `tool_result` with `is_error: true` and a useful message, so the model can retry, try another approach, ask the user or stop. An empty result is read as valid data ("no orders found"), and the model carries on confidently.

```json
{ "type": "tool_result", "tool_use_id": "toolu_01A",
  "content": "Inventory service timed out after 5s. Stock level unknown.",
  "is_error": true }
```

**Don't confuse this with an API error (2.4).** They happen at different points and are handled by different code:

| | **API error** (2.4) | **Tool error** (this section) |
|---|---|---|
| What failed | Your call **to Claude** | **Your own** function that Claude asked you to run |
| What you see | HTTP 4xx/5xx and an exception; no reply | A normal reply with `stop_reason: tool_use`; then *your* tool throws |
| Who deals with it | Your code: retry or give up | **Claude**: you tell it with `is_error: true`, and it decides what to do next |
| Example | 429 rate limited | The stock API timed out |

### Validate the tool's input, and send problems back to Claude

<Imagine text={"A customer types \"my order is 1234\". Claude calls `get_order_status` with `1234`, without the `A-` prefix. Your database finds nothing and says \"no such order\", and Claude tells the customer their order doesn't exist."} />

The arguments in a `tool_use` block are **untrusted input**, just like a form a user filled in. Usually they match your schema; sometimes a field is missing, has the wrong type or an extra key. (A **strict** tool, 6.3, enforces the schema shape, but you still need to check your business rules.) So every tool should:

1. **Validate the input** against a schema in your code: Zod in TypeScript, Pydantic in Python, Bean Validation or Jackson in Java. Apply defaults for optional fields.
2. **If it's invalid, don't crash and don't guess.** Return a `tool_result` with `is_error: true` and a message saying exactly what was wrong.
3. **Let Claude retry.** It reads the error and calls the tool again with corrected arguments.

### Keep tool results small, and safe to repeat

<Imagine text={"A search_orders tool returns all 4,000 of a customer's orders as raw JSON. One call fills a third of the context window, and Claude still can't find the order it needs."} />

Every tool result goes into the context window and is resent on every later call (6.5). Design tools to return **only what Claude needs**:

| Do | Example |
|---|---|
| **Filter and limit** in the tool | `search_orders(customer_id, status="open", limit=10)` |
| **Paginate** big result sets | Return 10 results plus a `next_cursor`; Claude asks for more only if it needs them |
| **Return the useful fields**, not the raw record | `{"order_id", "status", "eta"}`, not 80 database columns |
| **Summarise or truncate** long text, and say so | `"...first 2,000 characters of 48,000; call get_page for more"` |

```json
{ "orders": [ {"order_id": "A-1234", "status": "in_transit", "eta": "2026-11-24"} ],
  "returned": 1, "total_matching": 37, "next_cursor": "c_9f2" }
```

**Make write tools safe to repeat (idempotent).** An agent may call a tool twice: after a timeout, after a retry, or because it lost track. For a tool that changes something (a refund, an email, a new ticket), a second identical call must not do it twice.

- Give each action an **idempotency key**, for example the order ID plus the action.
- Have your tool ignore a repeat of a key it has already processed.

### Client tools vs server tools: where the tool runs

Tools differ in *who runs them*. Most are yours, but Anthropic also runs some tools for you on its own servers.

{/* more:8-clientserver-table */}
| | Client tools | Server tools |
|---|---|---|
| **Who runs it** | Your code | Anthropic |
| **Who writes it** | You (or you use a definition Anthropic provides, like bash) | Anthropic; you just switch it on |
| **Examples** | `get_order_status`, `issue_refund`, bash, text editor | Web search, web fetch, code execution |
| **What you get back** | `stop_reason: tool_use`; you run it and send a `tool_result` | The results are already in the reply |
| **Cost** | Just tokens | Tokens, and some charge per use |
{/* /more */}

`tool_choice` is a request setting that controls whether Claude may, must or must not call a tool.

| `tool_choice` | Meaning |
|---|---|
| `auto` (default) | Claude decides whether to call a tool |
| `any` | Must call some tool |
| `tool` + name | Must call that specific tool (forced) |
| `none` | Must not call tools |

**Model check:** Claude Opus 5.5 rejects the forcing options (`any` and `tool`) with a 400 error, so code that forced a tool breaks when you upgrade. On that model, keep `auto`, make the tool `strict`, and say in the prompt when it applies. For a guaranteed JSON shape, use structured outputs (`output_config.format`).

Claude can ask for several tools in one reply (**parallel tool use**). Add `disable_parallel_tool_use: true` if you want at most one tool call per reply.

Server tools such as web search can run several times in a row on Anthropic's side. If that goes on for too long, the API pauses and returns `stop_reason: pause_turn`. To let it carry on, send the conversation back exactly as it is; don't add a "please continue" message.

### Other Anthropic-defined tools: computer use, and the "batch tool" pattern

**Computer use** lets Claude operate a desktop through screenshots.

- **How:** Claude looks at a screenshot and replies with actions ("click at 420, 310", "type 'refund'"). **Your code** performs them in a sandboxed virtual machine and sends back a new screenshot.
- **Who runs it:** Anthropic defines the tool but you run it, so it's a client tool (like the text editor and bash tools).
- **Use it for:** systems with no API.
- **Be careful:** it's slower and less reliable than a real API. Run it isolated, with limited permissions, and have a person approve anything risky.

**Check the result, don't assume it.** An agent that acted should **inspect the environment** afterwards: take a new screenshot, re-read the file, run the tests, query the record. Then it knows the action worked, rather than trusting its own report.

**The "batch tool" pattern.** When Claude needs several independent lookups, it can ask for them in one turn as several `tool_use` blocks (8.1). Some older models were reluctant to do that, so one workaround is a single `batch` tool whose input is a *list* of tool calls, which your code runs together. Either way the aim is the same: fewer round trips, so the job finishes faster.

## 8.4 The Model Context Protocol

<ExamRef section="8.4" />
<Imagine text={"Three Acme apps (the chatbot, the staff dashboard and Claude Code) all need to check stock levels. Writing the same integration three times, and keeping three copies in sync, is wasted effort."} />

### Why MCP

**The picture to keep in mind: MCP is "a USB-C port for AI".** That's the official description. Before USB, every device needed its own cable and its own driver. MCP does the same job for AI apps and the tools they use: one agreed way to plug things in.

| USB world | MCP world |
|---|---|
| The USB standard: the agreed rules | **MCP** itself: the protocol, the agreed format of the messages |
| A device: printer, keyboard, drive | An **MCP server**: ticketing, Postgres, GitHub |
| The computer you plug into | The **MCP host**: Claude Desktop, Claude Code, your own app |
| Each port on the computer | An **MCP client**: a connector inside the host, one per connected server |
| The cable: plugged in, or over the network | The **transport**: stdio (local, on the same machine) or Streamable HTTP (remote) |
| The computer asks "what are you, and what can you do?" | The **handshake**: the client starts the connection and asks the server to list its tools, resources and prompts |

**Where the picture holds:** build a server once and it works with any MCP host, with no custom wiring.

**Where it breaks:** plugging in an unknown USB stick is risky, and so is connecting an unknown MCP server. Its tool descriptions and results go straight into Claude's context, so a malicious server can try prompt injection (7.1). Connect only servers you trust, and limit what each tool may do (8.5). And unlike a cable, MCP doesn't decide anything: your app (or Claude) still runs the loop and chooses which tools to call.

Wiring a tool straight into each app means three apps need three integrations. MCP moves the tool into a **server** that any **MCP client**, meaning any app that speaks MCP (Claude Code, Claude apps, your own app), can attach to, so you build the integration once. Think JDBC: one driver standard, many databases and clients.

{/* more:8-mcpcaps-table */}
An MCP server can offer three kinds of thing. The difference is **who decides to use it**:

| Capability | Who uses it | What it is | Example (an inventory server) |
|---|---|---|---|
| **Tool** | Claude decides to call it | An action with parameters | `get_stock(sku)` |
| **Resource** | The app attaches it to the conversation | Read-only data | `inventory://warehouses`, a list of warehouses |
| **Prompt** | The user picks it from a menu | A ready-made template | `restock-report` (in Claude Code it appears as a slash command) |
{/* /more */}

### Transports: how Claude connects to an MCP server

<Imagine text={"One MCP server is a script on a developer's laptop; another is a shared service the whole company uses. They can't connect the same way."} />

A **transport** is the channel the client and server use to exchange messages. There are two.

<VsPair

### Who controls each primitive, and resources in detail

The three things a server offers (tools, resources and prompts) are called its **primitives**. The table above shows who uses each one. Put another way, each is **controlled** by a different party, and that decides which one to build:

| Primitive | Controlled by | Build one when… |
|---|---|---|
| **Tool** | the **model**: Claude decides to call it | Claude should decide *when* to act or fetch something |
| **Resource** | the **application**: your app decides what to attach | Your app already knows which data is relevant (for example, the document the user opened) |
| **Prompt** | the **user**: they pick it, often as a slash command | Users run a well-tested workflow on purpose ("/restock-report") |

A resource has a **URI** (an address) and a **MIME type** that says what kind of content it is (`application/json`, `text/plain`), so the client knows how to read it. There are two kinds:

- **Direct (fixed) resources** have a fixed URI: `inventory://warehouses`.
- **Templated resources** have a parameter in the URI: `inventory://products/{sku}`. One definition serves every product.

```python
@mcp.resource("inventory://products/{sku}", mime_type="application/json")
def product(sku: str) -> str:
    """Stock and price for one product."""                  # templated: {sku} comes from the URI
    return json.dumps(inventory_api.product(sku))

@mcp.prompt()
def restock_report(warehouse: str) -> str:
    """Weekly restock report for one warehouse."""          # the user picks this from a menu
    return f"Using the inventory tools, list every SKU in {warehouse} below its reorder level..."
```

### Under the hood: messages, the handshake and sessions

<Imagine text={"A remote MCP server works with one instance, then fails randomly once it's behind a load balancer with three instances."} />

MCP messages are **JSON-RPC 2.0**: small JSON objects of three kinds:

| Message | Has an `id`? | Expects a reply? | Example |
|---|---|---|---|
| **Request** | Yes | Yes | `tools/call`, `resources/read` |
| **Result** (response) | Yes, the same `id` as its request | No | The tool's output |
| **Notification** | **No** | **No** | `notifications/progress`, `notifications/initialized` |

Every connection starts with a **handshake**: the client sends an `initialize` request (its version and capabilities), the server replies with its own, and the client sends an `initialized` notification. Only then can tools be listed and called.

```json
{"jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {"protocolVersion": "...", "capabilities": {}, "clientInfo": {"name": "claude-code"}}}
{"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "...", "capabilities": {"tools": {}}, "serverInfo": {"name": "inventory"}}}
{"jsonrpc": "2.0", "method": "notifications/initialized"}
{"jsonrpc": "2.0", "id": 2, "method": "tools/call", "params": {"name": "get_stock", "arguments": {"sku": "RTR-500"}}}
```

<Explain title="Reading it" steps={["Line 1 is a request (it has `id: 1`): the client introduces itself.", "Line 2 is the result for request 1: the server says it offers tools.", "Line 3 has no `id`: it's a notification that the handshake is done. No reply is expected.", "Line 4 is a normal request to call a tool. Its result will come back with `id: 2`."]} />

**Transports.** Over **stdio**, these messages travel through the server process's standard input and output on one machine. Over **Streamable HTTP**, the client POSTs messages to one URL, and the server can stream messages back using **server-sent events (SSE)**. The server may give the client an `Mcp-Session-Id` header during the handshake, and the client sends it on every later request.

That session is what broke behind the load balancer: a **stateful** server remembers each session in one instance's memory, so a request routed to another instance doesn't recognise the session. The fixes are to route each session to the same instance ("sticky sessions"), keep session state in a shared store, or run the server in **stateless** mode where every request stands alone.

MCP doesn't use **websockets**. Remote MCP is plain HTTP plus SSE, and so is Claude's own API streaming (2.3). Your app may still use websockets between its server and the browser, but that's your choice, not part of either protocol.

### Advanced server features: sampling, notifications and roots

| Feature | What it does | Why it matters |
|---|---|---|
| **Sampling** | The server asks the **client** to run a Claude call for it and send back the result | The server needs no API key or AI bill of its own; the client keeps control of which model is used and what's sent |
| **Progress and log notifications** | During a slow tool call, the server sends `notifications/progress` ("40% done") and log messages | Users see that a 30-second job is working, not frozen |
| **Roots** | The client tells the server which folders it may use ("only `/projects/acme`") | A file-handling server stays inside the folders it was given. Your server code must still check every path against the roots |

## 8.5 MCP scope, permissions and auth

<ExamRef section="8.5" />
<Imagine text={"The team shares a Jira MCP server. Everyone should be able to read and create issues, nobody should be able to delete them, and the password must never end up in Git."} />

### MCP server scopes in Claude Code

In Claude Code, an MCP server's **scope** is where its configuration is saved, and that decides who gets the server.

| Scope | Stored in | Who gets it | Right for |
|---|---|---|---|
| Local | `~/.claude.json` under the project | Only you, in this project | A tool tied to one project |
| User | Your personal Claude settings | Only you, every project | Your own local utilities |
| Project | `.mcp.json` at the repo root (committed) | Everyone who clones the repo | Team-wide servers |
| Enterprise | Managed settings, set by an admin | Everyone in the organisation | Internal services, security tooling |

**Transport** (how Claude connects to the server) and **scope** (who gets the configuration) are separate choices, but they affect each other. A stdio server listed in the committed `.mcp.json` **looks shared but isn't**: every teammate gets the entry, but it only works on machines where the script and its runtime are installed. A server the whole team relies on should run over HTTP, in project or enterprise scope.

### Per-tool permissions

<Imagine text={"The GitHub MCP server offers 40 tools. You want Claude to open issues freely but never merge a pull request."} />

Connecting a server gives Claude its whole list of tools. Permission rules can target a single tool by its full name, `mcp__<server>__<tool>`:

- **Allow one, ask for the rest:** allow `mcp__github__create_issue` without asking; every other GitHub tool still asks.
- **Block the risky one:** deny a tool that writes; the read tools stay available.
- **A deny on one tool beats an allow on the whole server.**

These are the same allow and deny rules as for any Claude Code tool (3.2). Only the naming is specific to MCP.

{/* more:8-pertool */}
```json
// .claude/settings.json: tool names follow mcp__<server>__<tool>; check your server's actual tool names
{
  "permissions": {
    "allow": ["mcp__github__create_issue"],
    "deny":  ["mcp__github__merge_pull_request"]
  }
}
```
<Explain steps={["`allow` lets Claude create GitHub issues without asking each time.", "`deny` blocks merging pull requests completely, even though the rest of the GitHub server is connected.", "MCP tool names follow the pattern `mcp__<server>__<tool>`."]} />
{/* /more */}

Outside Claude Code, the Messages API can call remote MCP servers directly through the **MCP connector**. There, an `mcp_toolset` setting switches each tool on or off. The difference: a permission rule decides whether a tool may **run**; switching it off means the model never even **sees** it.

### Authentication

<Imagine text={"The Jira MCP server needs credentials. A password typed into the shared config file would leak to everyone who clones the repo."} />

<MythReality rows={[
  { myth: 'Put the API key in .mcp.json so teammates can connect', reality: 'The key goes into git history for good: rotate it. Reference an environment variable; the file holds only the server address' },
  { myth: 'OAuth that works in staging will work in production', reality: 'Redirect URIs are registered per host: add production\'s before go-live' },
]} />

- **User identity (SaaS, cloud)** - for hosted products such as Jira or GitHub: OAuth, where each user signs in through their browser · audit with a PostToolUse hook
- **Service identity (internal API)** - API key in an environment variable or secrets manager · never in committed config
- **Local (filesystem, local DB)** - stdio, no network auth · deny rules enforce path access

<Exercise title="Configure it" id="exercise-mcp-config">

Your team wants everyone's Claude Code to use the company's hosted Jira MCP server, but nobody should be able to delete issues. What transport, scope and permission rule do you use, and where does the credential go?

<div slot="answer">

- **Transport: HTTP**, because the server is hosted, not running on each laptop.
- **Scope: project**, in a `.mcp.json` file committed to the repo, so everyone gets it. (Enterprise managed settings can do the same for the whole organisation.)
- **Permission: a deny rule** on the delete tool, `mcp__jira__delete_issue`, so it's blocked whatever anyone approves.
- **Credential:** each user signs in with **OAuth**, or it comes from an environment variable. Never put it in the file.

</div>
</Exercise>
