## 5.1 Choosing a model

<ExamRef section="5.1" />
<Imagine text={"Acme runs three AI jobs: tagging 2 million tickets a month, a customer chatbot, and an agent that investigates network faults. One model for all three would be too weak for the hard job or far too expensive for the easy one."} />

### In plain English

Picking which Claude to use, and not wasting money.

- **Bigger models** are smarter but cost more and respond more slowly. Sorting emails into "billing" or "tech" is easy, so use Haiku; reviewing a tricky contract is hard, so use a bigger model.
- **Caching:** re-sending the same long document is far cheaper the second time.
- **Batching:** send a pile of jobs to run overnight at half price.

### The current lineup

All four current models have a 1M-token **context window** (the most one request can hold, input plus output: roughly 750,000 words), a **max output** of 128K tokens (the longest single reply), and **adaptive thinking** (they reason before answering when it helps, 5.2). **Default effort** is how hard each model thinks unless you say otherwise (also 5.2).

| Model | API ID | Input / output per 1M tokens | Default effort | Speed | Best for |
|---|---|---|---|---|---|
| Fable 5.2 | `claude-fable-5-2` | $8 / $40 | high | Moderate | Hardest reasoning, long-horizon agents |
| Opus 5.5 | `claude-opus-5-5` | $4 / $20 | medium | Moderate | Long-running agentic coding and knowledge work |
| Sonnet 5.5 | `claude-sonnet-5-5` | $2 / $10 | high | Fast | The balanced default |
| Haiku 5.5 | `claude-haiku-5-5` | from $0.10 / $0.50 | medium | Fastest | Classification, extraction, routing, high volume |

Prices and IDs change: check the [models overview](https://platform.claude.com/docs/en/models-overview) when you build. In code, the Models API (`GET /v1/models`) lists the models your account can use, with their limits and capabilities. Read those values from it rather than hard-coding them.

### How a model works: the basics

Every model choice rests on a few facts about how Claude produces text:

| Property | What it means | What you do about it |
|---|---|---|
| **Next-token prediction** | Claude writes one token at a time, each time picking a likely next token given everything so far | It's why output costs per token, and why a reply can stop mid-sentence at `max_tokens` |
| **Non-determinism** | The same prompt can give different wording each time | Test **properties** ("is it valid JSON? under 50 words?"), not exact text (4.2) |
| **Knowledge cutoff** | What the model knows comes from training data up to a date; it knows nothing after that, or about your private data | Give it the facts in the prompt: RAG, tools, web search |
| **Working memory = the context window** | It "remembers" only what's in this one request | Resend history; manage the window (6.5) |
| **Hallucination** | When it lacks the facts, it can produce a confident, plausible answer that's wrong | Supply sources; let it say "I don't know"; ask it to quote its sources before answering; check outputs in code |
| **Steerability** | Clear instructions, examples and a system prompt change its behaviour a lot | Prompt engineering (Domain 6) is the first lever, before changing model |

Anthropic's guidance gives two ways to pick a starting model:

| | **Capability-first** | **Efficiency-first** |
|---|---|---|
| Start on | Opus 5.5 (Anthropic's recommendation for most work) | Haiku 5.5 |
| Good for | Getting quality right first | Prototypes, fast replies, high-volume simple jobs, tight budgets |
| Then | Lower the effort, or move down to Sonnet, once it works | Move up only when your tests show a specific gap |

Two rules apply either way:

- **Try changing effort before changing model.** It's a one-line change, and it's often enough.
- **Decide with your own test results**, not by feel.

Fable 5.2, the top tier, is for when even Opus at the highest effort still fails your tests.

**Worked example: tagging 1 million support tickets.** Each ticket is about 300 input tokens and the label about 20 output tokens, so the job is 300M input tokens and 20M output tokens. Using list prices (thinking would add a little more output):

| Model | Input | Output | Total | With the Batch API (50% off) |
|---|---|---|---|---|

| Sonnet 5.5 ($2 / $10) | $600 | $200 | **$800** | $400 |

If Haiku passes your eval on a sample of real tickets, it does the job for about 1/40th of the Opus price. That's why the model choice is a measured decision, not a default.

### Routing: a default plus an override

<Imagine text={"90% of chats are simple FAQs and 10% are complex faults. Running all of them on the most capable model wastes money on the 90%."} />

**Routing** (the workflow pattern from 1.2) means sending each request to a different model depending on what kind of request it is: simple ones to a cheap model, hard ones to a capable one. You don't have to use one model for everything.

A common setup in production: most requests go to a middle model (usually Sonnet), and your code moves particular requests up or down:

| Request | Goes to | Decided by |
|---|---|---|
| "What are your opening hours?" | Haiku | Task type: a simple FAQ |
| A normal support question | Sonnet (the default) | Everything else |
| A 300-page contract to review | Opus | Input length and difficulty |

- **Handles well** - matching each workload to the cheapest model that meets its quality bar
- **Costs** - a classification step and a second model path to maintain
- **Skip it when** - traffic is uniform at one quality bar: pin one model

## 5.2 Reasoning and effort

<ExamRef section="5.2" />
<Imagine text={"The same model answers \"when is my bill due?\" and \"why does my line drop every evening at 7pm?\". The first needs no thought; the second needs real reasoning. Paying for deep thinking on both wastes money."} />

### Two separate decisions

**Reasoning** (or **thinking**) is Claude working a problem through step by step before it writes the answer, like doing rough working before filling in the final box on an exam paper. That working costs tokens and time, so how much Claude does is something you control.

There are two separate decisions:

| Decision | What you choose | Like choosing… |
|---|---|---|
| **Model** (5.1) | Which Claude: Haiku, Sonnet, Opus, Fable | Which person does the job |
| **Effort** (this section) | How hard that model thinks: `low`, `medium`, `high`, `xhigh`, `max` | How long you give them |

### Fixed budget vs adaptive thinking

Older models used a **fixed thinking budget** (`budget_tokens`): you set one maximum, such as `{"type": "enabled", "budget_tokens": 10000}`, and every request got the same allowance. One size fitted nothing.

Current models use **adaptive thinking**: Claude decides how much to think from how hard the request is. `effort` is the overall dial (lower for speed and cost, higher for depth), not an exact token count.

Take the two questions from the Imagine above, sent to the same assistant:

| Request | Fixed budget of 10,000 | Adaptive thinking |
|---|---|---|
| "When is my bill due?" | May think far more than needed: slower and costs more | Little or no thinking: a fast, cheap answer |
| "Why does my line drop every evening at 7pm?" | May run out of room and "underthink": a weaker answer | Thinks it through: checks usage patterns, scheduled jobs, area faults |

> **Analogy:** a fixed budget gives every student exactly 30 minutes, whether the question is "what's 2 + 2?" or a long essay. Adaptive thinking lets each student take the time the question actually needs.

You don't set an exact token budget any more. By default the newest models don't show you the thinking text; ask for a summarised version (6.4) if you need to see or display it.

Things to know:

- **More thinking means more output tokens**, so more cost and more waiting. Thinking tokens are billed as output.
- **On some models you can't switch it off.** Opus 5.5 and Fable 5.2 always think: sending `thinking: {type: "disabled"}` or an old-style fixed `budget_tokens` returns a 400 error. Use low effort instead.
- **In a multi-turn conversation**, pass the **thinking blocks** (the reasoning parts of a reply) back unchanged. 6.4 covers how thinking looks in a reply and how to show it.

{/* code:5.2 */}
**In code:** effort is one field, `output_config.effort`: `low`, `medium`, `high`, `xhigh` or `max`. Leave it out and you get the model's default (`medium` on Opus 5.5 and Haiku 5.5, `high` on the others).

### Fast mode: same model, faster output

<Imagine text={"A coding agent on Opus 5.5 gives excellent answers, but developers wait too long while it writes long diffs. Switching to a smaller model would lower quality."} />

**Fast mode** runs the same Opus-class model on a faster setup: up to about **2.5× more output tokens per second**, with the **same quality**, at a **premium price**. You switch it on per request with `speed: "fast"` (with a beta header on some models).

| | Lower effort | Smaller model | Fast mode |
|---|---|---|---|
| What changes | It thinks less | A different, cheaper model | The same model writes faster |
| Quality | Less depth on hard problems | Lower on hard tasks | **Unchanged** |
| Cost | Lower | Much lower | **Higher** |
| Speeds up | Total time (less thinking) | Everything | Output speed, not the wait for the first token |

Use fast mode when quality must stay at Opus level *and* speed matters more than cost, for example an interactive coding agent. It isn't the answer for cutting cost.

## 5.3 Prompt caching

<ExamRef section="5.3" />
<Imagine text={"Every chatbot call sends the same 20,000-token policy handbook before the customer's question. You're paying to process identical text 10,000 times a day."} />

### How it works

Many apps send the same long text at the start of every request: a 20-page policy document, a big system prompt, a long list of tools.

- **Without caching:** Claude reads it from scratch each time, and you pay full price each time.
- **With prompt caching:** Claude keeps its already-processed version for a few minutes. The next request that starts the same way reuses it: much faster, and about a tenth of the price for that part.

Three words you'll see:

- **Prefix:** the unchanging start of your request. It's built in a fixed order: **tools → system → messages**.
- **Breakpoint:** the `cache_control` marker. It means "cache everything up to here".
- **Where the cache lives:** on Anthropic's side, private to your organisation. You don't look anything up: when a new request *starts* with exactly the same text as one cached in the last few minutes, it's reused automatically, and the reply's `usage` shows it as `cache_read_input_tokens`.

**Static or dynamic?** Caching depends on splitting the request into two kinds of content:

| | Static | Dynamic |
|---|---|---|
| **Means** | The same on every request | Changes from one request to the next |
| **Examples** | The policy manual, the role and rules, few-shot examples, tool definitions | The user's question, their name or ID, the time, retrieved chunks |
| **Where it goes** | First, **before** the cache marker | After the cache marker |

"Static" doesn't mean it can never change. If the company updates the manual, the next request misses the cache, the new version is cached, and every request after that hits it again.

Two ways to mark it:

- **Automatic** - one top-level cache_control; the breakpoint moves forward as the conversation grows · best for multi-turn chat
- **Explicit** - cache_control on specific blocks, up to 4 breakpoints · best when sections change at different rates (tools rarely, retrieved documents daily)

### What it costs

<Imagine text={"Caching sounds like free money, but the first call costs more than normal. When does it actually save?"} />

| Operation | Price vs base input |
|---|---|
| Cache write, 5-minute **TTL** (time to live: how long the entry lasts; the default) | 1.25× |
| Cache write, 1-hour TTL | 2× |
| Cache read | 0.1× on most models; **0.05× on Opus and Sonnet 5.5**; **0.025× on Fable** |

Writes cost **more** than normal input, so caching pays only when reads outnumber writes. The 5-minute lifetime refreshes free on every hit. These multipliers stack with the Batch API discount.

### What breaks the cache

<Imagine text={"Caching is switched on, but the bill hasn't dropped at all. Something at the top of the prompt changes on every call."} />

The prefix must be **byte-identical**: the same characters, in the same order. It's built in this order: **tools → system → messages**. A change at one level breaks the cache for that level and everything after it:

- Edit a **tool definition** (the very first thing) → the **entire** cache is lost.
- Edit the **system prompt** → the system prompt and messages are lost.
- Add a new **user message** at the end → nothing before it is lost.

<WhenThen whenLabel="If you change…" thenLabel="…this is invalidated" rows={[
  { when: 'tool definitions', then: 'Everything: tools, system and messages' },
  { when: 'web search or citations (Claude quoting its sources) on/off', then: 'System and messages' },
  { when: 'tool_choice, or add/remove images', then: 'Messages only' },
  { when: 'a timestamp or user name near the top', then: 'Everything after it, on every call (move it below the last breakpoint)' },
]} />

### Proving it works

<Imagine text={"Your manager asks: \"Is caching actually working?\" You need numbers, not a hunch."} />

Read the usage fields on each reply. Together they add up to the whole input: `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`. (`input_tokens` is only the uncached part after the last breakpoint.)

| What `usage` shows | What it means | What to do |
|---|---|---|
| `cache_read_input_tokens` above 0 | **Working**: the prefix came from the cache | Nothing |
| `cache_creation_input_tokens` above 0 on **every** call, reads always 0 | Something near the top changes every call, so every call writes a new entry and pays **more** | Move the changing part (time, user name) after the breakpoint |
| Both are 0 | Nothing was cached. Usually the cached part is **too short**: under **512 tokens** on the current models (Opus, Sonnet and Haiku 5.5). No error is returned | Cache a longer block, or don't bother caching |

```java
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY

    .model(Model.CLAUDE_SONNET_5_5).maxTokens(1024L)
    .systemOfTextBlockParams(List.of(   // ← new: the system prompt as blocks
        TextBlockParam.builder().text("You are Acme's support assistant. Answer briefly and politely.").build(),   // ← new
        TextBlockParam.builder().text(policy)   // ← new
            .cacheControl(CacheControlEphemeral.builder().build())   // ← new: cache everything up to here
            .build()))   // ← new
    .addUserMessage("Can I upgrade my plan mid-contract?")                // changes on every call, so it comes after the cached part
    .build());

long read  = msg.usage().cacheReadInputTokens().orElse(0L);   // ← new
long write = msg.usage().cacheCreationInputTokens().orElse(0L);   // ← new
// ← new: first call: write > 0. Same prefix again within 5 minutes: read > 0. Both 0: not cached
```

## 5.4 Batch processing

<ExamRef section="5.4" />
<Imagine text={"Every night, Acme wants yesterday's 50,000 tickets tagged by category for the morning dashboard. Nobody is waiting for any single answer, so why pay for instant ones?"} />

### The Message Batches API

For work that doesn't need an answer now (overnight classification, dataset backfills, eval runs, scheduled reports), the **Message Batches API** (often just "the Batch API") processes requests **asynchronously**, meaning you hand over the work and collect the answers later instead of waiting, at **50% off** input and output.

<Flow caption="A batch job: submit, poll, collect" steps={[
  { title: 'Submit', sub: 'up to 100,000 requests or 256 MB' },
  { title: 'Get a batch ID', sub: 'returned immediately' },
  { title: 'Poll for status', sub: 'often < 1 h, up to 24 h' },
  { title: 'Download results', sub: 'one per request' },
]} />

<MythReality rows={[
  { myth: 'Batch gives faster answers for big jobs', reality: 'It trades latency for cost: timing is non-deterministic, up to 24 hours. Never use it when a user is waiting' },
  { myth: 'Batch results are lower quality', reality: 'Same models and quality; only the scheduling and price differ' },
  { myth: 'A loop of synchronous calls is a batch job', reality: '"Serialisation with extra steps": you pay full price and still block. Use the Batches API, or the async client for concurrency' },
]} />

For high volume that **does** need fast answers, use the SDK's **async client** (`client.async()`, returning `CompletableFuture<Message>`), which sends many requests at once without blocking a thread per request.

{/* more:5-batchwhen */}
#### When should you batch? A three-question test

1. Are there **lots of separate requests**?
2. Does each one **stand alone** (no request needs another's answer)?
3. Is **nobody waiting** at a screen for the result?

Three yeses: batch it and pay half. Any no: use the normal Messages API.

**Not for agents:** an agent's loop needs each reply straight away to decide its next step (1.3). With batch results taking up to 24 hours, it can't run one.

| | Messages API | Batch API |
|---|---|---|
| Like… | Ordering at the counter | Dropping off a big laundry bag |
| You get the answer | Now, in seconds | Later: usually under an hour, at most 24 hours |
| Price | Full | Half |
| Use for | Chat, buttons a user clicked, agents | Overnight tagging, backfills, eval runs, reports |

Claude never sends anything to customers: the batch results come back to **your code**, which decides what happens next.

#### Putting it together: triage now, batch the rest

Acme wants urgent incidents handled straight away, but drafting replies to routine tickets can wait until the morning. If everything went into a batch, a P1 outage would sit unnoticed for hours. So each ticket gets one quick, cheap call as it arrives (**routing**, 1.2), and only the routine ones go into tonight's batch.

**In code:** submit many requests in one batch, each with your own `custom_id`, then read the results when the batch has ended. Results can come back in any order, so match them by `custom_id`.

<CodeSwitch title="Submit a batch, then read the results" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
// tickets: tonight's tickets from your database; each has an id and text
// save: your own code to store a result, or queue the request to try again
// ── The example ──
BatchCreateParams.Builder batch = BatchCreateParams.builder();
for (Ticket t : tickets) {
    batch.addRequest(BatchCreateParams.Request.builder()
        .customId("ticket-" + t.id())                         // your key for matching results
        .params(BatchCreateParams.Request.Params.builder()
            .model(Model.CLAUDE_HAIKU_5_5).maxTokens(50)
            .addUserMessage("Tag this ticket: " + t.text())
            .build())
        .build());
}
MessageBatch created = client.messages().batches().create(batch.build());

// later (a scheduled job): once processingStatus is ENDED, stream the results
try (var results = client.messages().batches().resultsStreaming(
        BatchResultsParams.builder().messageBatchId(created.id()).build())) {
    results.stream().forEach(r -> {
        if (r.result().isSucceeded()) save(r.customId(), r.result().asSucceeded().message());
        else retryLater(r.customId());                        // errored or expired
    });
}
```

## 5.5 Token budgets

<ExamRef section="5.5" />
<Imagine text={"In testing, conversations were short. In production, customers paste whole email threads, chats run to 60 turns, and requests start failing or getting cut off."} />

### Everything is tokens

This section is about the **cost** side of tokens: where the tokens in each call come from, how to count them before sending, what a feature will cost, and how to bring the bill down. (The other side, fitting everything into the model's size limit, the **context window**, is in 6.5. Reading the token counts in a reply is in 2.1.)

- **Count before sending** - the token counting endpoint measures a request before you send it, so you can gate or trim instead of failing
- **Images cost tokens** - roughly (width × height) / 784: a 1,000 × 1,000 px image ≈ 1,296 tokens
- **Tool definitions cost tokens** - on every call, so register only the tools the task needs

### Working out what a feature will cost

<Imagine text={"The chatbot will handle 100,000 conversations a day. Before launch, finance wants the daily cost on one page."} />

Turn token counts into money before you launch. Prices are per million tokens and differ by model (5.1); Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens. A support-bot call with a 3,000-token system prompt, 1,500 tokens of history and a 400-token answer:

| Item | Tokens | Rate | Cost |
|---|---|---|---|
| Input | 4,500 | $2 / 1M | $0.0090 |
| Output | 400 | $10 / 1M | $0.0040 |
| **Per call** | | | **$0.0130** |
| **100,000 calls a day** | | | **≈ $1,300 a day** |

**Prompt caching**, which lets Claude reuse the processed system prompt instead of reading it again on every call (cache reads cost 0.05× base on Sonnet 5.5), cuts that slice from $0.006 to $0.0003 per call, saving about $570 a day. 5.3 covers how.

### Cost levers, in the order to reach for them

<Imagine text={"Finance asks you to halve the AI bill without making the answers worse. Where do you start?"} />

1. **Right-size the model**, with routing for mixed traffic.
2. **Cache** stable prefixes: long system prompts, tool sets, reference documents.
3. **Batch** anything that can wait.
4. **Tune effort** down for simple work.
5. **Shrink the context**: fewer tools, trimmed history, **compaction** (summarising older history, 6.5).

{/* more:5-levers-table */}
| Lever | Saves | Best for | Trade-off |
|---|---|---|---|
| **Smaller model** | Up to ~40× on price | Simple, high-volume jobs (tagging, routing) | Must pass your eval first |
| **Prompt caching** | Up to ~95% on the repeated part | A long system prompt, documents or tools sent every call | First call costs more; the cached part must not change |
| **Batch API** | 50% on everything | Work nobody is waiting for | Results take up to 24 hours |
| **Lower effort** | Output (thinking) tokens | Simple questions | Less depth on hard ones |
| **Smaller context** | Input tokens on every call | Long chats, many tools | Risk of dropping something needed |

They stack: a batch job on Haiku with a cached prompt gets all three discounts.
{/* /more */}

### Latency levers: making replies feel faster

<Imagine text={"Users say the support bot \"feels slow\". Before changing anything, you need to know which kind of slow: waiting for the first word, or waiting for the whole answer?"} />

There are two different waits:

- **Time to first token (TTFT):** how long before *anything* appears.
- **Total time:** how long until the reply is finished. This depends mostly on how many tokens Claude writes, and how fast.

| Lever | Helps | Notes |
|---|---|---|
| **Streaming** (2.3) | How fast it *feels* | Words appear straight away; the total time doesn't change |
| **Shorter output** | Total time | Ask for brevity, set a sensible `max_tokens`; output is the slow part |
| **Lower effort** (5.2) | Total time | Less thinking before the answer |
| **Smaller model** (5.1) | Both | If it still passes your evals |
| **Prompt caching** (5.3) | TTFT | A cached prefix doesn't have to be processed again |
| **Smaller context** (6.5) | TTFT | Fewer input tokens to read |
| **Fast mode** (5.2) | Total time on supported Opus models | Same quality, higher price |
| **Batch API** (5.4) | Nothing: it's *slower* (up to 24 h) | Only for work nobody is waiting for |
