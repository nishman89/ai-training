## 5.1 Choosing a model

<ExamRef section="5.1" />







### In plain English

Picking which Claude to use, and not wasting money. Bigger models are smarter but cost more and respond more slowly. Sorting emails into "billing" or "tech" is easy, so use Haiku; reviewing a tricky contract is hard, so use a bigger model. The two big money-savers are **caching** (re-sending the same long document is far cheaper the second time) and **batching** (send a pile of jobs to run overnight at half price).

### The current lineup

All four current models have a 1M-token context window, 128K max output and adaptive thinking.

| Model | API ID | Input / output per 1M tokens | Default effort | Speed | Best for |
|---|---|---|---|---|---|
| Fable 5.2 | `claude-fable-5-2` | $8 / $40 | high | Moderate | Hardest reasoning, long-horizon agents |
| Opus 5.5 | `claude-opus-5-5` | $4 / $20 | medium | Moderate | Long-running agentic coding and knowledge work |
| Sonnet 5.5 | `claude-sonnet-5-5` | $2 / $10 | high | Fast | The balanced default |
| Haiku 5.5 | `claude-haiku-5-5` | from $0.10 / $0.50 | medium | Fastest | Classification, extraction, routing, high volume |

Prices and IDs change: check the [models overview](https://platform.claude.com/docs/en/models-overview) when you build. Use the Models API (`GET /v1/models`) to read limits and capabilities in code, and read its `line` field rather than parsing the ID.

### Pick a starting point, then let your test results decide

Anthropic's guidance offers two starting points. **Capability-first:** start on Opus 5.5 (the recommendation for most workloads), then lower effort or move down a tier as the workflow matures. **Efficiency-first:** start on Haiku 5.5 for prototypes, tight latency, cost-sensitive or high-volume simple work, and move up only when tests show a specific gap. Either way, **adjust effort before switching models**, and move only on measured results from your own test set. Fable 5.2 is for when evals still fall short at the highest effort levels.

### Routing: a default plus an override

You don't have to use one model for everything. The common production pattern sends most traffic to a balanced default and routes specific requests up or down by task type, input length or a difficulty classification.

- **Handles well** - matching each workload to the cheapest model that meets its quality bar
- **Costs** - a classification step and a second model path to maintain
- **Skip it when** - traffic is uniform at one quality bar: pin one model

## 5.2 Reasoning and effort

<ExamRef section="5.2" />







### Two separate decisions

Choosing the model and choosing how much it reasons are set separately. Current models use **adaptive thinking**: they decide when to think and how much. You tune depth with `effort` (low → max) rather than a fixed token budget. Thinking content is omitted by default on the newest models; ask for a summarised display when you need to show it.

<Compare middle="vs" caption="Where reasoning earns its cost (Exam guide: LLM Fundamentals)" columns={[
  { title: 'Worth it', sub: 'raise effort', points: ['Multi-step debugging', 'Planning an agent task', 'Complex analysis or maths', 'Ambiguous requirements'] },
  { title: 'Wasted', sub: 'lower effort', points: ['Lookups', 'Classification and routing', 'Simple extraction', 'Reformatting'] },
]} />

More thinking means more output tokens, so more cost and latency. In a multi-turn conversation, pass thinking blocks back unchanged (Domain 6).

## 5.3 Prompt caching

<ExamRef section="5.3" />







### How it works

Prompt caching stores the processing of a stable **prefix** of your request so the next request with the same prefix reads it back instead of recomputing it. The prefix is built in a fixed order: **tools → system → messages**, up to and including the block marked with `cache_control`.

Think of a barista who remembers your usual order: the first visit takes longer to set up, and every repeat is quick and cheap.

- **Automatic** - one top-level cache_control; the breakpoint moves forward as the conversation grows · best for multi-turn chat
- **Explicit** - cache_control on specific blocks, up to 4 breakpoints · best when sections change at different rates (tools rarely, RAG context daily)

### What it costs

| Operation | Price vs base input |
|---|---|
| Cache write, 5-minute TTL (default) | 1.25× |
| Cache write, 1-hour TTL | 2× |
| Cache read | 0.1× on most models; **0.05× on Opus and Sonnet 5.5**; **0.025× on Fable** |

Writes cost **more** than normal input, so caching pays only when reads outnumber writes. The 5-minute lifetime refreshes free on every hit. These multipliers stack with the Batch API discount. The minimum cacheable prefix is 512 tokens on the 5.x models; shorter prompts silently don't cache.

### What breaks the cache

The prefix must be **byte-identical**. A change at one level invalidates that level and everything after it.

<WhenThen whenLabel="If you change…" thenLabel="…this is invalidated" rows={[

  { when: 'web search or citations on/off', then: 'System and messages' },
  { when: 'tool_choice, or add/remove images', then: 'Messages only' },
  { when: 'a timestamp or user name near the top', then: 'Everything after it, on every call (move it below the last breakpoint)' },
]} />

### Proving it works

Read the usage fields: `total input = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`. Note that `input_tokens` counts only the uncached tokens **after** the last breakpoint. If both cache fields are 0, the prefix was too short or not identical.

<CodeSwitch>

```java
MessageCreateParams params = MessageCreateParams.builder()
    .model(Model.CLAUDE_SONNET_5_5)
    .maxTokens(1024L)
    .systemOfTextBlockParams(List.of(
        TextBlockParam.builder()
            .text(LONG_POLICY_DOCUMENT)                               // stable, reused prefix
            .cacheControl(CacheControlEphemeral.builder().build())    // 5-minute TTL
            .build()))
    .addUserMessage(userQuestion)                                     // changes every call
    .build();

Usage u = client.messages().create(params).usage();
long read  = u.cacheReadInputTokens().orElse(0L);
long write = u.cacheCreationInputTokens().orElse(0L);
// first call: write > 0. Repeat within 5 minutes: read > 0. Both 0: not cached.
```

```python
msg = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": LONG_POLICY_DOCUMENT,                    # stable, reused prefix
        "cache_control": {"type": "ephemeral"},         # 5-minute TTL
    }],
    messages=[{"role": "user", "content": user_question}],   # changes every call
)

read = msg.usage.cache_read_input_tokens or 0
write = msg.usage.cache_creation_input_tokens or 0
# first call: write > 0. Repeat within 5 minutes: read > 0. Both 0: not cached.
```

<div slot="answer">

The first line changes on every call, so the prefix is never identical and every call writes a new cache entry (paying 1.25× instead of 0.1×). Move the stable policy text first, put the breakpoint after it, and put the date and user name in a later block or in the user message.

## 5.4 Batch processing

<ExamRef section="5.4" />







### The Message Batches API

For work that doesn't need an answer now (overnight classification, dataset backfills, eval runs, scheduled reports), the Message Batches API processes requests asynchronously at **50% off** input and output.

<Flow caption="A batch job: submit, poll, collect (Exam guide: Cost and Token Management)" steps={[
  { title: 'Submit', sub: 'up to 100,000 requests or 256 MB' },
  { title: 'Get a batch ID', sub: 'returned immediately' },
  { title: 'Poll for status', sub: 'often < 1 h, up to 24 h' },
  { title: 'Download results', sub: 'one per request' },
]} />

<MythReality rows={[
  { myth: 'Batch gives faster answers for big jobs', reality: 'It trades latency for cost: timing is non-deterministic, up to 24 hours. Never use it when a user is waiting' },
  { myth: 'Batch results are lower quality', reality: 'Same models and quality; only the scheduling and price differ' },
  { myth: 'A loop of synchronous calls is a batch job', reality: '"Serialisation with extra steps": you pay full price and still block. Use the Batches API, or the async client for concurrency' },
]} />

For high volume that **does** need prompt answers, use the async client (`client.async()`, returning `CompletableFuture<Message>`) for concurrency without blocking threads.

<Gotcha

## 5.5 Token budgets

<ExamRef section="5.5" />







### Everything is tokens

The context window holds the system prompt, the whole conversation, injected documents, tool definitions, every tool result and the model's output. Two edge behaviours: an input larger than the window is **rejected** with a validation error; a reply that runs out of room **stops early** with a stop reason telling you so.

In development the window rarely fills because test inputs are short. In production, longer inputs and more turns fill it fast, so measure real traffic.

- **Count before sending** - the token counting endpoint measures a request before you send it, so you can gate or trim instead of failing
- **Images cost tokens** - roughly (width × height) / 784: a 1,000 × 1,000 px image ≈ 1,296 tokens
- **Tool definitions cost tokens** - on every call, so register only the tools the task needs

### Cost levers, in the order to reach for them

1. **Right-size the model**, with routing for mixed traffic.
2. **Cache** stable prefixes: long system prompts, tool sets, reference documents.
3. **Batch** anything that can wait.
4. **Tune effort** down for simple work.
5. **Shrink the context**: fewer tools, trimmed history, compaction (Domain 6).
