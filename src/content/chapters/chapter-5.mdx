## 5.1 How tool use works

### In plain English

This domain is about letting Claude **do** things, not just talk. You describe a function ("get_order_status takes an order ID"). Claude replies "please run get_order_status with A-1234", **your** code runs it and sends back the answer, and Claude continues. **MCP** is a standard way to package tools so they plug into any Claude app, like USB for tools.

**Real-life example:** connect the GitHub MCP server once, and Claude can search code and open issues in any app that supports MCP.

### The round trip

<Flow caption="Claude never runs your tools: it asks, your code runs them" steps={[
  { title: 'Send tools + question', sub: 'name, description, input_schema' },
  { title: 'stop_reason: tool_use', sub: 'tool_use block: name, id, input' },
  { title: 'Your code runs it', sub: 'Claude is not connected meanwhile' },
  { title: 'Send tool_result', sub: 'same tool_use_id' },
  { title: 'Claude continues', sub: 'answer or another tool' },
]} />

A tool conversation is built from typed blocks: `text`, `tool_use`, `tool_result` and (with thinking) `thinking`. The API enforces the pairing: each `tool_use` must be answered by a `tool_result` with the matching ID in the next user turn. Most bugs sit on that boundary between what Claude owns and what your code owns.

<CodeSwitch title="One tool call, answered">

```java
// Claude asked for a tool: echo its turn, then answer every tool_use with a tool_result
history.add(reply.toParam());
List<ContentBlockParam> results = new ArrayList<>();
for (ContentBlock block : reply.content()) {
    block.toolUse().ifPresent(use -> {
        try {
            String out = orders.status(use.input().toString());
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id()).content(out).build()));
        } catch (Exception e) {
            results.add(ContentBlockParam.ofToolResult(ToolResultBlockParam.builder()
                .toolUseId(use.id())
                .content("Order service unavailable: " + e.getMessage())
                .isError(true)                          // tell Claude it failed
                .build()));
        }
    });
}
history.add(MessageParam.builder().role(MessageParam.Role.USER).contentOfBlockParams(results).build());
```

```python
# Claude asked for a tool: echo its turn, then answer every tool_use with a tool_result
history.append({"role": "assistant", "content": reply.content})
results = []
for block in reply.content:
    if block.type != "tool_use":
        continue
    try:
        out = orders.status(**block.input)
        results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
    except Exception as e:
        results.append({
            "type": "tool_result", "tool_use_id": block.id,
            "content": f"Order service unavailable: {e}",
            "is_error": True,                           # tell Claude it failed
        })
history.append({"role": "user", "content": results})
```

## 5.2 Designing tools Claude picks correctly

### The description is the interface

Claude picks a tool by reasoning over every registered description in the context of the conversation. When two descriptions look alike, it has no reliable signal and picks on surface details.

- **Say when NOT to use it** - one sentence of exclusion gives a decision boundary · "Look up an order's status. Do not use for refunds."
- **Merge what you can't separate** - two overlapping tools → one tool with a type parameter
- **Use the schema** - enum for fixed values, required only for truly required fields, clear parameter descriptions
- **Don't over-tool** - every definition costs tokens on every call, and overlap makes selection erratic · start minimal

### Errors go back to Claude

Return failures as a `tool_result` with `is_error: true` and a useful message, so the model can retry, try another approach, ask the user or stop. An empty result is read as valid data ("no orders found"), and the model carries on confidently.

  title={"\"Sorry, that item is out of stock\""}
  scenario={"The inventory API times out, and the tool catches the exception and returns an empty list."}
  gotcha={"Claude reads the empty result as real data and confidently tells a customer the item is unavailable. A lost sale and a false statement."}
  fix={"Return `is_error: true` with a message (\"inventory service timed out\") so Claude can retry, apologise, or hand off."}

## 5.3 Client tools, server tools and tool_choice

### Who runs it?

<VsPair
  left={{ title: 'Client tools', meaning: 'Defined by you (or Anthropic-schema tools like bash and text_editor) and run in YOUR application.', example: 'Response stops with stop_reason tool_use; you run it and send tool_result.' }}
  right={{ title: 'Server tools', meaning: 'Run on Anthropic\'s side, e.g. web search, web fetch, code execution. Declared in the request; nothing to implement.', example: 'May cost extra per use. A long server loop returns pause_turn.' }}
/>

| `tool_choice` | Meaning |
|---|---|
| `auto` (default) | Claude decides whether to call a tool |
| `any` | Must call some tool |
| `tool` + name | Must call that specific tool (forced: handy for structured output) |
| `none` | Must not call tools |

Add `disable_parallel_tool_use: true` to allow at most one tool call per turn. When a server-tool loop hits its iteration cap the response has `stop_reason: pause_turn`. Resend the conversation as it is; don't add a "please continue" message.

<SectionSummary points={[
  "Client tools run in your app; server tools (web search, web fetch, code execution) run on Anthropic's side.",
  "`tool_choice`: auto, any, tool (forced) or none; `disable_parallel_tool_use` allows one call per turn.",
  "`pause_turn` means a server-tool loop paused: resend as it is, no \"continue\" message.",
]} />

## 5.4 The Model Context Protocol

### Why MCP

Wiring a tool straight into each app means three apps need three integrations. MCP moves the tool into a **server** that any MCP client (Claude Code, Claude apps, your own app) can attach to, so you build the integration once. Think JDBC: one driver standard, many databases and clients.

<Hub center="MCP server" caption="An MCP server exposes three kinds of capability" items={['Tools: actions the model calls', 'Resources: read-only data the client fetches', 'Prompts: templates the user invokes']} />

### Transports

<VsPair
  left={{ title: 'stdio', meaning: 'The client launches the server as a local subprocess and talks over stdin/stdout. Runs on ONE machine.', example: 'A personal script, a local database tool, a dev server.' }}
  right={{ title: 'Streamable HTTP', meaning: 'The server runs remotely; clients connect to its URL over the network.', example: 'A shared team server or a hosted integration.' }}
/>

SSE is the older remote transport and isn't recommended for new servers. Each connected server's tool definitions cost context, so connect only the servers a task needs. Claude Code defers loading tool definitions until they're needed.

<Gotcha
  title={"The shared server only one person could use"}
  scenario={"A developer adds a stdio MCP server to the committed `.mcp.json`, pointing at a script on their laptop."}
  gotcha={"It works for them. For everyone else Claude Code fails to start the server, because the script and runtime only exist on one machine."}
  fix={"Host shared servers over HTTP (project or enterprise scope); keep stdio servers in local or user scope, or bundle the script so every machine has it."}
/>

## 5.5 MCP scope, permissions and auth

### Scope in Claude Code

| Scope | Stored in | Who gets it | Right for |
|---|---|---|---|
| Local | `~/.claude.json` under the project | Only you, in this project | A tool tied to one project |
| User | Your personal Claude settings | Only you, every project | Your own local utilities |
| Project | `.mcp.json` at the repo root (committed) | Everyone who clones the repo | Team-wide servers |
| Enterprise | Managed settings, set by an admin | Everyone in the organisation | Internal services, security tooling |

Transport and scope are separate decisions with linked consequences: a **stdio server in `.mcp.json` looks shared but isn't**, because it only runs where it's installed. A shared team server needs HTTP plus project or enterprise scope.

### Per-tool permissions

Connecting a server exposes its whole tool list. Permission rules can target one tool by name: `mcp__server__tool`. For example, allow `mcp__github__create_issue` without a prompt while other GitHub tools still prompt, or deny a write tool while read tools stay available. **A deny on one tool beats an allow on the server.** Through the API's **MCP connector** (remote servers called straight from the Messages API), an `mcp_toolset` can enable or disable each tool: a permission rule decides "can it run", enabling decides "can the model see it".

### Authentication

<MythReality rows={[
  { myth: 'Put the API key in .mcp.json so teammates can connect', reality: 'The key goes into git history for good: rotate it. Reference an environment variable; the file holds only the server address' },
  { myth: 'OAuth that works in staging will work in production', reality: 'Redirect URIs are registered per host: add production\'s before go-live' },
]} />

- **User identity (SaaS, cloud)** - OAuth, browser sign-in · audit with a PostToolUse hook
- **Service identity (internal API)** - API key in an environment variable or secrets manager · never in committed config
- **Local (filesystem, local DB)** - stdio, no network auth · deny rules enforce path access
