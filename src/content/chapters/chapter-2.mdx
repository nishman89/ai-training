## 2.1 The Messages API

<ExamRef section="2.1" />

### In plain English

This domain is about how your program talks to Claude.

- **The API:** your code reaches Claude through an **API** (application programming interface), a web address your code sends requests to, like any REST service. The main one is the **Messages API**.
- **The request:** one HTTP request with some settings and the conversation so far.
- **The reply:** Claude's answer, a note saying why it stopped, and an itemised bill.
- **Tokens:** everything is measured and billed in **tokens**, chunks of text of about ¾ of a word (more in 2.2).

Most of the rest of this guide builds on this one request: its fields, how to handle the reply, and how to send many requests.

**Real-life example:** a bank's help chat. Behind it, the bank's Java service sends each customer question to Claude and shows the answer. When 10,000 customers ask at once, some calls get a "slow down" error (429), and the service should wait and retry instead of crashing. That's Domain 2.

### Anatomy of a request

A request to `POST /v1/messages` needs three fields and two headers. Everything else is optional.

| Part | What it is | Required? |
|---|---|---|
| `x-api-key` header | Your secret key; proves who you are and who pays | Yes |
| `anthropic-version` header | Which version of the API you're writing against, as a date (the current docs' examples use `2026-10-21`); the SDKs set it for you. Beta features add an `anthropic-beta` header | Yes |
| `model` | Which Claude does the work, e.g. `claude-sonnet-5-5` | Yes |
| `max_tokens` | Ceiling on the reply length, in tokens | Yes |
| `messages` | The conversation: alternating `user` and `assistant` turns | Yes |
| `system` | Standing instructions for the whole conversation (a top-level field, **not** a role) | No |
| `tools`, `tool_choice` | Functions Claude may ask you to run (Domain 8) | No |
| `stream` | Receive the reply piece by piece as **server-sent events** (a standard way for a server to push data over one open HTTP connection; see 2.3) | No |

**What the request actually looks like.** Here is one complete request, as it goes over the wire: the headers first, then the JSON body.

```http
POST https://api.anthropic.com/v1/messages
x-api-key: sk-ant-...your key...
anthropic-version: 2026-10-21
content-type: application/json
```

```json
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,
  "system": "You are Acme Broadband's support assistant. Be brief and friendly.",
  "messages": [
    { "role": "user", "content": "My router light is flashing. What colour should it be?" },
    { "role": "assistant", "content": "It should be solid white. What colour is it flashing?" },
    { "role": "user", "content": "Red." }
  ]
}
```

Reading it:

- **The two required headers** are `x-api-key` and `anthropic-version`. `content-type` is the usual "this body is JSON" header that any JSON request carries.
- **The three required fields** are `model`, `max_tokens` and `messages`. Delete `system` and the request still works.
- **`system` sits at the top level**, next to `model`, not inside `messages`.
- **`messages` holds the whole conversation so far**, not just "Red.". The earlier user and assistant turns are resent, because the API remembers nothing between calls.
- **The SDKs build exactly this for you.** You never write the headers by hand.

The API is **stateless**: it keeps no conversation. Your app stores the history and resends it every turn, which is why long chats get slower and pricier.

### Where each part of the request comes from

Nothing in a request arrives by magic: every part is supplied by you or your code.

| Part | Who supplies it | Where it comes from |
|---|---|---|
| API key | You, once | Created in the **Claude Console** (platform.claude.com, Anthropic's website for developers), then stored as the `ANTHROPIC_API_KEY` environment variable. The SDK reads it from there (Domain 7 covers keeping it safe) |
| `model`, `max_tokens` | You, when you build the feature | Usually in your app's configuration |
| `system` | You: you write the instructions | Often a text file in your project (see the next example) |
| `tools` | You: you describe your functions | Defined in your code, sent with every request (Domain 8) |
| `messages` | **Your code**, on every call | The person's new message, plus the earlier turns your app saved |

**How the `messages` array gets built.** The person using your app never sees or sends it. Take a support chat on a website:

1. The customer types *"Red."* into the chat box and presses Send.
2. Their browser sends just that text to **your** server, like any web form. Claude isn't involved yet.
3. Your server loads the earlier turns of this chat from wherever you saved them (a database, the session), and adds the new text as a `user` turn.
4. Your server calls Claude with the whole list.
5. Your server saves Claude's reply as an `assistant` turn, so it's included next time, and sends the reply text back to the browser.

So `"user"` means "from the human side" and `"assistant"` means "something Claude said earlier". **Your code adds both.**

<CodeSwitch title="Where the messages array comes from: a chat endpoint" fold>

```java
// ── Setup: where the names below come from ──
// Imports: com.anthropic.client.*, com.anthropic.client.okhttp.*, com.anthropic.models.messages.*, java.util.*, java.util.stream.Collectors
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // one per app; reads ANTHROPIC_API_KEY
// chatStore: your storage for each chat's history (a database table, Redis...): load(id) and save(id, history)
// ChatRequest: small records for the JSON the browser sends and receives
// ── The example ──
@PostMapping("/chat")
ChatAnswer chat(@RequestBody ChatRequest req) {                      // step 2: only the new text arrives
    List<MessageParam> history = chatStore.load(req.chatId());       // step 3: the earlier turns you saved
    history.add(MessageParam.builder()
        .role(MessageParam.Role.USER).content(req.text()).build()); //         + the new user turn

    Message reply = client.messages().create(MessageCreateParams.builder()   // step 4: call Claude
        .model(Model.CLAUDE_SONNET_5_5).maxTokens(1024L)
        .system("You are Acme Broadband's support assistant.")
        .messages(history)                                          // the whole conversation, every time
        .build());
    String answer = reply.content().stream().flatMap(b -> b.text().stream())
        .map(TextBlock::text).collect(Collectors.joining());

    history.add(reply.toParam());                                   // step 5: save Claude's turn for next time
    chatStore.save(req.chatId(), history);
    return new ChatAnswer(answer);                                  // the browser shows this
}
```

```python
client = anthropic.Anthropic()            # one client per app; reads ANTHROPIC_API_KEY
# chat_store: your storage for each chat's history (a database table, Redis...): load(id) and save(id, history)

@app.post("/chat")
def chat(chat_id: str, text: str):                  # step 2: only the new text arrives

    history.append({"role": "user", "content": text})          # + the new user turn

    reply = client.messages.create(                 # step 4: call Claude
        model="claude-sonnet-5-5", max_tokens=1024,
        system="You are Acme Broadband's support assistant.",
        messages=history,                           # the whole conversation, every time
    )
    answer = "".join(b.text for b in reply.content if b.type == "text")

    history.append({"role": "assistant", "content": answer})   # step 5: save Claude's turn for next time
    chat_store.save(chat_id, history)
    return {"answer": answer}                       # the browser shows this
```

```typescript
    system: "You are Acme Broadband's support assistant.",
    messages: history,                              // the whole conversation, every time
  });
  const answer = reply.content.map((b) => (b.type === 'text' ? b.text : '')).join('');

  history.push({ role: 'assistant', content: reply.content });   // step 5: save Claude's turn for next time
  await chatStore.save(chatId, history);
  res.json({ answer });                             // the browser shows this
});
```

#### 3. What actually goes over the wire

The SDK turns that into one HTTPS POST to `https://api.anthropic.com/v1/messages`, with your key in the `x-api-key` header and this JSON body:

```json
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,
  "system": "You are Acme's support assistant. Only answer about Acme orders...",
  "messages": [
    { "role": "user", "content": "Where's my order A-1234?" }
  ]
}
```

#### 4. What comes back

```json
{
  "id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "type": "message",
  "role": "assistant",
  "model": "claude-sonnet-5-5",
  "content": [
    { "type": "text", "text": "I can help with that. Could you confirm the email on the order?" }
  ],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 1840, "output_tokens": 18,
             "cache_creation_input_tokens": 0, "cache_read_input_tokens": 0 }
}
```

Your code shows the `text` block to the customer (pick blocks by `type`, never `content[0]`: on current models a reply can start with `thinking` blocks), checks `stop_reason`, and can log `usage` to track cost. On the customer's next message, your code sends the system prompt **again**, plus both earlier turns: the API remembers nothing.

### Reading the response

This is the one place that covers everything you get back from a call. Other sections link here.

#### Every call ends in one of three ways

<Compare caption="The three outcomes of any call: check them in this order" columns={[

  { title: '2. A reply, but not finished', sub: 'HTTP 200', points: ['stop_reason is max_tokens, refusal, pause_turn, tool_use or model_context_window_exceeded', 'No exception: easy to miss', 'Your code must act on it'] },

The trap: **outcome 2 looks like success.** The HTTP status is 200, nothing is thrown, and the text may look fine until it stops mid-sentence or turns out to be a tool request. So always check `stop_reason`, the way you'd check a program's exit code.

#### `content`: what Claude said

`content` is a list, and each block has a `type`:

| Block type | What it holds | What your code does with it |
|---|---|---|
| `text` | The written answer | Show it, or parse it |
| `thinking` | Claude's reasoning before answering (6.4) | Usually ignore it; keep it unchanged in the history during tool use |
| `tool_use` | A request to run one of your tools: a name, an ID and the inputs (8.1) | Run the tool, send back a `tool_result` |
| `server_tool_use` and its result | A tool Anthropic ran for you, such as web search (8.3) | Nothing to run; the results are already there |

**The rule: pick blocks by `type`, never by position.** Code that reads `content[0].text` breaks as soon as a `thinking` or `tool_use` block comes first.

#### `stop_reason`: why it stopped

| `stop_reason` | What happened | Example | Your code should… |
|---|---|---|---|
| `end_turn` | Claude finished naturally | A normal chat answer | Use the answer |
| `max_tokens` | It hit your `max_tokens` cap mid-reply | A JSON list of 150 items stops at item 61 | Treat it as **incomplete**: raise the cap, ask for less, or continue. Never parse it as complete JSON |
| `stop_sequence` | It wrote one of your `stop_sequences` | It wrote `</answer>`, so it stopped (2.2) | Use the text before the marker |
| `tool_use` | It wants you to run a tool | "Run `get_order` with `A-1234`" | Run it and send a `tool_result` (8.1); this is how the agent loop continues (1.3) |
| `pause_turn` | A long server-tool job (e.g. several web searches) was paused | A research question needing many searches | Send the conversation back as it is, and it carries on (8.3) |
| `refusal` | It declined for safety reasons | A request for something harmful | Read `stop_details` (it says why), log it, show a polite message or try a fallback model. Don't resend unchanged |
| `model_context_window_exceeded` | The reply filled the whole **context window** (input plus output, 6.5) | A huge document plus a long answer | Treat it as truncated, like `max_tokens` |

#### `usage`: the itemised bill

Every reply says exactly how many tokens it used. Anthropic bills from these same numbers.

| Field | What it counts | Price on Sonnet 5.5 |
|---|---|---|
| `input_tokens` | Input that was **not** read from or written to the cache: usually the newest part of the conversation | $2 per million |
| `cache_creation_input_tokens` | Input written to the cache on this call (5.3) | 1.25× = $2.50 per million |
| `cache_read_input_tokens` | Input read back from the cache | 0.05× = $0.10 per million |
| `output_tokens` | Everything Claude wrote, **including thinking** | $10 per million |

**The total input is the sum of the first three.** `input_tokens` alone is *not* everything you sent once caching is on.

**Worked example**, using the reply above:

| | Tokens | Rate | Cost |
|---|---|---|---|
| Uncached input | 312 | $2 / M | $0.000624 |
| Cache read | 9,800 | $0.10 / M | $0.00098 |
| Output | 145 | $10 / M | $0.00145 |
| **Total** | 10,112 input + 145 output | | **≈ $0.0031** |

Without the cache, the same 10,112 input tokens would cost about $0.0202, so caching cut the input cost by about 92%.

**Reading `usage` to find problems:**

| You see | It means |
|---|---|
| `input_tokens` grows on every turn of a chat | The history is growing: you're resending it all (expected, but watch it, 6.5) |
| `cache_read_input_tokens` is 0 on repeated calls | The cache isn't being hit: something at the start changes each time (5.3) |
| `cache_creation_input_tokens` is high on every call | You're paying to write the cache and never reading it back |
| `output_tokens` equals your `max_tokens` | The reply was cut off: check `stop_reason` |
| `output_tokens` is far larger than the visible text | Most of it was thinking: consider lower effort (5.2) |

#### Where errors fit

If a call fails (outcome 1), there's no `content`, `stop_reason` or `usage` at all, just an error with a status code. 2.4 covers what each error means, which to retry and how.

## 2.2 Request parameters, explained

<ExamRef section="2.2" />
<Imagine text={"Acme's chatbot works, but some answers are cut off mid-sentence and the bill is higher than expected. The cause is in the handful of settings sent with every request."} />

### What this section is about

Every request you send to Claude is a small JSON object of **settings** (also called **parameters**): which model, how long the reply may be, the instructions, the conversation, and a few optional dials. Section 2.1 showed that a request exists. This section takes the settings **one at a time**: what each does, what happens if you get it wrong, and how to set it in code.

Here's a typical request body. Each line is one setting, and each gets its own heading below:

```json
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,
  "system": "You are Acme Broadband's support assistant. Be brief.",
  "messages": [
    { "role": "user", "content": "My router light is red. What do I do?" }
  ],
  "stop_sequences": ["</answer>"]
}
```


The first three plus `messages` are what you'll set on almost every call. Only `model`, `max_tokens` and `messages` are required; everything else is optional.

### Think of a call as a job for a contractor

You pick the contractor (`model`), hand over the standing brief (`system`) and the case file so far (`messages`), and cap the billable hours (`max_tokens`). You get back the work (`content`), a note on why they stopped (`stop_reason`) and an invoice (`usage`).

### Tokens

<Imagine text={"Acme's finance team asks why one chatbot conversation cost 3p and another 40p, when both were \"one chat\". The difference is how much text went in and came out, measured in **tokens**."} />

A token is the unit Claude reads, writes and bills in: a chunk of text of roughly ¾ of an English word. Think of a taxi meter that ticks per chunk of road. Your prompt, the whole history, tool definitions, tool results and images all tick the **input** meter. Everything Claude writes ticks the **output** meter, which costs 5× more per token on every current model.

{/* more:2-tokens */}
**Example:** the sentence *"Please summarise this invoice."* is about 6–8 tokens. A one-page email is roughly 500 tokens; a 300-page book is roughly 100,000. You never count by hand: the API reports exact numbers in `usage` on every reply, and 5.5 shows how to count before sending.

**Picturing token counts:** at about ¾ of a word per token, and roughly 400 to 500 words per page:

| Tokens | ≈ Words | ≈ Pages | Typical example |
|---|---|---|---|
| 500 | 375 | 1 | An email |
| 5,000 | 3,750 | 8–10 | A long system prompt, or a short report |
| 30,000 | 22,500 | 45–60 | A company policy handbook |
| 100,000 | 75,000 | 150–300 | A book |

**When a question gives a size in tokens** ("a 30,000-token policy manual"), it's hinting that a big block of text is being sent. Ask: is it the **same every time**? Think caching (5.3). Is only **part of it** needed for each question? Think retrieval, RAG (6.5).

To see where the tokens in a reply are reported, see `usage` in 2.1; to turn them into a daily bill, see the worked example in 5.5.
{/* /more */}

### model

<Imagine text={"Acme's ticket tagger and its fault-finding agent use the same model. For the tagger it's overkill; the agent struggles. Each job needs a different size of Claude."} />

The `model` field chooses which Claude does the work. Think of choosing junior, mid-level or senior staff: seniors are better, but slower and more expensive.

For this field, you only need to know that the value is a model ID such as `claude-sonnet-5-5`. The rest lives elsewhere:

- **Which model to choose**, with prices and the Haiku / Sonnet / Opus / Fable trade-offs: **5.1**
- **How hard it thinks** (effort): **5.2**
- **Pinning the exact version** for production, and upgrading safely: **2.5**



### max_tokens

<Imagine text={"You ask Claude for 150 product descriptions in one JSON list, and the reply stops halfway through item 61. No error, just a broken list."} />

`max_tokens` is a hard ceiling on how many tokens Claude may **write** in this reply. It isn't a target (Claude doesn't try to fill it), it doesn't limit what you send, and you only pay for what's actually written. Think of a word limit on an essay.

If Claude reaches the limit mid-sentence, the reply is simply cut off and `stop_reason` is `max_tokens`. There's **no error**: just truncated text or broken JSON. Size it to the longest good answer: about 300 tokens for a label plus a reason, 1,024–4,096 for chat, and much more (with streaming) for long documents or code.

### stop_sequences, temperature and effort

<Imagine text={"Acme's marketing team wants ten **different** names for a new tariff. The billing team wants the **same** category label every time. The fault agent should think hard; the FAQ bot shouldn't. Those are three different dials."} />

- **stop_sequences** - strings that end the reply as soon as Claude writes them; stop_reason becomes stop_sequence · e.g. stop at a closing answer tag so no commentary follows
- **temperature / top_p** - randomness settings that older models accepted, low = predictable · on the newest models you can't set them: steer with the prompt and test properties, not exact wording
- **effort** - how hard the model thinks before answering · current models decide for themselves how much to think (**adaptive thinking**), and effort steers it: low for sorting an email into a category, high for a tricky bug · more thinking = more output tokens, cost and latency

{/* more:2-dials */}
**The dials side by side:**

| Setting | What it controls | Turn it… | Acme example | On current models |
|---|---|---|---|---|
| `max_tokens` | The longest the reply may be | Up for long outputs | 4,096 for a detailed answer | Required on every request |
| `stop_sequences` | Text that ends the reply immediately | Set it when you want nothing after a marker | Stop at `</answer>` | Works as normal |
| `temperature` | How varied word choices are (0 to 1) | Low for consistency, high for variety | Same label every time vs ten tariff names | Can't change it: Opus 5.5 and Sonnet 5.5 reject non-default values |
| `top_p` | A different way to limit variety | Rarely touched | | Same as temperature |
| `effort` | How hard Claude thinks before answering | Low for simple jobs, high for hard ones | Low for the FAQ bot, high for the fault agent | The main dial for speed, cost and depth |
{/* /more */}

{/* more:2-temp */}
#### Temperature, explained

When Claude writes, it picks each next word from a ranked list of likely options. **Temperature** controls how adventurous that pick is, on a scale from 0 to 1.

- **Low (close to 0):** it almost always takes the most likely word. Ask *"Suggest a name for a coffee shop"* ten times and you get nearly the same answer every time.
- **High (1, the default):** it sometimes takes less likely words. The same question gives ten different names.

**top_p** does a similar job a different way: it only lets Claude choose from the most likely words that together add up to, say, 90% of the probability.

**On the newest models you don't set either.** Opus 5.5 and Sonnet 5.5 reject any value except the default, so you steer variety through the prompt instead: *"Give one short name"* for consistency, *"Give five names that are very different from each other"* for variety. And because answers vary, your tests check **properties** (is it under 20 characters? does it avoid the word "coffee"?) rather than exact text.

A **stop sequence** is a piece of text that ends the reply the moment Claude writes it. Useful when you ask for an answer inside a tag and want nothing after it.

## 2.3 Streaming

<ExamRef section="2.3" />
<Imagine text={"Customers stare at an empty chat box for eight seconds while a long answer is generated, and some think it's broken. You want the words to appear as they're written, like someone typing."} />

### When to stream

**Streaming** sends the reply piece by piece as it's written, like watching a live broadcast instead of waiting for the recording. Use it for chat screens and long outputs. Skip it for short background jobs where nobody is watching: it means extra code (you assemble the message yourself) for no benefit.

**How the words reach the user's screen:** Claude streams to **your server**, not to the user. Your server passes each piece on to the browser as it arrives (usually over its own streaming connection), and the chat window adds the words as they come. Your server also collects the pieces, so it can save the complete reply to the history at the end.

<RoleLens dev={"Streaming sends text as server-sent events so the UI updates as it's written. Only commit the message to history once the stream has completed cleanly."} test={"Test the interrupted-stream case: kill the connection mid-reply and check the app doesn't save half an answer or show it as final."} data={"You rarely stream in batch pipelines: you want the whole result. Streaming matters for long outputs on the request path, where it avoids HTTP timeouts."} ba={"Streaming is a UX decision: users see words appear immediately. It makes no difference to cost or quality, so it belongs in the non-functional requirements."} />

### The event sequence

A streamed reply arrives as a series of small, named messages called **events**. Each reply is built from **content blocks** (a text block, a tool request), and the events tell you when each block starts, what to add to it, and when it's finished.

<Flow caption="Server-sent events for one streamed message" steps={[
  { title: 'message_start', sub: 'empty shell' },
  { title: 'content_block_start', sub: 'block type + index' },
  { title: 'content_block_delta', sub: 'append fragment' },
  { title: 'content_block_stop', sub: 'block complete' },
  { title: 'message_delta', sub: 'stop_reason, usage' },
  { title: 'message_stop', sub: 'message is whole' },
]} />

Every event has a `type`. Here's what each one means, in the order they arrive:

| # | Event | What it carries | What your code does |
|---|---|---|---|
| 1 | `message_start` | An empty message shell: `id`, `model`, and `usage` with the **input** token count | Start a new reply |
| 2 | `content_block_start` | A new block at position `index`, and its type (`text`, `tool_use`, `thinking`) | Open a new block |
| 3 | `content_block_delta` | A fragment to add to that block: `text_delta` (words), `input_json_delta` (part of a tool's JSON input) or `thinking_delta` | Append it. Show text to the user as it arrives |
| 4 | `content_block_stop` | Nothing new: that block is complete | Only now is a tool's JSON input complete and safe to parse |
| 5 | `message_delta` | Top-level changes for the whole message: the **`stop_reason`** and the final **`usage.output_tokens`** | Record why it stopped and the final token count |
| 6 | `message_stop` | Nothing new: the message is finished | Save the complete reply to the history |

Steps 2–4 repeat once per block (a reply with thinking, then text, then a tool call has three rounds). You may also see `ping` events, which just keep the connection alive, and an `error` event if something fails mid-stream.

**Easy to get wrong:** the `stop_reason` and final output-token count are **not** in `message_start` (the reply hasn't been written yet) and not in `content_block_stop` (that only closes one block). They arrive in **`message_delta`**, just before `message_stop`.

Here's a short stream as it arrives, slightly trimmed:

```text
event: message_start
data: {"type":"message_start","message":{"id":"msg_01...","model":"claude-sonnet-5-5","content":[],"stop_reason":null,"usage":{"input_tokens":25,"output_tokens":1}}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Your router light"}}
```

<Explain title="Reading it" steps={["`message_start`: the reply begins. `stop_reason` is still `null`, and `usage` shows the input tokens.", "`content_block_start` with `index: 0`: the first block is a text block, empty so far.", "Two `content_block_delta` events: fragments of text. The SDKs assemble these events for you (`text_stream` / `on('text')` for the words, and a final-message helper for the complete reply), so you rarely parse them by hand. But you need to know the order: it's how you know when it's safe to act.

A `tool_use` block's input arrives as JSON fragments, so it isn't valid JSON until its `content_block_stop`. **Never act on a partial block.**

### Interrupted streams

<Imagine text={"A customer's train goes into a tunnel halfway through a reply. The next time they type, the bot fails with a strange error about a tool."} />

A stream *ending* isn't the same as a message *completing*. Only `message_stop` means the message is whole. A common bug: the code saves whatever it has received when its read loop ends. If the connection drops, that saves a half-built reply into the conversation history, and the error only appears on the **next** request.

## 2.4 Errors, retries and rate limits

<ExamRef section="2.4" />
<Imagine text={"Monday, 9am: 10,000 customers report an outage at once. Your service floods Claude with requests, gets \"slow down\" errors and starts failing. Which errors should it retry, how, and which never?"} />

### What an error looks like

When a call fails, there's no reply at all: no `content`, no `stop_reason`, no `usage` (outcome 1 in 2.1). Instead you get an HTTP status code and a small JSON error, and the SDK turns it into an exception.

```http

retry-after: 6
request-id: req_011CQ4ezo8X3cXYEUm1ECQLX

{
  "type": "error",
  "error": { "type": "rate_limit_error", "message": "Number of request tokens has exceeded your per-minute rate limit." },
  "request_id": "req_011CQ4ezo8X3cXYEUm1ECQLX"

```

<Explain title="Reading it" steps={["The **status code** (429) is the category: 4xx means a problem with your request or account, 5xx a problem on Anthropic's side.", "`error.type` (`rate_limit_error`) is the precise kind. Branch on this, or on the SDK's exception class (`RateLimitError`).", "`message` is human-readable. A failed call to Claude is an **API error**. A failure inside one of your own tools is different: it goes back to Claude as a tool result (8.2 compares the two).

### Retriable or terminal?

A **retriable** error might succeed if you wait and send the same request again (the service was busy). A **terminal** error fails every time until you change the request (it was malformed). Ask one question of every failure: could waiting and sending the **same** request succeed?

| Status | `error.type` | Meaning | Retry? |
|---|---|---|---|
| 400 | `invalid_request_error` | Something is wrong with the request itself: a missing field, an invalid value | **No**: fix the request |
| 401 / 403 | authentication / permission | Bad key or no access | **No** |
| 404 / 413 | not_found / request_too_large | Wrong model or path; payload too big | **No** |
| 429 | `rate_limit_error` | Your org hit a rate or spend limit | **Yes**, after `retry-after`. A spend-cap 429 has no `retry-after` and won't clear by waiting |
| 500 / 504 | `api_error` / `timeout_error` | Server-side fault | **Yes**, with **backoff** (waiting longer between each attempt), a limited number of times |
| 529 | `overloaded_error` | Anthropic-wide capacity, not your quota | **Yes**, backoff with **jitter** (a random extra delay, so thousands of clients don't all retry at the same moment) |
| 200 + `refusal` | (not an error) | A content decision by the model | **Not as-is**: read `stop_details`, log it, then surface it or fall back to another model |

### Rate limits

<Imagine text={"A nightly job fires 5,000 requests in its first minute and most are rejected, even though Anthropic isn't down at all."} />

A **rate limit** is a cap on how much you can send to Claude in a given time. Go over it and Anthropic rejects the extra requests with a **429** error until you slow down. It isn't a fault, just a speed limit.

There are three caps, and you hit whichever runs out first:

| Limit | What it counts | Hit it when… |
|---|---|---|
| **RPM**: requests per minute | How many calls you make | You fire thousands of small calls at once |
| **ITPM**: input tokens per minute | How much text you *send* (prompt, documents, history) | Each call carries a long document or a big conversation |
| **OTPM**: output tokens per minute | How much text Claude *writes back* | You ask for long answers in bulk |

Four things to know about them:

- **They're shared.** The limits apply to your whole **organisation** (your company's Anthropic account), separately for each model. Two teams on the same account share one Sonnet allowance.
- **They refill gradually.** Think of a water tank with a tap that fills it steadily, not one that's emptied and refilled on the hour. If your limit is 60 requests a minute, you get roughly one request's worth back every second. A sudden burst of 60 at once can still be rejected (this is called a **token bucket**).
- **They grow over time.** Each account has a **usage tier**. As you spend more with Anthropic, it moves you up a tier, and the limits rise.
- **Caching helps.** On most current models, input read from the prompt cache (see 5.3) doesn't count towards ITPM. So caching a long system prompt lets you send more requests a minute, as well as making each one cheaper.

**Example:** your limit is 400,000 input tokens a minute and every call sends a 20,000-token policy document. That's only 20 calls a minute before you get 429s. Cache the policy, and the cached part no longer counts, so the same limit allows far more calls.

**How you see it in code:** every response carries headers that show how much is left. On a 429, a `retry-after` header says how many seconds to wait.

```http
anthropic-ratelimit-requests-remaining: 12
anthropic-ratelimit-input-tokens-remaining: 38000
anthropic-ratelimit-input-tokens-reset: 2026-11-21T10:15:30Z
retry-after: 4
```
<Explain steps={["`requests-remaining`: how many more calls you can make right now before hitting RPM.", "`input-tokens-remaining`: how much more input you can send before hitting ITPM.", "`…-reset`: when that allowance will be fully refilled.", "`retry-after`: only on a 429. It says to wait 4 seconds before trying again. The SDK reads this for you."]} />


### What the SDK already does

<Imagine text={"Your team wrapped every Claude call in its own 5-attempt retry loop, not knowing the SDK already retries. During a short blip, each request became 15."} />

The official SDKs retry connection errors, 408, 409, 429 and 5xx automatically, **twice by default**, with exponential backoff, honouring `retry-after`. Don't wrap your own retry loop around that: it multiplies attempts. Tune `maxRetries`, then handle what's left.

{/* more:2-retries */}
**What backoff looks like in practice:** attempt 1 gets a 529 → the SDK waits about half a second → attempt 2 gets a 529 → it waits about a second → attempt 3 succeeds. Each wait roughly doubles, with a little randomness (jitter) added. If the response includes a `retry-after` header, the SDK waits exactly that long instead.

**Tuning it:** set retries and a timeout once, when you create the client.

### Absorbing spikes: put a queue in front of Claude

<Imagine text={"Acme receives 10,000 tickets a day, unevenly, and up to 5× more during an outage, exactly when customers are most upset. The business rule: no ticket may ever be lost."} />

If tickets go straight from the website to Claude, a spike means hundreds of calls at once, 429 errors, and, once the SDK's retries run out, **lost tickets**. Retries alone can't fix that, because a request that keeps failing for minutes is eventually given up.

The standard design is a **queue** (a message queue such as SQS, RabbitMQ or Kafka, or a database table used as one) between the intake and the Claude calls:

<Flow caption="A queue absorbs bursts; workers drain it at a rate Claude's limits allow" steps={[
  { title: 'Intake', sub: 'save the ticket, reply \"received\"' },
  { title: 'Queue', sub: 'durable: nothing is lost' },
  { title: 'Workers', sub: 'a fixed number, e.g. 10' },
  { title: 'Claude', sub: '429? back off, retry' },
  { title: 'Done or dead-letter', sub: 'failures kept for a person' },
]} />

- **The queue absorbs the burst.** Tickets wait safely instead of failing; the backlog shrinks once the spike passes.
- **A fixed number of workers** limits calls in flight, so you stay within your rate limits (see the async example below).
- **A ticket leaves the queue only when it's done.** If a worker crashes or Claude keeps failing, the ticket goes back on the queue. After several failed attempts it moves to a **dead-letter queue** for a person to look at, so it's never silently dropped.

**Why the tempting alternatives aren't enough:** a higher rate limit still has a ceiling that a 5× spike can exceed; a bigger context window (many tickets in one call) doesn't absorb bursts and makes parsing fragile; more web servers don't help, because the bottleneck is Claude's throughput, not your front end.

```java
// queue, deadLetters, store: your queue (SQS, RabbitMQ, a database table…), a dead-letter queue for failures, and where results are saved
// triage: your function that makes the Claude call for one ticket

while (true) {
    QueueMessage m = queue.receive();                  // wait for the next ticket
    try {
        String reply = triage(m.body());               // the Claude call (SDK retries 429/529 itself)
        store.save(m.ticketId(), reply);
        queue.delete(m);                               // remove it ONLY after success
    } catch (RateLimitException | InternalServerException e) {
        queue.releaseLater(m, Duration.ofSeconds(30)); // back on the queue: try again later
    } catch (BadRequestException e) {
```

```python
        reply = triage(m.body)                          # the Claude call (SDK retries 429/529 itself)
        store.save(m.ticket_id, reply)
        queue.delete(m)                                 # remove it ONLY after success
    except (anthropic.RateLimitError, anthropic.InternalServerError):
        queue.release_later(m, seconds=30)              # back on the queue: try again later
    except anthropic.BadRequestError as e:
        dead_letters.add(m, str(e))                     # won't succeed by retrying: a person looks at it
        queue.delete(m)
```

### Calling Claude from async code: limit how many at once

<Imagine text={"A backfill script fires all 5,000 requests at once using async code. Most fail with 429 errors in the first second, and the retries make it worse."} />

**Async** (asynchronous) code lets one program wait on many network calls at the same time, instead of one after another. Each SDK has an async client for this: `AsyncAnthropic` in Python, and the normal client in TypeScript, where every call returns a promise. Async isn't the same as *unlimited*, though. Cap how many calls are **in flight** at once, so you stay inside your rate limits.

<CodeSwitch title="Run many calls at once, at most 10 at a time" fold>

```java
// ── Setup: where the names below come from ──
// Imports: java.util.*, java.util.concurrent.*
// tickets: tonight's tickets from your database; each has an id and text
// summarise: e.g. a cheap Haiku call that shortens the document
// ── The example ──
ExecutorService pool = Executors.newFixedThreadPool(10);       // at most 10 calls in flight
List<Future<String>> results = tickets.stream()
    .map(t -> pool.submit(() -> summarise(t)))                  // each task makes one Claude call
    .toList();
for (Future<String> f : results) System.out.println(f.get());  // collect as they finish
pool.shutdown();
```

### Seven lifecycle phases

A Claude application moves through the same lifecycle as any engineered system. Each phase ends with a gate you must pass before moving on.

<Flow caption="The lifecycle of a Claude application, with gates between phases" steps={[

- **Functional requirements** - what the system must do, with enough detail to check · these become your eval cases
- **Infrastructure requirements** - latency, scale, **data residency** (which country or region the data is stored and processed in), identity, audit · some of these decide the platform, so capture them first
- **Gates** - don't build until the platform meets residency · don't release until the new version clears the eval

### Choosing a platform

<Imagine text={"Acme's biggest customer insists everything runs inside its own Google Cloud account, under its own access controls."} />

Claude isn't only available from Anthropic directly: the big cloud providers also offer it, so a **platform** here means *where you call Claude from*. The customer's existing cloud, identity and compliance agreements usually decide the platform.

| Platform | Identity and data | Choose when |
|---|---|---|
| Claude API (first-party) | Anthropic identity and terms; new features first | No binding cloud or residency constraint |
| Claude Platform on AWS | Through the customer's AWS account, with Anthropic's own model IDs and release schedule | On AWS, but wants the same features as Anthropic's own API |
| Amazon Bedrock | AWS identity; data stays within the customer's AWS setup | On AWS, with compliance rules that require data to stay there |
| Google Vertex AI | Google Cloud IAM (Google's identity and access system); regional or global endpoints | On Google Cloud |
| Microsoft Foundry (Microsoft's AI platform) | Microsoft's identity and billing | Customer already runs Foundry |

Don't choose on token price alone. Compare the platforms on three things:

- **Latency:** how fast replies arrive, measured from where the customer's users are.
- **Compliance:** whether the platform meets the customer's rules (for example, "data must stay in our AWS account"). This is usually pass or fail: if a platform fails, it's out, however cheap it is.
- **Total cost:** token prices, plus **egress** (the fee a cloud charges when data leaves it), plus platform fees and the effort of integrating it.

### Pin the exact model version you release

<Imagine text={"On Monday morning the chatbot's answers suddenly look different. Nobody deployed anything over the weekend."} />

The **model ID** is the exact name you put in the `model` field. There are two kinds:

| | Full ID (a **snapshot**) | **Alias** |
|---|---|---|
| What it is | A frozen version of the model | A nickname Anthropic re-points to newer versions over time |
| Does it change? | Never: same model every call | Yes, and it may point at different versions on different platforms |
| Use it for | Production | Quick prototypes you'll throw away |

The safe routine for production:

1. Put the full ID in **configuration**, not in code, so changing model is a config change.
2. Keep the previous ID to hand, so you can **roll back** quickly.
3. Move to a new model only after it scores at least as well as your **eval baseline**: the score your current model gets on your test set (Domain 4).

### Ask before you design

<Imagine text={"A bank wants a support assistant that will \"answer anything customers ask\". Before choosing a model or writing a prompt, there are questions that must be answered first."} />

Vague goals hide the decisions that matter most. Before any design, clarify:

| Ask | Why it comes first | Bank example |
|---|---|---|
| **Scope:** which topics may it handle, and which must it refuse or hand over? | It shapes the prompt, the tools, the data it can see and the evals | Account and card questions: yes. Investment advice: no, hand over |
| **Escalation:** when and how does a person take over? | Every assistant needs a safe exit | Disputes, vulnerable customers, anything about fraud |
| **Compliance and data:** what rules apply, and where may data go? | It can rule out platforms, models and features outright | Data must stay in the UK; every answer logged for audit |
| **Success:** how will you know it works? | It becomes the eval set and the release gate (4.1) | 95% of answers correct on 300 labelled real questions |
| **Volume and speed:** how many requests, how spiky, how fast? | It decides streaming, queues, batching and cost (next table) | 50,000 chats a day, replies within 3 seconds |

Model choice, streaming and scaling come **after** these answers, because they depend on them.

### From business need to technical requirement

<Imagine text={"The brief says: \"handle every ticket, answer customers within a few seconds, keep UK data in the UK, and keep costs predictable\". Each phrase quietly implies a piece of infrastructure."} />

Part of the developer's job is turning what the business says into what the system must have. These pairings come up again and again:

| The business says… | So the system needs… | See |
|---|---|---|
| "No request may be lost," with uneven or spiky load | A durable **queue**, a fixed number of workers, retries with backoff, a dead-letter queue | 2.4 |
| "Answers within 2 seconds" | **Streaming**, a smaller or faster model, short outputs, prompt caching | 2.3, 5.5 |
| "Data must stay in the UK/EU" | A platform and **regional** endpoint that meets the rule | 2.5 above, 7.4 |
| "Costs must be predictable" | Token budgets, **workspace spend limits**, the cheapest model that passes, caching, batching | 5.5 |
| "Process last year's 2 million records" | The **Batch API** (nobody is waiting) | 5.4 |
| "Same answer quality after updates" | A **pinned model ID**, versioned prompts, an eval gate | 2.5, 4.1 |
| "The agent must never refund over £100" | A check **in the tool's code**, plus human approval | 7.2 |
| "We must be able to explain any answer" | Logging: prompt version, model, `request-id`, inputs and outputs | 4.4 |

### Version your prompts like code

<Imagine text={"Answers got worse last Tuesday. Nobody changed the code, but someone \"tidied up\" the system prompt in a shared document, and nobody can say what it said before."} />

A prompt is part of your application: change it and behaviour changes. Treat it like code:

- **Keep prompts in files in Git**, not pasted into code or kept in a shared document. Changes then get reviewed in pull requests and are easy to roll back.
- **Give each version an ID** (`support-v7`) and log it with every call (4.4), so you can tell which prompt produced which answer.
- **Change one thing, then run the evals** before releasing (4.1). A prompt change goes through the same gate as a model change.
- **Pin the pair:** a released version is *this prompt with this model ID*. Changing either one is a new release.

```text
prompts/
  support-system.v7.txt      ← live
  support-system.v8.txt      ← candidate: must match or beat v7 on the eval set
config/production.yaml       ← claude.model: claude-sonnet-5-5   prompt: support-system.v7
```

### Keep each environment's configuration separate

<Imagine text={"A developer tries a new system prompt and a newer model in staging. The next morning, production customers are getting the experimental answers too, because both environments read the same configuration."} />

If staging and production share one configuration, every experiment is live. Give each environment its **own** configuration, and move changes forward on purpose:

```text
config/staging.yaml       ← claude.model: claude-opus-5-5     prompt: support-system.v8   (experiment)
config/production.yaml    ← claude.model: claude-sonnet-5-5   prompt: support-system.v7   (released)
```

- **Separate files (or settings) per environment**, each naming its own model ID and prompt version.
- **Separate API keys and workspaces** for staging and production, so a staging mistake can't spend production's budget.
- **Promote, don't share:** a change reaches production only by being copied into production's configuration after it passes the evals, through a reviewed change.

### Changing old Claude code safely

<Imagine text={"A large, old module builds prompts and calls Claude. It has no tests and dozens of callers. Now it must also support a second model provider, and nobody wants to break production."} />

The safe order is the one you'd use for any risky refactor, with one Claude-specific twist:

1. **Pin today's behaviour first** with **characterization tests**: tests that record what the code does now, right or wrong. Because Claude's wording varies, check **properties** (valid JSON, the right fields, a category from the list), not exact text.
2. **Put an interface in front of the model calls**, such as `ModelClient.complete(request)`, with the current Claude code as its first implementation. Callers switch to the interface one at a time.
3. **Change in small, tested steps.** Run the tests and the evals after each one, and add the second provider as another implementation of the same interface.

What not to do: a big rewrite from scratch, a long-lived branch that merges everything at the end, or provider `if` statements scattered through the old code. Each makes it hard to see what broke, and when.

### Organising access: workspaces, limits and the Workbench

In the **Claude Console**, an organisation can be split into **workspaces**, for example one per team or per environment (dev, staging, production). Each workspace has its own API keys, its own **spend and rate limits**, and its own usage reports. A runaway test script in dev then can't use up production's budget, and finance can see what each team spends.

The Console's **Workbench** is a browser playground for drafting and testing prompts against real models before you write any code. When a prompt works there, its code view gives you the request to copy into your app.
